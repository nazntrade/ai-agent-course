# Проверяемый старт проекта

Процесс одинаков для Standalone и CourseModule. Генератор создаёт `.project-bootstrap.json` с типом и версией шаблона и переносимую проверку `.bootstrap/Test-ProjectBootstrap.ps1`. Маркер не содержит ручного флага готовности. Единственный источник состава каркаса — `bootstrap-contract.json`; готовность вычисляется по текущим файлам.

1. **GOVERNANCE: каркас.** Уточнить тип и точную целевую папку, выполнить штатный генератор только в отсутствующую или пустую папку. Если генератор недоступен, показать команду и завершить `BOOTSTRAP_REQUIRED`: не создавать даже SPEC или каталог спецификации. Проверить `Scaffold`.
2. **GOVERNANCE: подготовка.** Configurator заполняет правила и выбранный стек, проверяет наследование и точечные права ролей. Скрипты с `CONFIGURE_ME` на этом этапе допустимы. После изменения конфигурации перезапустить runtime; статическая проверка не подтверждает, что процесс перечитал настройки. Проверить `Specification`.
3. **PRODUCT: спецификация.** Только при готовой подготовке создать `docs/specs/<задача>/{SPEC,PLAN,ACCEPTANCE}.md`, провести review текущих документов. Текстовый PASS другой задачи или проверки корневых правил не является допуском. До реализации сохранить review, привязанный к содержимому комплекта.
4. **GOVERNANCE: точки запуска.** После утверждения PLAN Configurator настраивает четыре `.bat`. Проверить `Implementation -SpecPath docs/specs/<задача>`. Этот результат подтверждает готовность файлов, а не фактический запуск приложения.
5. **PRODUCT: реализация.** Требуются текущая проверка `Implementation`, review актуальной спецификации и разрешение пользователя. После реализации Developer → Architect post-review → Tester. Post-review обязателен перед Tester для каждой реализации, включая работу по существующему дизайну; Architect проверяет соответствие Task Contract без выдумывания нового архитектурного задания.

Пример проверки из папки проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .bootstrap/Test-ProjectBootstrap.ps1 -ProjectRoot "$PWD" -Stage Specification
powershell -NoProfile -ExecutionPolicy Bypass -File .bootstrap/Test-ProjectBootstrap.ps1 -ProjectRoot "$PWD" -Stage Implementation -SpecPath docs/specs/example
```

CourseModule наследует роли и конфигурацию ближайшего курсового корня; при неоднозначности указать `-ParentRoot <абсолютный путь>`. Собственная конфигурация модуля запрещена. Проверка возвращает JSON `schemaVersion/templateType/stage/ready/issues`, exit 0 при готовности и 2 при недостающих условиях или некорректном входе. Отчёт указывает конкретный путь и причину; секреты не читаются.

Существующие проекты не регенерировать и не выдавать за новые. Для read-only аудита старого проекта использовать `-AuditExisting -TemplateType CourseModule` (или Standalone). Этот режим помечает результат `auditOnly`; он не доказывает происхождение от генератора и не выдаёт технический допуск. Старые опубликованные проекты остаются без изменений. Курсовая `.project-bootstrap-policy.json` перечисляет ограниченные пути старых проектов, для новых совпадений `modulePatterns` маркер обязателен.

Перед делегированием изменения Coordinator фиксирует исходное состояние tracked и untracked файлов и передаёт идентификатор снимка в Task Contract. Tester сравнивает результат со снимком начала текущей задачи: получает изменения, появившиеся с этого момента, вместо общего накопленного dirty diff. Снимок не доказывает авторство: изменения пользователя, других процессов и ручных действий после начала задачи также могут попасть в сравнение. Такие изменения нужно явно отделить от выполненного агентом задания при приёмке. При отсутствии или несоответствии снимка не давать PASS; промежуточный commit не требуется. Секреты исключаются из снимков. В контролируемом runtime исходные снимки и review принадлежат контроллеру; чат и ручной marker не подменяют их. Сохранённый SPEC receipt повторно проверяется по актуальному содержимому документов. После перезапуска прежние результаты ролей, реализации и Tester не считаются новым допуском: нужны актуальные проверки текущей задачи.

Инструкции и preflight помогают агенту соблюсти порядок. Фактический запрет записи и устойчивые review/снимки обеспечиваются контроллером среды выполнения. В среде без контроллера это обязательный процесс и диагностика, но не доказательство технической блокировки.

## Готовые задания для запуска процесса

Каждый блок ниже отправляется отдельным сообщением пользователя в указанном порядке. Замените учебный путь `week-06/example-module`, идентификатор `example-feature` и описание задачи на свои. Для Standalone выберите `Standalone` при генерации; после подключения к папке созданного проекта используйте `PROJECT_TARGET: .`. Для CourseModule целевой путь задаётся относительно курсового корня. Путь к штатному генератору определяется отдельно в используемом репозитории шаблонов.

### 1. GOVERNANCE: генерация каркаса

```text
TASK_CLASS: GOVERNANCE
PROJECT_TARGET: week-06/example-module
Создай новый CourseModule штатным генератором New-ProjectFromTemplate.ps1.
Цель — только каркас и проверка Scaffold, без спецификации и кода приложения.
Проверь точный целевой путь и отсутствие содержимого. Не ослабляй запрет генератора на непустую папку и ничего не перезаписывай.
Если генератор нельзя выполнить, верни BOOTSTRAP_REQUIRED, покажи точную команду и заверши работу. В этом случае не создавай целевую папку, SPEC или любые вспомогательные файлы в цели.
Не составляй каркас вручную и не добавляй marker вместо штатной генерации. Существующий проект не регенерируй.
Configurator выполняет разрешённую подготовку; Tester независимо проверяет результат Scaffold.
```

### 2. GOVERNANCE: подготовка правил и прав

```text
TASK_CLASS: GOVERNANCE
PROJECT_TARGET: week-06/example-module
Подготовь сгенерированный проект к спецификации через Configurator.
Проверь Scaffold. Заполни правила проекта/модуля, исходное состояние и выбранный стек; укажи цель, границы и учебные ограничения.
Для CourseModule сохрани наследование корневых правил, конфигурации и пяти ролей. Для Standalone проверь собственные управляющие файлы.
Проверь необходимые точечные права Configurator на управляющие файлы и четыре bat, запрет их редактирования Developer и разрешения запуска Developer/Tester. Не вводи широких allow/ask и не считай временное разрешение сессии конфигурацией.
До спецификации CONFIGURE_ME в bat допустим: команды приложения согласуем после review PLAN. SPEC и код приложения сейчас не создавай.
После изменения конфигурации явно укажи необходимость перезапуска или переподключения runtime. Tester независимо выполняет Specification preflight; готовность файлов не подтверждает перечитывание настроек запущенным процессом.
```

### 3. PRODUCT: только спецификация и независимая проверка

```text
TASK_CLASS: PRODUCT
PROJECT_TARGET: week-06/example-module
PROJECT_STAGE: SPECIFICATION
Подготовь только docs/specs/example-feature/SPEC.md, PLAN.md и ACCEPTANCE.md.
Учебная задача: [вставьте описание ожидаемого поведения, границ и критериев готовности].
Сначала проверь актуальную готовность Specification. При незавершённой подготовке верни BOOTSTRAP_REQUIRED без записи SPEC или иных файлов в цели.
Coordinator формирует Task Contract и фиксирует исходный снимок. Developer создаёт документы. Architect проверяет текущий комплект и возвращает SPEC_GATE_STATUS: PASS и ARCHITECTURE_REVIEW: PASS либо конкретные замечания.
После обоих положительных review-гейтов Tester независимо проверяет документы и возвращает TEST_STATUS: PASS либо конкретные несоответствия. При замечаниях сначала исправьте документы и повторите необходимые проверки.
Код приложения и защищённые файлы не изменять; прикладные тесты и приложение на этой стадии не запускать. Результаты других задач не использовать как допуск. Завершить после приёмки спецификации, без реализации.
```

### 4. GOVERNANCE: настройка запуска по утверждённому PLAN

```text
TASK_CLASS: GOVERNANCE
PROJECT_TARGET: week-06/example-module
Через Configurator настрой setup.bat, test.bat, smoke_test.bat и run_app.bat по проверенному PLAN из docs/specs/example-feature.
Перед настройкой проверь, что утверждённый комплект SPEC/PLAN/ACCEPTANCE актуален. При отсутствии review не угадывай команды и не переходи к реализации.
Проверь необходимые точечные права запуска и запреты редактирования управляющих файлов. Код приложения не изменять, заглушки CONFIGURE_ME должны исчезнуть из всех четырёх bat.
Tester независимо выполняет Implementation preflight с -SpecPath docs/specs/example-feature. Положительный preflight подтверждает готовность файлов, но не фактический запуск ещё не реализованного приложения.
После изменения конфигурации требуется перезапуск или переподключение runtime до следующего задания. Не объявляй, что действующий процесс перечитал настройки, без проверки.
```

### 5. PRODUCT: реализация утверждённого комплекта

```text
TASK_CLASS: PRODUCT
PROJECT_TARGET: week-06/example-module
PROJECT_STAGE: IMPLEMENTATION
ДЕЛАЕМ
Реализуй утверждённую спецификацию docs/specs/example-feature.
До записи кода проверь актуальную готовность Implementation, review текущих SPEC/PLAN/ACCEPTANCE и действующую конфигурацию runtime. При недостающем условии сообщи точный блокер и следующий этап без обхода защиты.
Coordinator фиксирует исходное состояние tracked/untracked для этой задачи. Developer реализует Task Contract и выполняет необходимые проверки. После реализации обязательны Architect post-review и затем независимый Tester.
Tester сравнивает изменения со снимком начала задачи, проверяет критерии на требуемом уровне и сообщает TEST_STATUS. Разницу со снимком не выдавай за доказательство авторства: отдельно учти возможные ручные и внешние изменения.
Правила, роли, конфигурацию и доверенные bat не изменять внутри PRODUCT. Не выдавать статический preflight или моки за фактический запуск приложения либо реальный внешний API. Приёмку объявить только после необходимых актуальных PASS.
```

Заголовки стадии и целевого пути задаёт корневой пользователь; дочернее задание не разрешает себе следующий этап. Положительная строка `ДЕЛАЕМ` относится к конкретному IMPLEMENTATION-заданию. Упоминание слова в цитате, примере или отрицательной фразе не выдаёт разрешение. Публикация требует собственного явно запрошенного действия. Обязательные LIVE-тесты, включая платный remote, разрешаются по разделу ниже; прочие платные вызовы требуют отдельного явного поручения.

## Разрешение LIVE по выбранной тестовой модели

Выбор пользователем любой тестовой модели в панели — local или remote — является явным разрешением обязательных ограниченных LIVE-тестов выбранной моделью, включая платный remote, без повторного вопроса. Это решение передаётся как `AI_TEST_LIVE_POLICY=allowed`; пункт «Запрещено» передаётся как `AI_TEST_LIVE_POLICY=forbidden` и запрещает реальные вызовы. Политика находится вне префикса `AI_TEST_MODEL_*`; запрещённый профиль не заменяется другой моделью или fallback. Coordinator передаёт дочерним ролям актуальные policy, kind/name выбранной модели и границы сценария, без секретов.

`allowed` не запускает inference автоматически: Developer и независимый Tester выполняют только обязательные LIVE-проверки текущего Task Contract через доверенный bat/штатный harness с изолированными TEMP-данными. Local runtime использует lease acquire/use/release в finally и сохраняет чужие/заимствованные модели; remote runtime не запускают и не останавливают локально. Обычные UNIT/INT остаются offline с mock/stub, LIVE учитывается отдельно. Выбор модели не разрешает скачивание моделей, чтение/вывод секретов, использование рабочей пользовательской БД или остановку чужих моделей; read-only аудит сам по себе не запускает inference.

При `forbidden` не выполняй реальные embedding/chat-вызовы независимо от старых RUN-флагов и унаследованных профилей, продолжай разрешённые offline-проверки. Если LIVE обязателен, фиксируй конкретный policy-блокер и невыполненные проверки (BLOCKED/PARTIAL), не запрашивай повторное разрешение для обхода запрета и не выдавай mock-тесты за полный PASS. Неподдерживаемое значение policy также блокирует LIVE (fail closed). Если вне панели policy отсутствует, модельные переменные сами по себе не дают разрешения: сохраняется ранее явно предоставленная пользователем авторизация standalone-сценария. Без policy задача реализовать и проверить/протестировать AI-функцию или завершить её приёмку сохраняет разрешение обязательного ограниченного local-сценария; remote/платный standalone-сценарий требует явной авторизации пользователя. Явный запрет имеет приоритет.

Если разрешённый профиль, сервер или lifecycle недоступны, проверь доступность штатным preflight/runner в разрешённых границах без чтения `.env` и вывода секретов, укажи конкретную фактическую причину вместо абстрактного «нужно разрешение». В итоговом отчёте явно укажи решение пользователя (`allowed`/`forbidden` либо standalone-авторизацию), выбранную модель или её отсутствие, фактически выполненные/невыполненные LIVE-проверки и причины. Моки не подтверждают реальную генерацию, provider-контракт или lifecycle.

## Доступность команд обязательной приёмки

До Implementation для каждого обязательного критерия ACCEPTANCE зафиксируй достаточный уровень проверки и одну из двух связок: проверка агента → точная доверенная команда проекта с её mode/аргументами; внешняя проверка → конкретный ответственный и ожидаемое свидетельство (например, проверка интеграции владельцем внешнего сервиса в рамках порученной задачи). Наличие общего test.bat не доказывает наличие режима полного сценария; прямой запуск неизвестной команды не заменяет подготовленный entrypoint.

Шаблоны включают готовую универсальную доверенную точку `test.bat scenario <slug>` и stdlib-dispatcher `harness/scenario_runner.py`. При первичной GOVERNANCE настройте `TEST_SCENARIO_PYTHON` на существующий Python 3.10+ либо подготовьте `.venv/Scripts/python.exe`; сценарий не устанавливает зависимости. Это отдельный тестовый исполнитель и для приложения другого стека: approved-адаптер стека создаётся при начальной подготовке. Developer добавляет обычные PRODUCT-файлы `tests/scenarios/<slug>.py` и одноимённый JSON с точными полями `{"schema_version":"test-scenario-v1","kind":"offline"}` либо `kind: live`, без изменения защищённого bat и без Configurator в PRODUCT. Slug: `[a-z][a-z0-9-]{0,63}`; произвольные пути, дополнительные аргументы, symlink/reparse запрещены. OFFLINE очищает профиль и Tavily, устанавливает forbidden; LIVE требует allowed и полный выбранный профиль, а lifecycle остаётся обязанностью сценария. Конфигурация остальных CONFIGURE_ME-команд сохраняется отдельной GOVERNANCE, без расширения PRODUCT-допуска.

Перед Implementation и перед приёмкой Coordinator и независимый Tester сверяют эту матрицу с фактическими разрешёнными bat и их поддерживаемыми режимами. Configurator на отдельном GOVERNANCE-этапе готовит недостающий mode по проверенному PLAN до PRODUCT-реализации; планируемый продуктовый harness реализует Developer, фактический запуск проверяется после реализации. При отсутствии обязательного entrypoint фиксируй точный защищённый файл/mode и GOVERNANCE_REQUIRED/BOOTSTRAP_REQUIRED, не расширяй shell permissions и не проси повторное общее разрешение вместо подготовки команды. PRODUCT/GOVERNANCE-разделение сохраняется.

Критерии порученной задачи с явно назначенным внешним ответственным учитываются отдельно: их отсутствие не останавливает выполнение и завершение разрешённых проверок агента. В отчёте разделяй завершённые проверки агента и полный результат проекта; при невыполненных внешних критериях общий результат остаётся PARTIAL/NOT_ASSESSED, а не полный ACCEPTED.

Coordinator ведёт пользователя одним конкретным следующим действием только там, где действительно нужен человек: где выполнить, что сделать, зачем и какое свидетельство подтвердит результат. Внутреннюю делегацию, наличие доверенной команды и добавление PRODUCT-сценария не перекладывай на пользователя; после завершённого bootstrap не требуй от него терминов TASK_CLASS или названий ролей. Явно назначенный внешний ответственный в рамках порученной задачи не создаёт сам по себе необходимость вопроса через API. Расширение GOVERNANCE-области по-прежнему требует явного согласования; конкретный неустранимый блокер отражай честно.

## Test runtime: выбранная модель приложения

До Specification Configurator заполняет единственную декларацию `test-runtime-json` в PROJECT_RULES/MODULE_RULES: applicability `none` для проекта без AI либо `ai` для AI-проекта. `unresolved` запрещает Specification и Implementation. Для `ai` фиксируются поля по примеру из bootstrap-guide. Модели ролей агента, генерации ответов приложения и embeddings — разные контракты; выбранный chat-профиль не заменяет embedding-модель.

Присутствующий профиль `AI_TEST_MODEL_*` имеет приоритет для генерации ответов приложения в тестах: KIND (`local`/`remote`), BASE_URL, NAME; API_KEY обязателен для выбранного профиля (local и remote), секрет не выводить. Для live-прогона local требуется loopback LEASE_URL; приложение с внешним владельцем может использовать local без собственного lease. Частичный или неподдерживаемый профиль — явная ошибка до реализации/тестов, без молчаливой замены модели. Только полностью отсутствующий профиль допускает явный конфиг приложения. SPEC/PLAN/ACCEPTANCE должны описать адаптер, модель/провайдер, реальную проверку выбранной модели и требуемый UI-инструмент; preflight не доказывает доступность сервера, inference или UI.

Локальный управляемый runtime: внешний test-harness приобретает lease через AI_TEST_MODEL_LEASE_URL, передаёт дочерним процессам готовый профиль (AI_TEST_MODEL_PARENT_READY=1), освобождает свой lease в finally при успехе, ошибке и штатном прерывании. Дочерний процесс не освобождает lease родителя. Lifecycle — acquire/use/release, а не безусловная остановка: borrowed/уже работающая или используемая другим потребителем модель не выгружается; при отсутствии доказуемого владения выгрузка запрещена. Remote-профиль не запускают и не останавливают локально. Ключи и приватные endpoint не сохраняются в публичных правилах, примерах и отчётах.

AI-декларация (none требует только schemaVersion/applicability):

```test-runtime-json
{
  "schemaVersion": 1,
  "applicability": "ai",
  "profileEnvironment": "AI_TEST_MODEL_",
  "profileRole": "chat",
  "provider": "openai-compatible",
  "absentProfile": "explicit-config",
  "partialProfile": "reject",
  "embeddings": "independent",
  "lifecycle": "lease-finally"
}
```

Scaffold принимает unresolved; Specification/Implementation требуют заполненную декларацию. Отсутствие профиля допускает только явный конфиг приложения. Env preflight проверяет структуру без чтения .env, без сетевых вызовов и без печати значений. URL допускает только HTTP(S), без userinfo/query/fragment. При live-приёмке отдельно проверяются readiness, настоящая генерация, выбранная identity и cleanup lease. Non-AI проекты не требуют AI-сервера.

## Полная матрица приёмки и доказательства

Матрица содержит только критерии порученной агентам задачи. Требования за пределами порученной агентам задачи не включаются в матрицу и не перечисляются в их отчётах, даже как исключённые; не снижают статус.

До первой реализации Coordinator фиксирует полный состав критериев из задания и SPEC/ACCEPTANCE в fenced-блоке `acceptance-contract`: JSON `{"schema_version":"acceptance-contract-v1","criteria":[{"id":"C01","required":true,"owner":"agent","requirement":"Обязательное наблюдаемое поведение","source":"Задание или точная ссылка на критерий SPEC/ACCEPTANCE","check":"Достаточный уровень проверки и точная trusted-команда либо способ ручной проверки"}]}`. Список непустой; id уникальны и стабильны; required — boolean, owner — только agent/external; requirement/source/check непустые. Пример формы не заменяет конкретные критерии задачи. Architect сверяет полноту и смысл с исходным заданием, включая качество результата, ошибочные сценарии и явно запрошенные артефакты.

Полный структурированный acceptance-contract-v1 обязателен уже в первом поручении (task prompt) делегируемой роли, до её запуска: fenced-блок acceptance-contract с валидным JSON, а не только описание критериев прозой. Объяснение или JSON, показанные лишь в чате, не считаются передачей контрактного блока в task prompt. Перед каждым handoff Coordinator проверяет схему и полный неизменённый состав. Ошибку формата или отсутствие блока Coordinator исправляет в той же задаче до вызова роли, сохраняя исходные критерии; новое задание или повторное поручение от пользователя для исправления внутренней передачи не требуется.

Контракт замораживается до первого editor: весь состав, обязательность, owner, смысл и достаточный уровень проверки сохраняются при каждом делегировании, продолжении и перезапуске. Центр передаёт полный контракт дочерним задачам; Coordinator передаёт его целиком и проверяет совпадение, а не сокращает до списка технических тестов. Нельзя удалять, переименовывать, перепоручать критерии или ослаблять их формулировку ради PASS. При продолжении используй проверенный исходный контракт из родительского задания; старый PASS не заменяет актуальные доказательства. Реальное изменение пользовательского задания фиксируется отдельно и проходит проверку, а не скрытое редактирование матрицы.

MANUAL — способ проверки, а не автоматическое назначение пользователю. Developer и независимый Tester могут читать исходники и фактические ответы, сравнивать с источниками и сохранять протокол проверки через разрешённые инструменты. Owner external допустим только для действия внутри порученной агентам задачи, при явном внешнем назначении либо действительно недоступной агенту возможности; запрет/отсутствие инструмента отражается конкретно. Не объявляй ручной критерий выполненным по одному запуску тестов. Не добавляй произвольные пороги качества или дополнительные LIVE-вызовы: уровень доказательств следует исходному критерию и действующей авторизации.

Независимый Tester выдаёт fenced-блок `acceptance-evidence`: JSON `{"schema_version":"acceptance-evidence-v1","criteria":[{"id":"C01","status":"PASS","evidence":["Путь к фактическому протоколу или проверяемому результату"],"reason":""}]}`. Точные id покрывают весь исходный список, включая необязательные критерии, без дубликатов и добавлений. Status — PASS/FAIL/BLOCKED/NOT_ASSESSED; PASS требует непустых проверяемых ссылок evidence, любой иной статус — непустой конкретной reason. Укажи выполненную проверку, фактический результат и ограничения доказательства; ссылка на команду или существование файла сами по себе не подтверждают качество. Developer предоставляет материалы, но не принимает собственную реализацию; Tester проверяет их достаточность независимо.

Итоговый ответ независимого Tester обязательно содержит структурированный fenced-блок acceptance-evidence с acceptance-evidence-v1; обычный текст TEST_STATUS не заменяет этот блок. Для каждого PASS подтверждение соответствует уровню исходного check: требуемое реальное поведение, фактические ответы и их качество не подменяются mock/unit, доступностью порта или успешным выполнением команды.

TEST_STATUS описывает технический прогон в заявленной области и не означает общую приёмку. Agent acceptance завершена, только если все обязательные owner=agent критерии имеют независимый PASS с достаточными доказательствами. Project acceptance допускает ACCEPTED, только если ВСЕ обязательные критерии, включая external, имеют такой PASS. Любой непроверенный/заблокированный/проваленный обязательный критерий исключает общий ACCEPTED: отчёт отдельно показывает технический результат, результат агентской проверки и общий PARTIAL/BLOCKED/FAIL/NOT_ASSESSED с конкретными остатками. Отсутствующий/невалидный контракт или evidence блокирует ACCEPTED, но не запрещает безопасное продолжение и исправление legacy-задачи. Доводи разрешённую агентскую часть до конца независимо от ожидаемой внешней проверки.
