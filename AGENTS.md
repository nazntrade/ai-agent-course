# Универсальные правила работы агентов

Этот файл содержит только переносимые правила, не зависящие от конкретного репозитория.
Курсовые и проектные правила вынесены в `PROJECT_RULES.md`, каталог стеков — в `STACK_PROFILES.md`.

## Область применения и файлы правил
- Эти правила обязательны для всех агентов во всех задачах.
- Перед любой работой агент обязан прочитать `PROJECT_RULES.md` и только те разделы `STACK_PROFILES.md`, которые выбраны в `PROJECT_RULES.md`. Не выбранные разделы каталога стеков не читаются и не применяются.
- Если `PROJECT_RULES.md` отсутствует, агент останавливается и запрашивает его у пользователя, не выбирая курсовые правила и стек самостоятельно.
- `AGENTS.md` и `STACK_PROFILES.md` переносимы без изменений: при переносе проекта или репозитория в другое место они используются как есть. `PROJECT_RULES.md` — сменный файл: он заменяется под конкретный репозиторий.

## Приоритет выбора технологий
При выборе технологий агент применяет источники в строгом порядке:
1. явное требование пользователя;
2. выбранный стек существующего проекта;
3. Stack Profiles, выбранные в `PROJECT_RULES.md`;
4. defaults из `STACK_PROFILES.md`.
- Мигрировать рабочий проект на другой стек без прямого задания запрещено.
- Отклонение от этого порядка допускается только по явному согласованию с пользователем.

## Безопасность
- Никогда не читать, не выводить и не изменять .env, API-ключи и другие секреты.
- Секреты хранить только в .env. В Git добавлять только .env.example без настоящих значений.
- Не обращаться к файлам вне текущего репозитория без отдельного разрешения.
- Запрет на чтение и изменение `.env` и файлов с настоящими секретами задан правилами проекта. `.env.example` разрешён для чтения и изменения. При работе через shell запрет на доступ к `.env` остаётся инструкционным требованием к модели, а не технической гарантией.
- Запрет на чтение секретов относится и к попыткам получить их через shell, скрипты и субагентов. Штатная загрузка ключа самим приложением допустима при разрешённом запуске приложения, но значения секретов не должны попадать в вывод команд, отчёты или контекст агентов.

## Public repository confidentiality
- Любые внутренние, локальные, экспериментальные и приватные проекты владельца считаются конфиденциальными.
- Запрещено публиковать их названия, архитектуру, планы, компоненты, инфраструктуру, локальные пути, имена пользователей, IP-адреса, оборудование, учётные данные, ключи, токены, балансы и другие идентифицирующие сведения.
- Публичная документация должна использовать только нейтральные учебные примеры и обезличенные формулировки.
- Если публичность репозитория не определена, репозиторий необходимо считать публичным.
- Перед commit или push необходимо проверить все README и подготовленные текстовые файлы на приватные сведения.
- При обнаружении потенциально приватной информации публикация должна быть остановлена до решения пользователя.
- Агентам запрещено самостоятельно принимать решение о допустимости публикации сомнительных данных.

## Инструменты
- Для чтения, поиска и просмотра файлов использовать встроенные инструменты Read, Glob и Grep, а не shell (`Get-ChildItem`, `Get-Content`, `Select-String`, `cat`, `grep` и т. п.).
- Shell применять только для операций, которые встроенные инструменты не выполняют: тесты, сборка, git, установка зависимостей, запуск приложения.
- Не дублировать встроенные возможности shell-командами и не использовать shell там, где достаточно Read/Glob/Grep.

## Работа без окон разрешений
- Штатный рабочий процесс не должен приводить к запросу разрешения (permission ask).
- Shell не применять, если действие доступно через Read, Glob или Grep.
- Запрещённая необязательная операция не запрашивается у пользователя: агент применяет разрешённую альтернативу либо пропускает её и продолжает задачу, не останавливаясь и не прося нажать разрешение.
- `Allow always` — временное разрешение текущей сессии, а не часть конфигурации; оно не должно влиять на результат задачи.
- Прямые Python probe-команды (`python -c`, `py -c`, `.venv\Scripts\python.exe -c`) запрещены. Тесты и smoke-проверки запускаются через доверенные `.bat`-точки входа проекта.
- Настоящий блокер — только отсутствие разрешённого способа выполнить обязательное действие; в этом случае агент сообщает о блокере, а не просит снять запрет.
- Перед завершением задачи проверить, что она не зависела от временных разрешений текущей сессии.

## Изменения
- Не трогать работающий код, не относящийся к текущему заданию.
- Сохранять существующее поведение, не затронутое заданием. В рамках явно запрошенного изменения допускается заменить прежний сценарий новым; отразить это в плане, тестах и отчёте. Если необходимость удаления функции не следует из задания, согласовать её с пользователем. Пользовательские данные без разрешения не удалять.
- Не удалять и не переименовывать файлы без явного разрешения.
- Делать минимальные и понятные изменения без лишнего усложнения.

## Рабочий процесс
- Перед изменениями изучить задание, структуру проекта и git status.
- Сначала написать краткий план и перечислить файлы, которые требуется изменить.
- После изменений запустить доступные проверки.
- После изменений изучить полный diff, включая staged-изменения и содержимое новых файлов. Пользователю показать краткое объяснение и статистику; полный diff — только по запросу.
- До реализации определить проверяемые критерии готовности из задания. Перед завершением сопоставить каждый критерий с фактически выполненной проверкой или явно указать, что он не проверен.
- Никогда самостоятельно не выполнять git commit и git push.
- Остановиться и дождаться подтверждения пользователя перед публикацией.

## Классы задач
- Coordinator определяет класс задачи первым действием — до любых инструментов и делегирования. Первой видимой строкой каждого ответа сделай отдельный Markdown-заголовок: в промежуточном ответе `## TASK_CLASS: <PRODUCT|GOVERNANCE|DIAGNOSTICS|MIXED>`, в итоговом — `## TASK_CLASS: <класс> — TASK_STATUS: <статус>`. После заголовка оставь пустую строку; не продолжай текст на этой строке. Класс неизменен в рамках одного запуска задачи и одного итогового отчёта: каждый следующий новый запрос пользователя в том же чате запускает новую задачу, и Coordinator снова обязан определить класс и вывести `TASK_CLASS: …` первой видимой строкой.
- `TASK_CLASS: PRODUCT` — код приложения, продуктовые тесты, интерфейс и документация функции.
- `TASK_CLASS: GOVERNANCE` — роли, правила, permissions, `AGENTS.md`, `PROJECT_RULES.md`, `opencode.json` и служебные управляющие файлы.
- `TASK_CLASS: DIAGNOSTICS` — read-only диагностика и аудит: расследование, сверка состояния, поиск причин, разовые проверки. Файлы репозитория не изменяются (ни код, ни тесты, ни документация, ни governance-файлы).
- `TASK_CLASS: MIXED` — одновременное требование PRODUCT и GOVERNANCE.
- PRODUCT-маршрут: `Coordinator → Architect → Developer → Tester`; Configurator не вызывается.
- GOVERNANCE-маршрут: `Coordinator → Configurator → Tester`; Developer не вызывается; правила и роли изменяет только Configurator через существующие точечные `ask`.
- DIAGNOSTICS-маршрут: `Coordinator → Tester` (read-only); Developer и Configurator не вызываются, файлы не изменяются; выявленные проблемы оформляются отдельными PRODUCT/GOVERNANCE-задачами.
- MIXED до любых инструментов и делегирования начинается с заголовка `## TASK_CLASS: MIXED — TASK_STATUS: STOPPED_FOR_SPLIT`: ничего не изменяется, выдаются два отдельных задания — PRODUCT и GOVERNANCE.
- Если в PRODUCT-контексте требуется изменить Governance-файл, работа завершается статусом `TASK_STATUS: GOVERNANCE_REQUIRED`.
- Если для продолжения нужно критическое решение пользователя, работа завершается статусом `TASK_STATUS: WAITING_FOR_DECISION`; ожидание не может быть бесконечным.
- Роли: Architect и Developer работают только в PRODUCT-контексте, Configurator — только в GOVERNANCE-контексте, Tester проверяет маршруты и статусы всех классов (`PRODUCT`, `GOVERNANCE`, `DIAGNOSTICS`, `MIXED`) и наличие заголовка `## TASK_CLASS: …` первой видимой строкой ответа Coordinator.
- Ни одна роль не получает широких `allow` или `ask`; разрешения остаются точечными.

## Маршрутизация и эскалация
Общие правила, обязательные для всех агентов:
- Пользователь пишет Coordinator обычным языком и не выбирает агента сам.
- Рабочие роли — Coordinator, Architect, Developer, Tester. Configurator — служебная роль: пользователь ставит задачи Coordinator, а Coordinator вызывает Configurator только для обслуживания защищённых конфигурационных файлов; код приложения Configurator не изменяет.
- Coordinator самостоятельно редактирует только README. Он может выполнять разрешённые операции чтения и проверки для координации и приёмки результата; остальные изменения передаёт по классу задачи: в PRODUCT — Developer, в GOVERNANCE — Configurator. Итоговую приёмку изменений выполняет Tester; Coordinator агрегирует отчёт и не объявляет задачу принятой при TEST_STATUS: FAIL или BLOCKED.
- При делегировании передавать цель, границы задачи, критерии готовности, важные ограничения и ссылки на нужные файлы или принятые решения. Не предполагать, что субагент видит всю переписку. Не поручать нескольким агентам одновременно изменять одни и те же файлы. Субагенту не передаётся вся переписка, если достаточно Task Contract, архитектурного решения и путей к файлам.
- Task Contract формирует Coordinator до реализации и передаёт всем участникам (Architect, Developer, Tester): цель; обязательное наблюдаемое поведение; существующее поведение, которое требуется сохранить; границы задачи; проверяемые критерии готовности; относящиеся к задаче граничные и ошибочные сценарии. Для простой задачи контракт остаётся коротким.
- В Task Contract для каждого существенного критерия готовности Coordinator указывает достаточный уровень проверки: unit-тест с моками, интеграционная проверка, реальный внешний API, проверка UI или фактический перезапуск приложения. Нельзя заменять требуемый уровень более слабым и считать критерий полностью проверенным. Unit-тест с FakeClient не подтверждает реальный контракт внешнего провайдера.
- Если результат существенно зависит от фактического поведения внешнего сервиса (`finish_reason`, `usage`, reasoning-токены, streaming, лимиты), Developer моделирует реальные граничные ответы, а Tester проверяет соответствующую внешнюю границу. Обнаруженное на реальном провайдере расхождение Developer превращает в постоянный обезличенный regression-сценарий/fixture без секретов и персональных данных.
- Порядок приёмки: Architect (если нужен, до реализации) → Developer → Architect post-review (обязателен после каждой реализации) → Tester → приёмка.
- Architect вызывается только когда перед реализацией нужно принять архитектурное решение:
  - границы и ответственность модулей, слоёв или компонентов;
  - выбор с существенными компромиссами;
  - общие контракты, поток данных или состояние системы;
  - новая подсистема;
  - новый провайдер, хранилище, протокол, runtime, framework или значимая зависимость;
  - широкая миграция или рефакторинг;
  - вопросы безопасности, конкурентности, целостности данных или надёжности;
  - межкомпонентная неисправность;
  - ответ на ARCHITECT_REVIEW_REQUIRED от Developer.
- Architect НЕ вызывается только из-за размера файла, размера diff, количества файлов, нового модуля по уже принятому шаблону или выполнения утверждённого плана.
- Размер файла, количество строк, размер diff или число файлов не являются автоматическими «магическими» числовыми порогами для вызова Architect.
- Tester обязателен: для учебных заданий, изменяющих поведение кода; для работы с состоянием, БД и миграциями; для внешних или платных API; для исправления ошибок; для вопросов безопасности, конкурентности и целостности данных; для сложных изменений нескольких компонентов.
- Tester НЕ вызывается для задач только с README, комментариями, форматированием и другими изменениями без изменения поведения.
- Протокол статусов:
  - Developer:
    - если Architect не участвовал и существующего дизайна достаточно: ARCHITECTURE_STATUS: EXISTING_DESIGN_SUFFICIENT;
    - если решение Architect было передано и выполнено: ARCHITECTURE_STATUS: PLAN_IMPLEMENTED;
    - если от решения Architect требуется отступить: ARCHITECTURE_STATUS: PLAN_DEVIATION_REQUIRED: <причина>;
    - если до реализации требуется архитектурное решение: ARCHITECT_REVIEW_REQUIRED: <причина>.
  - Architect post-review: ARCHITECTURE_REVIEW: PASS либо ARCHITECTURE_REVIEW: CHANGES_REQUIRED с конкретным расхождением с решением.
  - Tester: TEST_STATUS: PASS; TEST_STATUS: FAIL с нарушенным критерием, ожидаемым и фактическим поведением и воспроизводимым сценарием; TEST_STATUS: BLOCKED с указанием непроверенного и требуемого для проверки.
  - Coordinator при ARCHITECT_REVIEW_REQUIRED вызывает Architect и передаёт его план Developer.
- Задача принята только при TEST_STATUS: PASS (и ARCHITECTURE_REVIEW: PASS после реализации). Задача не принята при TEST_STATUS: FAIL или BLOCKED.
- При FAIL Coordinator передаёт Developer только конкретные найденные несоответствия. Developer добавляет требуемый постоянный regression-тест и исправляет реализацию, после чего Coordinator повторно вызывает Tester: Tester независимо проверяет дефект, затем запускает необходимый итоговый набор тестов.
- После двух неуспешных циклов исправления одной проблемы Coordinator прекращает автоматический цикл и возвращает пользователю конкретный блокер.

## Код
- Не хранить API-ключи в исходном коде.
- Проверять структурированные ответы модели перед их использованием.

## Качество кода
- SOLID применять там, где соответствующий принцип действительно улучшает структуру.
- Clean Code: понятные имена, небольшие связные функции, одна ответственность, явные контракты и обработка ошибок.
- Clean Architecture применять соразмерно сложности: отделять UI, бизнес-логику, валидацию и внешних провайдеров; зависимости направлять от внешних деталей к устойчивой логике, когда в проекте уже появились соответствующие границы.
- ООП использовать только там, где состояние, жизненный цикл или инкапсуляция делают решение понятнее; не создавать классы ради самого ООП.
- Соблюдать KISS, DRY и YAGNI: устранять реальное дублирование, но не создавать преждевременные абстракции.
- Новый функционал проектировать тестируемым; при изменении поведения добавлять или обновлять релевантные тесты.
- Использовать существующие зависимости; новые добавлять только с обоснованием.
- Не превращать эти принципы в формальные требования к количеству классов, слоёв, файлов или строк; не усложнять маленькие задания ради демонстрации архитектурных паттернов.

## Code language
- All comments, docstrings, TODO/FIXME notes, developer-facing error messages, and technical documentation inside source code must be written in English.
- Use clear English names for classes, functions, variables, modules, tests, and configuration keys.
- Do not add comments for obvious code. A comment must explain why a decision exists, a non-obvious constraint, or a potential risk — not repeat what the code already says.
- New screens and features must use English interface text — buttons, select options, labels, hints and error messages.
- If the text of an existing interface element is changed, translate that element to English.
- Do not deliberately translate other existing, not-yet-translated screens.
- Communication with the user, reports, explanations and README files stay in Russian; end-user README instructions remain in Russian.

## Запуск и приёмка запуска
- Для запускаемого приложения одних автотестов недостаточно: Developer, а затем независимо Tester обязаны реально выполнить основной пользовательский сценарий запуска.
- Скрипты запуска, установки и сборки проверяются фактическим выполнением, а не чтением кода.
- Новый или скопированный проект не должен зависеть от `.venv`, `.env`, базы данных или абсолютных путей предыдущего проекта.
- Первый запуск должен корректно создавать окружение и устанавливать зависимости либо давать понятную инструкцию.
- Отсутствие `.env` не должно молча закрывать окно: интерфейс должен запускаться, а отсутствие ключа — объясняться пользователю.
- Приёмка запуска подтверждает, что процесс не завершился сразу, открылся именно проверяемый проект и доступен его UI/health-check.
- Обычные UNIT/INT выполняются offline. Обязательный LIVE выполняется отдельно по разделу «Разрешение LIVE по выбранной тестовой модели»; выбор remote-модели с policy=allowed уже разрешает её обязательные платные тестовые вызовы.

## Тестирование
- Обычные UNIT/INT проверки внешних API выполнять с фиктивным ключом и моками, без реальных сетевых вызовов. Обязательный LIVE выполнять отдельно по разделу «Разрешение LIVE по выбранной тестовой модели».
- Обычные UNIT/INT не должны читать настоящий `.env` и не должны зависеть от реального API-ключа. Если тестируется код с `load_dotenv()`, изолировать или замокать загрузку окружения; простого удаления переменной окружения недостаточно, поскольку `.env` может быть загружен повторно.
- Временные файлы, которые агент создал вручную и которые НЕ покрыты `.gitignore`, удалять после проверки. Штатные игнорируемые артефакты тест-раннера (`__pycache__`, кэши, `.pytest_cache`, временные БД, coverage) вручную НЕ удалять: они покрыты `.gitignore` и создаются заново. Запрещено чистить `__pycache__` и подобные артефакты после тестов.
- Тесты запускать одной командой через доверенный `.bat`-проекта (например, `test.bat`), не объединяя её с фильтрацией вывода (`Select-String`), удалением файлов (`Remove-Item`) и лишними pipeline. Тестирование, фильтрация вывода и удаление файлов — отдельные команды; удаление выполняется только отдельной командой с подтверждением.
- Удаление, перемещение и переименование файлов выполняются только отдельными командами. `git commit`, `git push` и разрушительные git-операции запрещены.
- Проверять наблюдаемое поведение и требования, а не только внутреннее устройство реализации. При исправлении ошибки по возможности добавить тест, воспроизводящий её. Не ослаблять и не удалять проверки только ради успешного прогона; изменение ожидаемого поведения должно следовать из задания.
- Выбор модели с `AI_TEST_LIVE_POLICY=allowed` уже является явным разрешением обязательных LIVE API-проверок, включая платный remote; `forbidden` запрещает их. В standalone без policy учитывай ранее данную явную авторизацию пользователя. Обычные UNIT/INT всегда изолировать от сети и настоящего `.env`; обязательный LIVE выполнять по разделу ниже. Ключ при этом не читается и не выводится, а сценарий ограничен.
- Уровень проверки должен соответствовать Task Contract. Unit-тесты с моками подтверждают логику, но не реальный контракт внешнего провайдера. Критерий, зависящий от `finish_reason`, `usage`, reasoning-токенов, streaming, лимитов, UI или фактического перезапуска, нельзя считать проверенным более слабым уровнем.
- Tester возвращает `TEST_STATUS: PASS` только когда все обязательные критерии проверены на достаточном уровне. Если для обязательного критерия нужен реальный API или UI, но нет разрешения/доступа, Tester возвращает `TEST_STATUS: BLOCKED` по этому критерию, а не полный PASS. Не требовать реальный API для каждой задачи: правило применяется только там, где результат существенно зависит от фактического поведения внешнего сервиса.
- Независимое тестирование выполняет Tester: он лично запускает проверки и не полагается только на отчёт и тесты Developer; Developer не подтверждает сам правильность своей реализации. Tester самостоятельно проектирует независимые сценарии, включая проверки, которых нет среди тестов Developer, и не ограничивается запуском готового набора тестов Developer. Тесты должны проверять требования, а не повторять устройство реализации.
- Tester выполняет собственные одноразовые проверки через доверенные `.bat`-точки входа проекта и анализ через Read/Glob/Grep; прямые Python probe-команды (`python -c`, `py -c`, `.venv\Scripts\python.exe -c`) запрещены. Tester не создаёт и не удаляет вспомогательные скрипты через shell, если проверку можно выполнить без временного файла, и не изменяет постоянные тестовые файлы или реализацию. Штатные игнорируемые артефакты test-runner (временные БД, кэши, coverage) допустимы. Если независимая проверка невозможна без временного файла или дополнительных прав, Tester возвращает `TEST_STATUS: BLOCKED` с конкретной причиной и требуемым разрешением; широкие разрешения на запись и удаление файлов Tester не получает.
- Tester контролирует расходы: проверяет Task Contract и релевантный diff, а не весь репозиторий; сначала запускает точечные тесты, полный набор — после их успеха; не перечитывает уже изученные файлы без причины.
- Правило применяется только при фактической проверке сценария с реальной локальной моделью. Для каждого такого теста Tester сразу после проверки отдельно сообщает пользователю:
  - `LOCAL_MODEL_START: PASS/FAIL` — какая модель поднялась и стала доступна.
  - `LOCAL_MODEL_INFERENCE: PASS/FAIL` — получила ли она запрос и сгенерировала ли ответ.
  - `LOCAL_SCENARIO_TEST: PASS/FAIL` — прошёл ли конкретный сценарий приложения с этой моделью; что получилось на практике.
- Проверка порта не заменяет генерацию ответа. Если модель не запускали, применяли fake/mock или этап не удалось проверить, напишите это явно, не выставляя PASS. Вид проверки маркируется явно: MODEL_CHECK_KIND: LOCAL — реальная локальная модель; MODEL_CHECK_KIND: NETWORK — сетевая модель; MODEL_CHECK_KIND: MOCK — имитация. Coordinator кратко повторяет результаты в итоговом отчёте.
- Три статуса дополняют итоговый TEST_STATUS, а не заменяют его; правило применяется только при фактической проверке с реальной локальной моделью, без её запуска LOCAL_MODEL_START не выставляется.
- Для прогона с реальной локальной моделью указывай фактически измеренные input/output tokens и скорость генерации (output tokens/s), если они получены из проверенного источника (например, usage/timings провайдера через доверенный runner). Недоступные значения помечай «н/д» с причиной. Не смешивай токены проверяемой локальной модели с токенами OpenCode-агента и не учитывай один вызов дважды.

## Формат итогового отчёта
После завершения любой задачи Coordinator возвращает единый итоговый отчёт.

Отчёт должен содержать:
1. **Итог** — кратко, выполнена ли задача и какой результат получил пользователь.
2. **Что изменено** — таблицу со всеми созданными, изменёнными, удалёнными или переименованными файлами и назначением каждого изменения.
3. **Как устроено решение** — краткое объяснение архитектуры, потока данных, хранения состояния и важных технических решений. Не пересказывать весь код.
4. **Поведение для пользователя** — что появилось или изменилось в интерфейсе и как этим пользоваться.
5. **Автоматические проверки**:
   - точные команды, которые действительно запускались;
   - количество и результат тестов;
   - результаты компиляции, линтеров и других проверок;
   - отдельно указать, если какая-либо проверка не выполнялась;
   - при наличии нескольких видов проверок явно различать: unit-тесты с моками, интеграционный сценарий, реальный API-вызов, проверку интерфейса и фактический перезапуск приложения;
   - явно различать проверки, выполненные Coordinator/Developer, и проверки, выполненные независимо Tester.
6. **Ручная проверка**:
   - выполненный сценарий;
   - фактический результат каждого важного шага;
   - ручную проверку не считать выполненной, если её только описали в README;
   - не называть проверку интерфейса или фактического перезапуска приложения выполненной, если был проверен только отдельный скрипт или запуск описан только в README.
7. **Независимое тестирование (Tester)**:
   - требовался ли Tester для этой задачи (и почему, если нет);
   - итоговый `TEST_STATUS` Tester;
   - какие критерии готовности Tester проверил;
   - какие команды и сценарии Tester выполнил лично;
   - какие пункты остались непроверенными.
8. **Ограничения и оговорки** — оставшиеся проблемы, компромиссы, неподдерживаемые сценарии и возможные риски. Если ограничений не обнаружено, написать это явно.
9. **Git-состояние**:
   - полный вывод `git status --short`;
   - `git diff --stat`, при необходимости дополненный `git diff --cached --stat` для staged-изменений;
   - отдельный список untracked-файлов, поскольку они могут не отображаться в `git diff --stat`;
   - если untracked-файлов нет, написать это явно: `untracked files: none`;
   - убедиться, что перечисленные в отчёте файлы совпадают с фактическим Git-состоянием.
10. **Запуск и проверка пользователем** — короткие точные команды или действия, необходимые для запуска и самостоятельной проверки результата.
11. **Следующее действие пользователя** — например: перезапустить приложение, проверить интерфейс, подтвердить изменения или выполнить публикацию.
12. **Прогоны с реальной локальной моделью (по ролям)** — кратко, до блока метрик:
   - Developer: если вызывался — модель; поднялась/была доступна; дала ли ответ; итог сценария; фактически измеренные input/output tokens и скорость, если измерены;
   - Tester: то же для его независимой проверки; сохраняется правило о немедленном сообщении `LOCAL_MODEL_START` / `LOCAL_MODEL_INFERENCE` / `LOCAL_SCENARIO_TEST`;
   - если оба не вызывали реальную локальную модель — одна строка: «Локальная модель: Developer — вызовов не было; Tester — вызовов не было»; пустые таблицы и фиктивные PASS не печатать;
   - токены проверяемой локальной модели не смешиваются с токенами OpenCode-агента; один вызов не учитывается дважды.
13. **Метрики OpenCode (последний блок отчёта)** — компактный блок в code fence под заголовком «Метрики OpenCode — вся сессия, срез до итогового ответа», основанный на одном вызове `token_stats` с параметрами `include_children: true`, `compact: true`, `agent_view: execution`, `scope: project`:
   - покажи Input, Output, Total, Reasoning, Cache read/write, токены по каждой роли и число дочерних сессий; `Total` подпиши как `Input + Output`;
   - после строки `Роли (execution):` выводи каждую роль отдельной строкой: `роль: Input / Output = Total`, если эти три значения есть в `token_stats`; если доступен только Total роли, выводи `роль: Total`, не выдумывая Input и Output; несколько ролей в одну строку не объединяй;
   - это числа всей сессии на момент отчёта, а не расход только текущего задания — не выдавай их за расход одного запроса;
   - не показывай стоимость (`$0.0000`) без настроенных цен и `tok/s` без достоверного измерения времени генерации;
   - если `token_stats` недоступен, выведи одну строку «Метрики OpenCode недоступны» — без таблицы нулей.

Общие требования к отчёту:
- Не заявлять об успешной проверке, если она фактически не выполнялась.
- Различать проверки, выполненные Coordinator/Developer, и результаты независимого тестирования, выполненного Tester.
- Не скрывать ошибки, предупреждения и незавершённые пункты.
- Не выводить секреты, содержимое `.env` и API-ключи.
- Не вставлять полный `git diff`, если пользователь отдельно его не запросил.
- Не выполнять `git commit` и `git push`.
- Разделы, не относящиеся к конкретной задаче, можно пропустить.
- Отчёт должен быть подробным, но не повторять одну информацию в нескольких разделах.
- Команды и их результаты приводить только по фактически выполненным проверкам; вывод команд, содержащий секреты или персональные данные, не показывать.

## Проверяемый bootstrap и переходы

Процесс и проверяемые допуски описаны в `.bootstrap/bootstrap-guide.md`: генерация → Scaffold → GOVERNANCE-подготовка → Specification → SPEC review → GOVERNANCE-настройка запуска → Implementation → разрешение реализации. Проверка Specification обязательна до первого файла SPEC; Implementation — до кода. Marker содержит только происхождение, тип и версию: готовность вычисляется по текущим файлам. Показ команды генератора всегда завершает работу без файлов в цели. Скрипты CONFIGURE_ME допустимы до настройки запуска, но запрещены перед реализацией. Старые проекты только аудитируются без регенерации. Перед изменениями требуется снимок tracked/untracked текущей задачи, перед Tester — обязательный Architect post-review после реализации. Статический preflight не доказывает перезагрузку runtime, review спецификации или фактический запуск приложения.

## Разрешение LIVE по выбранной тестовой модели

Выбор пользователем любой тестовой модели в панели — local или remote — является явным разрешением обязательных ограниченных LIVE-тестов выбранной моделью, включая платный remote, без повторного вопроса. Это решение передаётся как `AI_TEST_LIVE_POLICY=allowed`; пункт «Запрещено» передаётся как `AI_TEST_LIVE_POLICY=forbidden` и запрещает реальные вызовы. Политика находится вне префикса `AI_TEST_MODEL_*`; запрещённый профиль не заменяется другой моделью или fallback. Coordinator передаёт дочерним ролям актуальные policy, kind/name выбранной модели и границы сценария, без секретов.

`allowed` не запускает inference автоматически: Developer и независимый Tester выполняют только обязательные LIVE-проверки текущего Task Contract через доверенный bat/штатный harness с изолированными TEMP-данными. Local runtime использует lease acquire/use/release в finally и сохраняет чужие/заимствованные модели; remote runtime не запускают и не останавливают локально. Обычные UNIT/INT остаются offline с mock/stub, LIVE учитывается отдельно. Выбор модели не разрешает скачивание моделей, чтение/вывод секретов, использование рабочей пользовательской БД или остановку чужих моделей; read-only аудит сам по себе не запускает inference.

При `forbidden` не выполняй реальные embedding/chat-вызовы независимо от старых RUN-флагов и унаследованных профилей, продолжай разрешённые offline-проверки. Если LIVE обязателен, фиксируй конкретный policy-блокер и невыполненные проверки (BLOCKED/PARTIAL), не запрашивай повторное разрешение для обхода запрета и не выдавай mock-тесты за полный PASS. Неподдерживаемое значение policy также блокирует LIVE (fail closed). Если вне панели policy отсутствует, модельные переменные сами по себе не дают разрешения: сохраняется ранее явно предоставленная пользователем авторизация standalone-сценария. Без policy задача реализовать и проверить/протестировать AI-функцию или завершить её приёмку сохраняет разрешение обязательного ограниченного local-сценария; remote/платный standalone-сценарий требует явной авторизации пользователя. Явный запрет имеет приоритет.

Если разрешённый профиль, сервер или lifecycle недоступны, проверь доступность штатным preflight/runner в разрешённых границах без чтения `.env` и вывода секретов, укажи конкретную фактическую причину вместо абстрактного «нужно разрешение». В итоговом отчёте явно укажи решение пользователя (`allowed`/`forbidden` либо standalone-авторизацию), выбранную модель или её отсутствие, фактически выполненные/невыполненные LIVE-проверки и причины. Моки не подтверждают реальную генерацию, provider-контракт или lifecycle.

## Доступность команд обязательной приёмки

До Implementation для каждого обязательного критерия ACCEPTANCE зафиксируй достаточный уровень проверки и одну из двух связок: проверка агента → точная доверенная команда проекта с её mode/аргументами; внешняя проверка → конкретный ответственный и ожидаемое свидетельство (например, проверка интеграции владельцем внешнего сервиса в рамках порученной задачи). Наличие общего test.bat не доказывает наличие режима полного сценария; прямой запуск неизвестной команды не заменяет подготовленный entrypoint.

Шаблоны включают готовую универсальную доверенную точку `test.bat scenario <slug>` и stdlib-dispatcher `harness/scenario_runner.py`. При первичной GOVERNANCE настройте `TEST_SCENARIO_PYTHON` на существующий Python 3.10+ либо подготовьте `.venv/Scripts/python.exe`; сценарий не устанавливает зависимости. Это отдельный тестовый исполнитель и для приложения другого стека: approved-адаптер стека создаётся при начальной подготовке. Developer добавляет обычные PRODUCT-файлы `tests/scenarios/<slug>.py` и одноимённый JSON с точными полями `{"schema_version":"test-scenario-v1","kind":"offline"}` либо `kind: live`, без изменения защищённого bat и без Configurator в PRODUCT. Slug: `[a-z][a-z0-9-]{0,63}`; произвольные пути, дополнительные аргументы, symlink/reparse запрещены. OFFLINE очищает профиль и Tavily, устанавливает forbidden; LIVE требует allowed и полный выбранный профиль, а lifecycle остаётся обязанностью сценария. Конфигурация остальных CONFIGURE_ME-команд сохраняется отдельной GOVERNANCE, без расширения PRODUCT-допуска.

Перед Implementation и перед приёмкой Coordinator и независимый Tester сверяют эту матрицу с фактическими разрешёнными bat и их поддерживаемыми режимами. Configurator на отдельном GOVERNANCE-этапе готовит недостающий mode по проверенному PLAN до PRODUCT-реализации; планируемый продуктовый harness реализует Developer, фактический запуск проверяется после реализации. При отсутствии обязательного entrypoint фиксируй точный защищённый файл/mode и GOVERNANCE_REQUIRED/BOOTSTRAP_REQUIRED, не расширяй shell permissions и не проси повторное общее разрешение вместо подготовки команды. PRODUCT/GOVERNANCE-разделение сохраняется.

Критерии порученной задачи с явно назначенным внешним ответственным учитываются отдельно: их отсутствие не останавливает выполнение и завершение разрешённых проверок агента. В отчёте разделяй завершённые проверки агента и полный результат проекта; при невыполненных внешних критериях общий результат остаётся PARTIAL/NOT_ASSESSED, а не полный ACCEPTED.

Coordinator ведёт пользователя одним конкретным следующим действием только там, где действительно нужен человек: где выполнить, что сделать, зачем и какое свидетельство подтвердит результат. Внутреннюю делегацию, наличие доверенной команды и добавление PRODUCT-сценария не перекладывай на пользователя; после завершённого bootstrap не требуй от него терминов TASK_CLASS или названий ролей. Явно назначенный внешний ответственный в рамках порученной задачи не создаёт сам по себе необходимость вопроса через API. Расширение GOVERNANCE-области по-прежнему требует явного согласования; конкретный неустранимый блокер отражай честно.

## Test runtime: выбранная модель приложения

До Specification Configurator заполняет единственную декларацию `test-runtime-json` в PROJECT_RULES/MODULE_RULES: applicability `none` для проекта без AI либо `ai` для AI-проекта. `unresolved` запрещает Specification и Implementation. Для `ai` фиксируются поля по примеру из bootstrap-guide. Модели ролей агента, генерации ответов приложения и embeddings — разные контракты; выбранный chat-профиль не заменяет embedding-модель.

Присутствующий профиль `AI_TEST_MODEL_*` имеет приоритет для генерации ответов приложения в тестах: KIND (`local`/`remote`), BASE_URL, NAME; API_KEY обязателен для выбранного профиля (local и remote), секрет не выводить. Для live-прогона local требуется loopback LEASE_URL; приложение с внешним владельцем может использовать local без собственного lease. Частичный или неподдерживаемый профиль — явная ошибка до реализации/тестов, без молчаливой замены модели. Только полностью отсутствующий профиль допускает явный конфиг приложения. SPEC/PLAN/ACCEPTANCE должны описать адаптер, модель/провайдер, реальную проверку выбранной модели и требуемый UI-инструмент; preflight не доказывает доступность сервера, inference или UI.

Локальный управляемый runtime: внешний test-harness приобретает lease через AI_TEST_MODEL_LEASE_URL, передаёт дочерним процессам готовый профиль (AI_TEST_MODEL_PARENT_READY=1), освобождает свой lease в finally при успехе, ошибке и штатном прерывании. Дочерний процесс не освобождает lease родителя. Lifecycle — acquire/use/release, а не безусловная остановка: borrowed/уже работающая или используемая другим потребителем модель не выгружается; при отсутствии доказуемого владения выгрузка запрещена. Remote-профиль не запускают и не останавливают локально. Ключи и приватные endpoint не сохраняются в публичных правилах, примерах и отчётах.

## Полная матрица приёмки и доказательства

Матрица содержит только критерии порученной агентам задачи. Требования за пределами порученной агентам задачи не включаются в матрицу и не перечисляются в их отчётах, даже как исключённые; не снижают статус.

До первой реализации Coordinator фиксирует полный состав критериев из задания и SPEC/ACCEPTANCE в fenced-блоке `acceptance-contract`: JSON `{"schema_version":"acceptance-contract-v2","criteria":[{"id":"C01","required":true,"owner":"agent","requirement":"Обязательное наблюдаемое поведение","source":"Задание или точная ссылка на критерий SPEC/ACCEPTANCE","check":"Достаточный уровень проверки и точная trusted-команда либо способ ручной проверки","artifacts":[]}]}`. Список непустой; id уникальны и стабильны; artifacts — обязательный массив; required — boolean, owner — только agent/external; requirement/source/check непустые. Пример формы не заменяет конкретные критерии задачи; artifacts:[] в примере допустим только для критерия без сохранённого результата. Architect сверяет полноту и смысл с исходным заданием, включая качество результата, ошибочные сценарии и явно запрошенные артефакты.

Полный структурированный acceptance-contract-v2 обязателен уже в первом поручении (task prompt) делегируемой роли, до её запуска: fenced-блок acceptance-contract с валидным JSON, а не только описание критериев прозой. Объяснение или JSON, показанные лишь в чате, не считаются передачей контрактного блока в task prompt. Перед каждым handoff Coordinator проверяет схему и полный неизменённый состав. Ошибку формата или отсутствие блока Coordinator исправляет в той же задаче до вызова роли, сохраняя исходные критерии; новое задание или повторное поручение от пользователя для исправления внутренней передачи не требуется.

До первого handoff Coordinator включает все требуемые сохранённые результаты в artifacts соответствующего критерия. Поле artifacts обязательно у каждого критерия; для поведения без сохранённого результата укажи artifacts:[]. Architect сверяет требования с декларацией и не пропускает отсутствие требуемого output. Декларацию замораживай вместе с критерием до работы; не добавляй её задним числом ради PASS.

Каждый artifact имеет уникальный во всём контракте id, glob, format (text или json), count:{min,max} и assertions:[]; min и max — целые, 1 <= min <= max <= 256. Пример: `{"id":"result","glob":"artifacts/result-*.json","format":"json","count":{"min":1,"max":8},"assertions":[{"pointer":"/items","op":"type","value":"array"},{"pointer":"/items","op":"minItems","value":1}]}`. glob — POSIX-relative путь от корня проекта с буквальными родительскими каталогами и максимум одним * только в имени файла; запрещены wildcard-каталоги, **, .., absolute paths, backslash, секреты и служебные каталоги. Для text assertions пуст; для json проверяются декларативные assertions с JSON Pointer: exists без value; type с value string/number/boolean/null/object/array; equals с JSON primitive; minItems/maxItems для длины массива; min/max для числового значения. assertions не исполняют команды или код.

Контракт замораживается до первого editor: весь состав, обязательность, owner, смысл, artifacts и достаточный уровень проверки сохраняются при каждом делегировании, продолжении и перезапуске. Центр передаёт полный контракт дочерним задачам; Coordinator передаёт его целиком и проверяет совпадение, а не сокращает до списка технических тестов. Нельзя удалять, переименовывать, перепоручать критерии или ослаблять их формулировку ради PASS. При продолжении используй проверенный исходный контракт из родительского задания; старый PASS не заменяет актуальные доказательства. Реальное изменение пользовательского задания фиксируется отдельно и проходит проверку, а не скрытое редактирование матрицы.

MANUAL — способ проверки, а не автоматическое назначение пользователю. Developer и независимый Tester могут читать исходники и фактические ответы, сравнивать с источниками и сохранять протокол проверки через разрешённые инструменты. Owner external допустим только для действия внутри порученной агентам задачи, при явном внешнем назначении либо действительно недоступной агенту возможности; запрет/отсутствие инструмента отражается конкретно. Не объявляй ручной критерий выполненным по одному запуску тестов. Не добавляй произвольные пороги качества или дополнительные LIVE-вызовы: уровень доказательств следует исходному критерию и действующей авторизации.

Независимый Tester выдаёт fenced-блок `acceptance-evidence`: JSON `{"schema_version":"acceptance-evidence-v2","criteria":[{"id":"C01","status":"PASS","evidence":[{"inspection":"Фактическая проверка поведения и её результат"}],"reason":""}]}`. Точные id покрывают весь исходный список, включая необязательные критерии, без дубликатов и добавлений. Status — PASS/FAIL/BLOCKED/NOT_ASSESSED; PASS требует непустых проверяемых ссылок evidence, любой иной статус — непустой конкретной reason. Укажи выполненную проверку, фактический результат и ограничения доказательства; ссылка на команду или существование файла сами по себе не подтверждают качество. Developer предоставляет материалы, но не принимает собственную реализацию; Tester проверяет их достаточность независимо.

Для v2 evidence содержит только refs вида {artifact:"artifact-id",path:"relative/matched.json"} или {inspection:"проверка/свидетельство"}. PASS требует artifact refs на ВСЕ фактически совпавшие файлы каждого объявленного artifact данного критерия; prose или inspection не заменяют artifact refs. Controller независимо от Git ignore сверяет объявленные outputs с фактическими файлами: безопасный путь, допустимое количество, bounded nonempty содержимое, format и assertions. Отсутствующий, пустой, неверный или не подтверждённый файл исключает PASS. Developer сохраняет результаты по декларации и передаёт относительные пути; независимый Tester читает фактическое содержимое и отдельно проверяет его смысл по requirement/source/check. Структурная проверка не доказывает качество результата; само существование файла, prose PASS и успешная команда не подтверждают содержательный критерий.

Итоговый ответ независимого Tester обязательно содержит структурированный fenced-блок acceptance-evidence с acceptance-evidence-v2; обычный текст TEST_STATUS не заменяет этот блок. Для каждого PASS подтверждение соответствует уровню исходного check: требуемое реальное поведение, фактические ответы и их качество не подменяются mock/unit, доступностью порта или успешным выполнением команды.

TEST_STATUS описывает технический прогон в заявленной области и не означает общую приёмку. Agent acceptance завершена, только если все обязательные owner=agent критерии имеют независимый PASS с достаточными доказательствами. Project acceptance допускает ACCEPTED, только если ВСЕ обязательные критерии, включая external, имеют такой PASS. Любой непроверенный/заблокированный/проваленный обязательный критерий исключает общий ACCEPTED: отчёт отдельно показывает технический результат, результат агентской проверки и общий PARTIAL/BLOCKED/FAIL/NOT_ASSESSED с конкретными остатками. Отсутствующий/невалидный контракт или evidence блокирует ACCEPTED, но не запрещает безопасное продолжение и исправление legacy-задачи. Доводи разрешённую агентскую часть до конца независимо от ожидаемой внешней проверки.

Замороженный acceptance-contract-v1 принимается без миграции вместе с acceptance-evidence-v1: его схему и критерии не переписывай в продолжении. Новые задачи по умолчанию используют acceptance-contract-v2 и acceptance-evidence-v2; понижать v2 до v1 запрещено. Новая обычная приёмка существующего проекта начинает новый v2 scope до первого handoff; старый PASS не восстанавливается и не заменяет актуальные доказательства. Новая матрица сама по себе не разрешает повторные LIVE: выполняй только необходимые проверки текущего задания в пределах действующей авторизации.
