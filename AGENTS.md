# AI-Agent-Course Rules

## Безопасность
- Никогда не читать, не выводить и не изменять .env, API-ключи и другие секреты.
- Секреты хранить только в .env. В Git добавлять только .env.example без настоящих значений.
- Не обращаться к файлам вне текущего репозитория без отдельного разрешения.
- Запрет на чтение и изменение `.env` и файлов с настоящими секретами задан правилами и ограничениями read/edit. `.env.example` разрешён для чтения и изменения. При работе через shell запрет на доступ к `.env` остаётся инструкционным требованием к модели, а не технической гарантией.
- Запрет на чтение секретов относится и к попыткам получить их через shell, скрипты и субагентов. Штатная загрузка ключа самим приложением допустима при разрешённом запуске приложения, но значения секретов не должны попадать в вывод команд, отчёты или контекст агентов.

## Изменения
- Не трогать работающий код, не относящийся к текущему заданию.
- Сохранять существующее поведение, не затронутое заданием. В рамках явно запрошенного изменения допускается заменить прежний сценарий новым; отразить это в плане, тестах и отчёте. Если необходимость удаления функции не следует из задания, согласовать её с пользователем. Пользовательские данные без разрешения не удалять.
- Не удалять и не переименовывать файлы без явного разрешения.
- Делать минимальные и понятные изменения без лишнего усложнения.

## Рабочий процесс
- Перед изменениями изучить задание, структуру проекта и git status.
- Сначала написать краткий план и перечислить файлы, которые требуется изменить.
- После изменений запустить доступные проверки.
- После изменений изучить полный diff, включая staged-изменения и содержимое новых файлов. Пользователю показать краткое объяснение и статистику; полный diff — только по запросу.
- До реализации определить проверяемые критерии готовности из задания. Перед завершением сопоставить каждый критерий с фактически выполненной проверкой или явно указать, что он не проверен.
- Никогда самостоятельно не выполнять git commit и git push.
- Остановиться и дождаться подтверждения пользователя перед публикацией.

## Маршрутизация и эскалация
Общие правила, обязательные для всех агентов:
- Пользователь пишет Coordinator обычным языком и не выбирает агента сам.
- Coordinator самостоятельно редактирует только README. Он может выполнять разрешённые операции чтения и проверки для координации и приёмки результата; остальные изменения передаёт Developer.
- При делегировании передавать цель, границы задачи, критерии готовности, важные ограничения и ссылки на нужные файлы или принятые решения. Не предполагать, что субагент видит всю переписку. Не поручать нескольким агентам одновременно изменять одни и те же файлы.
- Architect вызывается только когда перед реализацией нужно принять архитектурное решение:
  - границы и ответственность модулей, слоёв или компонентов;
  - выбор с существенными компромиссами;
  - общие контракты, поток данных или состояние системы;
  - новая подсистема;
  - новый провайдер, хранилище, протокол, runtime, framework или значимая зависимость;
  - широкая миграция или рефакторинг;
  - вопросы безопасности, конкурентности, целостности данных или надёжности;
  - межкомпонентная неисправность;
  - ответ на ARCHITECT_REVIEW_REQUIRED от Developer.
- Architect НЕ вызывается только из-за размера файла, размера diff, количества файлов, нового модуля по уже принятому шаблону или выполнения утверждённого плана.
- Размер файла, количество строк, размер diff или число файлов не являются автоматическими «магическими» числовыми порогами для вызова Architect.
- Протокол Developer:
  - если текущей архитектуры достаточно — реализует и сообщает: ARCHITECTURE_STATUS: EXISTING_DESIGN_SUFFICIENT;
  - если нужен архитектурный план — ничего широко не рефакторит и возвращает: ARCHITECT_REVIEW_REQUIRED: <конкретная причина>;
  - Coordinator при ARCHITECT_REVIEW_REQUIRED вызывает Architect и передаёт его план Developer.

## Учебные проекты
- Все задания курса хранятся в этом Git-репозитории.
- Существующий проект развивать на месте; не создавать и не распаковывать новые архивные копии.
- Для запускаемого проекта сохранять run_app.bat.
- Для человеческого AI-интерфейса всегда показывать индикатор ожидания. Если выбранная модель и конфигурация поддерживают streaming, выводить ответ потоково; иначе показать итоговый ответ после завершения запроса.
- README обновлять после каждого учебного этапа.

## Код
- Не хранить API-ключи в исходном коде.
- Проверять структурированные ответы модели перед их использованием.

## Качество кода
- SOLID применять там, где соответствующий принцип действительно улучшает структуру.
- Clean Code: понятные имена, небольшие связные функции, одна ответственность, явные контракты и обработка ошибок.
- Clean Architecture применять соразмерно сложности: отделять UI, бизнес-логику, валидацию и внешних провайдеров; зависимости направлять от внешних деталей к устойчивой логике, когда в проекте уже появились соответствующие границы.
- ООП использовать только там, где состояние, жизненный цикл или инкапсуляция делают решение понятнее; не создавать классы ради самого ООП.
- Соблюдать KISS, DRY и YAGNI: устранять реальное дублирование, но не создавать преждевременные абстракции.
- Новый функционал проектировать тестируемым; при изменении поведения добавлять или обновлять релевантные тесты.
- Использовать существующие зависимости; новые добавлять только с обоснованием.
- Не превращать эти принципы в формальные требования к количеству классов, слоёв, файлов или строк; не усложнять маленькие учебные задания ради демонстрации архитектурных паттернов.

## Code language
- All comments, docstrings, TODO/FIXME notes, developer-facing error messages, and technical documentation inside source code must be written in English.
- Use clear English names for classes, functions, variables, modules, tests, and configuration keys.
- Do not add comments for obvious code. A comment must explain why a decision exists, a non-obvious constraint, or a potential risk — not repeat what the code already says.
- User-facing interface text and end-user README instructions may be written in Russian.

## Тестирование
- Автоматические проверки внешних API выполнять с фиктивным ключом и моками, без реальных сетевых вызовов.
- Тесты не должны читать настоящий `.env` и не должны зависеть от реального API-ключа. Если тестируется код с `load_dotenv()`, изолировать или замокать загрузку окружения; простого удаления переменной окружения недостаточно, поскольку `.env` может быть загружен повторно.
- Удалять временные тестовые файлы после проверки.
- Проверять наблюдаемое поведение и требования, а не только внутреннее устройство реализации. При исправлении ошибки по возможности добавить тест, воспроизводящий её. Не ослаблять и не удалять проверки только ради успешного прогона; изменение ожидаемого поведения должно следовать из задания.
- Реальные API-проверки, способные расходовать средства, выполнять только при явном разрешении пользователя. Обычные автоматические тесты всегда изолировать от сети и настоящего `.env`.

## Формат итогового отчёта
После завершения любой задачи Coordinator возвращает единый итоговый отчёт.

Отчёт должен содержать:
1. **Итог** — кратко, выполнена ли задача и какой результат получил пользователь.
2. **Что изменено** — таблицу со всеми созданными, изменёнными, удалёнными или переименованными файлами и назначением каждого изменения.
3. **Как устроено решение** — краткое объяснение архитектуры, потока данных, хранения состояния и важных технических решений. Не пересказывать весь код.
4. **Поведение для пользователя** — что появилось или изменилось в интерфейсе и как этим пользоваться.
5. **Автоматические проверки**:
   - точные команды, которые действительно запускались;
   - количество и результат тестов;
   - результаты компиляции, линтеров и других проверок;
   - отдельно указать, если какая-либо проверка не выполнялась;
   - при наличии нескольких видов проверок явно различать: unit-тесты с моками, интеграционный сценарий, реальный API-вызов, проверку интерфейса и фактический перезапуск приложения;
6. **Ручная проверка**:
   - выполненный сценарий;
   - фактический результат каждого важного шага;
   - ручную проверку не считать выполненной, если её только описали в README;
   - не называть проверку интерфейса или фактического перезапуска приложения выполненной, если был проверен только отдельный скрипт или запуск описан только в README.
7. **Ограничения и оговорки** — оставшиеся проблемы, компромиссы, неподдерживаемые сценарии и возможные риски. Если ограничений не обнаружено, написать это явно.
8. **Git-состояние**:
   - полный вывод `git status --short`;
   - `git diff --stat`, при необходимости дополненный `git diff --cached --stat` для staged-изменений;
   - отдельный список untracked-файлов, поскольку они могут не отображаться в `git diff --stat`;
   - если untracked-файлов нет, написать это явно: `untracked files: none`;
   - убедиться, что перечисленные в отчёте файлы совпадают с фактическим Git-состоянием.
9. **Запуск и проверка пользователем** — короткие точные команды или действия, необходимые для запуска и самостоятельной проверки результата.
10. **Следующее действие пользователя** — например: перезапустить приложение, проверить интерфейс, подтвердить изменения или выполнить публикацию.

Общие требования к отчёту:
- Не заявлять об успешной проверке, если она фактически не выполнялась.
- Различать проверки Coordinator и результаты, сообщённые другим агентом.
- Не скрывать ошибки, предупреждения и незавершённые пункты.
- Не выводить секреты, содержимое `.env` и API-ключи.
- Не вставлять полный `git diff`, если пользователь отдельно его не запросил.
- Не выполнять `git commit` и `git push`.
- Разделы, не относящиеся к конкретной задаче, можно пропустить.
- Отчёт должен быть подробным, но не повторять одну информацию в нескольких разделах.
- Команды и их результаты приводить только по фактически выполненным проверкам; вывод команд, содержащий секреты или персональные данные, не показывать.
