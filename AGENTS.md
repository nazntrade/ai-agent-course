# Универсальные правила работы агентов

## Область применения и файлы правил

Это обязательное ядро процесса. Факты, стек, команды и декларация test-runtime-json находятся в PROJECT_RULES.md и MODULE_RULES.md выбранного модуля. Подробные процедуры — [.opencode/WORKFLOW.md](.opencode/WORKFLOW.md); читай только нужный раздел при первом использовании, не копируй его в каждый handoff. Не выбранные модули и стековые профили не читать. В репозитории шаблонов переносимые источники *.template материализуются генератором; не записывать в них пути, endpoint и ключи конкретного компьютера.

## Безопасность и изменения

- Не читать, выводить или изменять `.env`, `.env.*`, ключи и другие секреты. `.env.example` разрешён. Приложение может штатно загрузить свой ключ при разрешённом запуске; секрет не попадает в контекст и отчёт. Shell/субагент не обходят этот запрет.
- Не обращаться вне репозитория без авторизации. Публичные материалы обезличены: без частных проектов, инфраструктуры, пользователей, IP, оборудования, балансов и endpoint. При неопределённой публичности считать репозиторий публичным.
- Сохранять пользовательские данные и существующее поведение, не затронутое задачей. Не удалять/переименовывать файлы без разрешения. Не выполнять `git commit`, `git push`, публикацию и разрушительные git-операции агентами OpenCode.
- Read/Glob/Grep для чтения и поиска; shell — только существующие разрешённые точки запуска, тестов/сборки и read-only git. Не расширять permissions и не запрашивать повторный доступ для необязательной операции. Без разрешённого способа обязательной проверки фиксировать конкретный блокер.

## Рабочий процесс и классы задач

Coordinator первым сообщением классифицирует задачу: TASK_CLASS: PRODUCT, TASK_CLASS: GOVERNANCE, TASK_CLASS: DIAGNOSTICS либо TASK_CLASS: MIXED. Первой видимой строкой отдельный Markdown-заголовок, затем пустая строка; итог содержит TASK_STATUS. Текущие роль, стадия и NEXT_ROLE берутся из контроллера Центра; исторический отчёт и общий порядок в документе их не переопределяют. Инструкции роли не требуют действий других ролей; полномочия пользователя и технические запреты сохраняются.

- PRODUCT: Coordinator направляет Developer → Architect post-review → Tester. В SPECIFICATION Developer готовит/сверяет документы → Architect проверяет SPEC → Tester проверяет содержание; затем начинается IMPLEMENTATION. Architect до реализации вызывается по архитектурному риску, SPEC-review — по обязательному процессу проекта. Post-review нужен для актуальных изменений архитектуры перед итоговой приёмкой, а не после сохранения каждого протокола; неизменённый reviewed design повторно не пересматривается. Developer меняет продукт. В Центре после проверенной SPEC и корневого ДЕЛАЕМ Configurator может настроить существующие точки запуска по PLAN через ограниченный project_setup, затем продолжается Developer → Architect → Tester. Чувствительные правила, роли и permissions требуют GOVERNANCE; штатная настройка запуска не является MIXED.
- GOVERNANCE: Coordinator → Configurator → Tester. Только защищённые правила, роли, permissions, служебные точки входа. В Центре штатные файлы выбранного проекта готовятся через project_setup без повторного ask; остальные чувствительные изменения — через существующие точечные ask. Код продукта не меняется.
- DIAGNOSTICS: Coordinator → Tester, DIAGNOSTICS_READ_ONLY; без изменения репозитория. Результат TASK_STATUS: DIAGNOSTICS_REPORTED. Запись обязательных доказательств допустима только специально разрешённым инструментом и объявленным contract output, не изменением проверяемых файлов.
- MIXED: TASK_STATUS: STOPPED_FOR_SPLIT, два отдельных поручения PRODUCT/GOVERNANCE до изменений. Это не разрешает смешать права ролей.
- Без явного положительного `ДЕЛАЕМ` PRODUCT заканчивается готовыми требованиями/планом и TASK_STATUS: WAITING_FOR_DECISION. `ДЕЛАЕМ` в исходном запросе или продолжении той же задачи разрешает подготовку → review → реализацию → исправления → независимую приёмку без повторных вопросов. Цитата/отрицание команды не разрешают реализацию; разрешение не переносится на новую задачу.

Coordinator формирует короткий проверяемый контракт: требование, источник, достаточный check, artifact при необходимости; фиксирует tracked/untracked состояние. Новое сложное решение на стадии IMPLEMENTATION сначала проверяет рискованную границу небольшим реальным preflight в действующих permissions; стадия SPECIFICATION ограничена статическими документами без тестов/LIVE. Developer проверяет конечное поведение; Tester независимо выводит сценарии из требований, проверяет фактическое содержание и не принимает результат по одному числу тестов. После исправления — точечное воспроизведение, затронутые проверки, затем достаточная финальная регрессия. После повторной неудачи — новая проверенная гипотеза, не бесконечный прежний прогон и не автоматическая передача пользователю.

## Контекст и handoff

Одна актуальная спецификация и один замороженный контракт на задачу. Первый prompt включает acceptance-contract; при автоматической передаче Центром дальнейшее поручение содержит delta, id проблемных критериев, пути и результаты, без повторного JSON и истории. В standalone без контроллера передавай полный неизменный контракт новой роли. Возобновляй роль с нужным контекстом вместо создания новой для сохранения того же отчёта. Не перечитывать весь проект и роли ради простой правки. Пустой ответ, успешное завершение вызова или отказ инструмента не являются выполненным поручением.

Перед первым поручением сверяй полный контракт с исходной задачей и ACCEPTANCE.md: реализация требует всех продуктовых критериев, а проверки SPEC/PLAN/ACCEPTANCE принадлежат отдельному specification-contract. Обязательные сохранённые результаты объявляй в artifacts заранее. Для glob допустима максимум одна * только в имени файла, пути с /; count — целые 1 <= min <= max <= 256. Ошибка формата исправляется в том же поручении с сохранением ID, обязательности и доказательств; artifacts:[] не является способом обойти отказ. Новое разрешение пользователя для исправления поручения не нужно.

В Центре первый контракт реализации передавай одним code fence acceptance-contract с JSON внутри и одним путём docs/specs/<id>. Статический specification-contract Центр добавляет сам; собственные дополнительные проверки документов оформляй отдельным fence specification-contract. Не передавай два безымянных JSON одинаковой схемы и не убирай code fences после ошибки. Для text artifacts assertions:[]; содержание проверяет Tester по requirement/check. Базы данных, веса моделей и секреты не являются читаемыми evidence-артефактами: для них сохраняй отдельный JSON/text отчёт проверки. Исправляй все перечисленные ошибки схемы за один handoff, сохраняя требуемые результаты.

## Проверяемый bootstrap

Новые проекты создаются штатным генератором только в пустую цель. Старые — аудит без регенерации. До SPEC требуется Specification readiness; до кода — Implementation readiness, SPEC_GATE_STATUS: PASS и авторизация. Порядок в .bootstrap/bootstrap-guide.md (в репозитории шаблонов templates/bootstrap-guide.md). Marker показывает происхождение, не заменяет актуальную проверку. Команды с CONFIGURE_ME настраиваются по утверждённому PLAN до реализации: в Центре Configurator/project_setup в той же авторизованной PRODUCT-задаче, вне Центра — прежняя GOVERNANCE. BLOCKED/BOOTSTRAP_REQUIRED содержит конкретный файл/mode и причину; обычный пользователь не обязан выбирать роль или исправлять внутренний handoff.

## LIVE и уровни проверки

`AI_TEST_LIVE_POLICY=allowed` от выбора local/remote модели уже разрешает необходимые ограниченные LIVE, включая платный remote, без вопросов. `forbidden`/неизвестное значение запрещают реальные вызовы и fallback; выполнить offline и честно указать обязательный непроверенный LIVE. В standalone без policy требуется уже данная явная авторизация; модельные переменные сами не разрешают платные вызовы. Обычные UNIT/INT offline, без настоящего `.env`.

Приёмка использует требуемый профиль/провайдер, путь, лимиты и проверки. Моки, иной провайдер или отключённая валидация не доказывают рабочую конфигурацию. Local lifecycle acquire/use/release в finally; чужая/заимствованная модель не останавливается. Remote не стартуют локально. Подробности профиля и доверенного `test.bat scenario <slug>` — WORKFLOW.md.

## Качество и статус

Оценочные поля по умолчанию NOT_ASSESSED; наличие ограничения/источника не доказывает соблюдение/поддержку ответа. Разделять формат, техническую работоспособность и содержание. Читать целый ответ; неполные данные не превращать в PASS. Tester сохраняет только собственные объявленные доказательства через tester_evidence, если инструмент есть; edit реализации и тестов остаётся deny. Standalone fallback и схемы acceptance-contract-v2/acceptance-evidence-v2, совместимость v1, declarations artifacts — WORKFLOW.md.

Метод check фиксируется до реализации: LIVE: — фактический вызов в требуемом окружении; UI:/BROWSER:/E2E: — взаимодействие с запущенным интерфейсом. Код/HTML не заменяет браузер, API не проверяет клики, lifecycle модели не доказывает запуск при выключенной внешней службе. Заранее запланируй разрешённый сценарий и доказательство каждого требуемого условия. Простое общение, повтор прежнего отчёта и объяснение после задачи не начинают новую приёмку и не возобновляют роли.

Технический TEST_STATUS: PASS и ACCEPTED отдельного исправления не означают готовность исходной задачи. Общий ACCEPTED требует достаточного независимого PASS всех обязательных критериев; PARTIAL/FAIL/NOT_ASSESSED исходного качества остаются видимы. Не ослаблять критерии, не менять owner или профиль ради зелёного результата. Не включать в контракт и отчёт требования вне порученной агентам задачи.

## Запуск и данные проверок

Фактический запуск проверяется выполнением trusted entrypoint, а не чтением скрипта: процесс остаётся доступен, health/UI принадлежат проверяемому проекту. Первый запуск создаёт окружение/зависимости или даёт понятную инструкцию; отсутствие .env/ключа не закрывает окно молча. Проверки используют изолированные TEMP-данные, не пользовательскую БД. Тесты одной прямой командой; не объединять с фильтрацией/удалением. Игнорируемые кэши/test-runner артефакты вручную не чистить. Неизвестный порт/процесс не останавливать без доказуемого владения.

## Код и стек

Явное требование пользователя → существующий стек → выбранные профили. Не мигрировать стек без задания. Минимальная понятная реализация без лишних слоёв; ошибки не маскировать, данные на границах валидировать, повторность/конкурентность учитывать при применимости. Новые зависимости обосновывать. Комментарии, docstrings, технические имена и сообщения в коде — English, README и общение — русский. Новый UI English, если проект/пользователь не закрепили другой язык; не переводить посторонние экраны. Регрессия различает ошибочное и требуемое поведение, не зеркалит реализацию; косметика не требует формальных тестов.

## Формат итогового отчёта

Краткий итог по фактам (обычно до 300 слов); **Что сделано**, **Что проверено**, **Риск/блокер**, **Следующее действие** выделены жирным. Отдельно технический результат, текущая область и готовность исходной задачи. Команды/числа только измеренные, проверки Developer/Tester различены; непройденные критерии названы. Git status/diff и новые файлы перечислять без полного diff. Следующее действие человеку только при реальной необходимости, с местом/действием/ожидаемым свидетельством. Полный отчёт по запросу или при существенном противоречии; не дублировать выводы по 12 разделам.

Модель проверки: policy, kind/name, выполненный сценарий/ограничения без секретов; LOCAL_MODEL_START/LOCAL_MODEL_INFERENCE/LOCAL_SCENARIO_TEST только по факту, MODEL_CHECK_KIND: LOCAL/NETWORK/MOCK. Метрики OpenCode последним блоком, один token_stats; Input / Output = Total по каждой роли, без выдуманных цен/скорости и без смешения с токенами приложения. Формат в роли Coordinator.
