# Каталог технологических стеков (Stack Profiles)

Переносимый каталог рекомендуемых технологических стеков. Он не привязан к конкретному репозиторию и переносится вместе с `AGENTS.md` без изменений.
Конкретный репозиторий выбирает нужные профили в `PROJECT_RULES.md`; неперечисленные в нём профили не читаются и не применяются.
Приоритет выбора технологий задан в `AGENTS.md`: явное требование пользователя → стек существующего проекта → выбранные в `PROJECT_RULES.md` профили → defaults этого каталога.

## Общие правила каталога
- Конкретные версии библиотек и инструментов фиксируются внутри проекта (lock-файлы, зависимости, конфигурация сборки), а не навечно в этом каталоге. Каталог описывает состав стека, а не версии.
- Обновление версий — решение конкретного проекта; оно не меняет этот каталог и не требует миграции других проектов.
- Профиль описывает рекомендуемый состав. Допустимые исключения перечислены в каждом профиле; любое другое отклонение требует явного согласования с пользователем.
- Существующий рабочий проект не мигрируется на профиль из каталога: профиль применяется к новым проектам или по явному заданию.

## Общий API-контракт
- Единый контракт HTTP API — OpenAPI 3.1.
- Клиенты и типы для потребителей генерируются из спецификации, а не пишутся вручную.
- Спецификация хранится в репозитории проекта и является источником истины для серверной и клиентской частей.
- Для сервисов без внешнего HTTP API обязательность OpenAPI не применяется.

## Web
- **Назначение:** браузерные SPA и веб-интерфейсы, в том числе дашборды и админки.
- **Основной стек:** TypeScript + React + Vite + TanStack Query + Tailwind + shadcn/ui. Zustand — только при необходимости глобального клиентского состояния.
- **Контракты:** типизированный API-клиент, сгенерированный из OpenAPI 3.1; серверное состояние через TanStack Query; локальное состояние через props/context.
- **Хранение данных:** источник истины — серверное API; в браузере допускаются только кэш TanStack Query и минимальное UI-состояние; локальное хранилище — лишь для несекретных настроек.
- **Тесты:** Vitest для модульных и компонентных проверок, Playwright для end-to-end сценариев.
- **Build gates:** проверка типов (tsc), линтер, Vitest, сборка (vite build); Playwright при наличии e2e-сценариев.
- **Допустимые исключения:** Zustand вместо локального состояния при действительно сложном клиентском состоянии; отказ от shadcn/ui при наличии собственной дизайн-системы.

## Backend Standard
- **Назначение:** серверные HTTP API и сервисы общего назначения вне AI-нагрузки.
- **Основной стек:** TypeScript + Hono; Fastify — для крупных сервисов; PostgreSQL + Drizzle.
- **Контракты:** OpenAPI 3.1 как источник истины; валидация входных данных схемами; единый формат ответов об ошибках.
- **Хранение данных:** PostgreSQL; доступ через Drizzle; миграции версионируются в репозитории.
- **Тесты:** модульные тесты и интеграционные проверки на тестовой базе.
- **Build gates:** проверка типов, линтер, применение миграций, тесты, сборка.
- **Допустимые исключения:** Fastify при росте сервиса и разделении ответственности; замена СУБД только по явному требованию.

## Backend AI
- **Назначение:** серверные сервисы с LLM/AI-логикой, обращениями к внешним провайдерам и хранением истории.
- **Основной стек:** Python + FastAPI + Pydantic + SQLAlchemy/Alembic + PostgreSQL; Pytest.
- **Контракты:** OpenAPI 3.1 из FastAPI; Pydantic-схемы для запросов, ответов и разбора ответов внешних провайдеров; адаптеры провайдеров изолированы от бизнес-логики.
- **Хранение данных:** PostgreSQL через SQLAlchemy, миграции Alembic; секреты только в окружении, не в коде и не в репозитории.
- **Тесты:** Pytest; внешние провайдеры мокаются; отдельно моделируются граничные ответы (обрыв по `finish_reason`/лимиту, отсутствие или частичный `usage`, ошибка провайдера, streaming).
- **Build gates:** проверка типов и линтер (по конфигурации проекта), применение миграций, Pytest, запуск сервиса.
- **Допустимые исключения:** другой веб-фреймворк или ORM только по явному требованию; SQLite допустим для локальных проверок, но не как продакшен-хранилище.

## Windows Desktop
- **Назначение:** десктопные приложения для Windows.
- **Основной стек:** Electron + React + TypeScript; C#/.NET/WPF — для строго native Windows; Tauri — только по явному требованию.
- **Контракты:** типизированный IPC между UI и нативной частью; версионирование внутренних интерфейсов и формата данных приложения.
- **Хранение данных:** локальные файлы или встроенная БД приложения; секреты — в защищённом хранилище ОС, не в репозитории.
- **Тесты:** модульные тесты логики, проверки IPC и ключевых UI-сценариев.
- **Build gates:** проверка типов, тесты, сборка и упаковка дистрибутива, фактический запуск приложения.
- **Допустимые исключения:** C#/.NET/WPF, если приложение обязано быть строго native для Windows; Tauri применяется только по явному требованию пользователя.

## macOS Native
- **Назначение:** нативные приложения для macOS.
- **Основной стек:** Swift + SwiftUI.
- **Контракты:** системные API Apple; асинхронные операции через async/await; изоляция сетевого слоя от UI.
- **Хранение данных:** SwiftData или Core Data для прикладных данных; Keychain для секретов.
- **Тесты:** XCTest для модульных и интеграционных проверок.
- **Build gates:** сборка в Xcode, тесты, фактический запуск приложения.
- **Допустимые исключения:** AppKit для возможностей, отсутствующих в SwiftUI.

## iOS Native
- **Назначение:** нативные приложения для iOS.
- **Основной стек:** Swift + SwiftUI + async/await + URLSession.
- **Контракты:** системные API Apple; сетевой слой на URLSession; изоляция моделей и состояния от представлений.
- **Хранение данных:** SwiftData или Core Data для прикладных данных; Keychain для секретов.
- **Тесты:** XCTest для модульных проверок, XCUITest для UI-сценариев.
- **Build gates:** сборка в Xcode, XCTest/XCUITest, фактический запуск приложения.
- **Допустимые исключения:** UIKit для возможностей, отсутствующих в SwiftUI.

## Cross-platform Mobile
- **Назначение:** общий UI для Android и iOS без тяжёлой native-интеграции.
- **Основной стек:** React Native + Expo — только при необходимости общего Android/iOS UI.
- **Контракты:** типизированные модели и API-клиент; нативные модули подключаются точечно.
- **Хранение данных:** локальное хранилище устройства для несекретных данных; секреты — в защищённом хранилище ОС.
- **Тесты:** модульные тесты логики и компонентов, UI-проверки на устройстве или эмуляторе.
- **Build gates:** проверка типов, линтер, тесты, сборка для Android и iOS.
- **Допустимые исключения:** профиль не применяется, если требуется тяжёлая native-интеграция — тогда используются `Android Native` и `iOS Native`.

## Android Native
- **Назначение:** нативные приложения для Android.
- **Основной стек:** Kotlin + Jetpack Compose + Coroutines/Flow + ViewModel + Hilt + Room + Retrofit/OkHttp.
- **Контракты:** модели и API-клиент на Retrofit/OkHttp; состояние UI через ViewModel и Flow; зависимости через Hilt.
- **Хранение данных:** Room для локальных данных; секреты — в защищённом хранилище ОС.
- **Тесты:** JUnit для модульных проверок, Compose UI tests для интерфейсных сценариев.
- **Build gates:** сборка Gradle, JUnit, Compose UI tests, фактический запуск приложения.
- **Допустимые исключения:** отказ от Compose в пользу XML-разметки только по явному требованию.

## Educational Prototype
- **Назначение:** учебные и демонстрационные прототипы с минимальной инфраструктурой.
- **Основной стек:** Python + Streamlit + SQLite.
- **Контракты:** простые функции и модули; обязательный OpenAPI не требуется, если нет внешнего HTTP API; внешние ответы проверяются перед использованием.
- **Хранение данных:** SQLite локально, без выделенного сервера БД.
- **Тесты:** Pytest для модульных и функциональных проверок.
- **Build gates:** запуск приложения и прохождение тестов.
- **Допустимые исключения:** отсутствие слоёв, DI и строгой Clean Architecture, пока сложность проекта этого не требует.
