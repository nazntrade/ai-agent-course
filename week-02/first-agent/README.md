# Неделя 2 — День 10. Управление контекстом: стратегии

Streamlit-приложение «Первый агент» продолжает развиваться. Контекст по-прежнему хранится в **SQLite** и переживает перезапуск, а для каждого обращения сохраняется и показывается подробная статистика токенов и стоимости (День 8). На Дне 9 появилось сжатие истории в **накопительную сводку**; теперь у каждого чата есть одна настройка **стратегии контекста** с пятью режимами:

| Стратегия | Что уходит в запрос |
|---|---|
| **Полная история** (`full`) | вся история активной линии без сжатия |
| **Сводка** (`summary`) | сводка Дня 9 вместо покрытых ею старых ходов |
| **Скользящее окно** (`sliding`) | только последние `N` сообщений плюс текущий запрос |
| **Sticky Facts** (`sticky_facts`) | активные факты (key-value) плюс последние `N` сообщений |
| **Ветвление** (`branching`) | история активной ветки без сжатия |

Полная переписка всегда остаётся в SQLite и отображается: сокращение влияет **только** на payload очередного запроса. Данные «неактивных» стратегий не удаляются — сводка, факты и ветки хранятся независимо и снова используются при возврате к стратегии.

День 10 ничего не удаляет из поведения Дней 6–9: несколько независимых чатов, создание/удаление, восстановление последнего выбранного чата, индивидуальные настройки, пустое стартовое состояние, потоковый и непотоковый режимы, индикатор ожидания, демо-лимит контекста и откат при ошибке сохранены.

## Что умеет приложение

- показывать в сайдбаре список сохранённых чатов (новые — сверху) и компактный накопительный расход по каждому чату;
- создавать, выбирать, переименовывать и удалять чат прямо в сайдбаре: имя задаётся вручную через иконку ✏️ (inline-поле, без вызова API и без изменения `updated_at`, поэтому порядок чатов не «подпрыгивает»), удаление — через иконку 🗑️ и только после явного подтверждения;
- восстанавливать последний выбранный чат и всю его историю со статистикой из SQLite;
- хранить для каждого чата собственные настройки: system prompt, модель, temperature, max tokens, потоковый вывод, демо-лимит контекста, **стратегию контекста** и её окна;
- рядом с полем модели показывать её полное название (`DeepSeek V4.1 Flash`) через безопасное сопоставление ID → имя, не подменяя технический ID и не отправляя название в API;
- показывать у каждого сообщения пользователя оценочное число токенов именно этого сообщения;
- показывать у ответа ассистента токены ответа и компактную строку завершённого обращения: контекст, всего, cache hit/miss, оценочная стоимость, `finish_reason`;
- **выбирать стратегию контекста** и показывать панель, соответствующую активной стратегии:
  - «Сжатие истории» для сводки: текст сводки, её покрытие, расход и сравнение размера контекста до/после;
  - «Sticky Facts» для памяти фактов: окно, граница покрытия, таблицы активных и отменённых/заменённых фактов, расход успешных и оборванных вызовов;
  - «Ветки» для ветвления: дерево линий с родителем по имени и checkpoint, переключение, создание ветки из завершённого хода и удаление отдельной ветки с подтверждением;
- показывать подробную статистику текущего чата и таблицу всех его ходов в раскрывающихся блоках;
- показывать сравнение диалогов (стратегия, последний контекст, стоимость ходов, сжатия и фактов, итог);
- безопасно демонстрировать переполнение контекста через демо-лимит по фактическому payload выбранной стратегии, не отправляя запрос в API.

## Стратегии контекста

Стратегия — это **одна настройка на уровень чата**. Она влияет только на то, какой payload уйдёт в модель; хранение и отображение полной переписки не меняются. Выбранная стратегия сохраняется в базе и восстанавливается между запусками.

### Полная история (`full`)

В запрос уходит вся история активной линии. Никаких вспомогательных вызовов нет.

### Сводка (`summary`, по умолчанию)

Поведение Дня 9: последние `N` ходов («Последних ходов без сжатия») всегда уходят полностью, более старая часть заменяется накопительной сводкой. Сводка обновляется порциями и хранится в БД. См. раздел «Управление контекстом: как работает сжатие».

### Скользящее окно (`sliding`)

В запрос уходит **system prompt** и последние `W − 1` сообщений истории плюс текущий запрос (`W` — «Размер скользящего окна, сообщения», по умолчанию 6). System prompt в окно не входит. При `W = 1` отправляется только текущий запрос. Никаких сводок и фактов при этом не вызывается.

### Sticky Facts (`sticky_facts`)

В запрос уходит system prompt, блок **активных фактов** (если они есть) и последние `W − 1` сообщений плюс текущий запрос. После каждого пользовательского хода отдельным **непотоковым** вызовом модель извлекает факты из сообщений, ещё не покрытых якорем. Она возвращает строго JSON `{"facts": [...]}`.

- Каждый факт — это `key` (краткое имя) и `value` (значение), а также `category` (`goal`, `constraint`, `preference`, `decision`, `agreement`, `parameter`, `other`) и `status`.
- **Добавление/уточнение**: если факта с таким ключом ещё нет — он добавляется; если значение изменилось, старая запись помечается `replaced` (причина «заменено новым значением»), а новая становится активной. Повтор того же значения — no-op.
- **Отмена**: `status = cancelled` помечает активный факт отменённым; если активного нет — no-op.
- **Якорь покрытия** (`facts_anchor_message_id`) — id последнего сообщения, из которого уже извлекли факты. Он двигается только вперёд, поэтому одна и та же порция не обрабатывается дважды, а при ошибке повторяется целиком, без дублей.
- Платный вспомогательный вызов делается **только во время пользовательского хода** и никогда при открытии чата, rerun, смене настройки или ветки.
- Разбор: снимается единичный markdown-fence, `json.loads`, проверяются структура и поля. Пустой список `[]` — валидный no-op: якорь двигается, факты не меняются.
- Обрыв (`finish_reason = length`/`max_tokens`) вызывает одну повторную попытку с увеличенным бюджетом; если обе оборваны, факты и якорь не меняются, выводится предупреждение.
- Расход **всех** выполненных попыток учитывается в статистике раздельно: успешные (включая валидный пустой список) — в бакет `facts_ok_*`, оборванные/невалидные/ошибочные — в `facts_fail_*`.

### Ветвление (`branching`)

Чат можно разветвить от **завершённого хода** (checkpoint — assistant-сообщение с записью в `turns`). Ветка хранит ссылку на родительскую ветку и на checkpoint, а новые сообщения помечаются `branch_id`. Пустое значение `branch_id` — основная линия.

- В запрос уходит история **активной линии**: общий префикс до checkpoint берётся ровно один раз, затем сообщения активной ветки. Соседние ветки друг в друга не попадают.
- Ветки могут быть вложенными (ветка от ветки).
- Панель «Ветки» показывает дерево линий с отступами и маркером активной линии; у каждой ветки видны **имя родителя** (основная линия или имя ветки) и checkpoint (завершённый ход), а не только технический ID.
- Ветка создаётся из формы, где родительская линия выбирается явно среди основной линии и всех веток (по умолчанию — активная), а список checkpoint'ов соответствует именно выбранной линии. До нажатия «Создать ветку» показан предпросмотр «от какой линии и какого хода». Так соседняя ветка не создаётся случайно дочерней.
- Пустое имя и имя, совпадающее с уже существующим (без учёта регистра и лишних пробелов), отклоняются с понятным сообщением — ветка не создаётся. После успешного создания поле имени очищается, а активной становится новая ветка.
- Любую ветку можно удалить с подтверждением: удаляются только её собственные сообщения, ходы и сводка, а общий префикс, основная линия и соседние ветки не меняются. Если удаляется активная ветка, активной становится её родительская линия. Ветку с дочерними удалить нельзя, пока не удалены дети: каскадного удаления нет, интерфейс перечисляет мешающие ветки.
- Активная ветка сохраняется в базе и восстанавливается после перезапуска; удалённая ветка не возвращается.
- Сводка привязана к линии (`summaries.branch_id`), поэтому память ветки и основной линии не смешиваются. Ветвление само по себе не запускает ни сжатие, ни извлечение фактов.

## Управление контекстом: как работает сжатие

### Настройки чата

- **«Стратегия контекста»** — выпадающий список с пятью режимами; по умолчанию **«Сводка»**. Настройка сохраняется в базе и восстанавливается между запусками. Роль прежнего чекбокса «Сжимать историю автоматически» выполняет сама стратегия: сжатие работает только в режиме «Сводка».
- В зависимости от стратегии показываются свои поля:
  - «Сводка» — **«Последних ходов без сжатия»** (по умолчанию **3**);
  - «Скользящее окно» — **«Размер скользящего окна, сообщения»** (по умолчанию **6**);
  - «Sticky Facts» — **«Размер окна Sticky Facts, сообщения»** (по умолчанию **6**);
  - «Полная история» и «Ветвление» — без дополнительных полей.

Это не ограничение хранения. Полная переписка остаётся в SQLite и целиком отображается в чате; настройка влияет только на то, что уходит в запрос к модели.

### Условие автоматического сжатия (только стратегия «Сводка»)

После каждого успешно сохранённого хода, если сжатие включено, приложение считает, сколько ходов ещё **не покрыто** сводкой.

- **Первая сводка** создаётся, как только за окном «последних ходов без сжатия» появляется хотя бы один старый ход.
- **Дальнейшие обновления идут порциями**: сводка пересобирается не после каждого ответа, а когда накапливается ещё **3 хода** (внутренний интервал `COMPRESSION_BATCH_TURNS`). Когда порция накопилась, в сводку сворачивается сразу весь лишний хвост — так сводка не пересоздаётся ради одного устаревшего хода.
- Поэтому между сжатиями в запрос может уходить немного больше `N` ходов, чем указано в настройке, но **последние N ходов всегда передаются полностью**, а полная переписка неизменно хранится в базе.

Почему выбран счёт по ходам, а не порог по токенам: он детерминирован, объясняется в одно предложение и воспроизводим в видео; токен-триггер давал бы нерегулярные платные вызовы. При значениях по умолчанию (`N = 3`, порция 3) первая сводка появляется после четвёртого хода, следующая — после седьмого.

### Сжатие перед запросом при превышении лимита

Обычно сжатие происходит после ответа. Но если чат уже длинный, а сводки ещё нет и следующий запрос не помещается в **демо-лимит контекста**, ждать ответа бесполезно: запрос не уйдёт. В этом случае **только стратегия «Сводка»** сначала сворачивает старую часть истории в сводку и только потом отправляет основной запрос. Все остальные стратегии при превышении демо-лимита сразу показывают `ContextLimitError`, не делая ни одного вызова API и не меняя БД.

### Накопительная сводка

- **Якорь покрытия** — количество первых сообщений чата, которые заменены сводкой. Слияние всегда начинается ровно от якоря и идёт непрерывно, поэтому каждое сообщение попадает в сводку ровно один раз — без пропусков и без дублирования контекста.
- Предыдущая сводка передаётся модели вместе с новыми сообщениями, поэтому накопление непрерывное: более поздние факты и исправления учитываются, а устаревшие могут быть заменены.
- Актуальная сводка сохраняется в БД. После перезапуска она **загружается**, а не создаётся заново.
- Открытие чата и изменение настроек **не запускают платную суммаризацию**: вызов модели происходит только при отправке нового сообщения.
- При **выключении сжатия** снова используется полная история. Сводка при этом не удаляется: она сохраняется и снова используется после включения сжатия (досжимается только новый непокрытый хвост).

### Что сохраняет сводка

Промпт суммаризации требует сохранять важные факты, ограничения и предпочтения пользователя, принятые решения, а также ошибки и их исправления. Если более позднее утверждение отменяет более раннее, в сводке остаётся актуальное. Качество сводки зависит от модели, поэтому сценарий для видео проверяет ранние факты и исправления явно.

### Ошибки и целостность

Если вызов суммаризации или запись сводки не удались, это **не ломает ход**: пара сообщений уже сохранена, показывается понятное предупреждение, а сводка и её якорь остаются прежними. Сжатие автоматически повторится, когда накопится следующая порция старых ходов, — с тех же непокрытых сообщений, без потери переписки и без дублей.

Отдельно проверяется **оборванная сводка**: если ответ суммаризатора завершился по лимиту длины (`finish_reason = length`), он не сохраняется как полноценная сводка — прежняя сводка и её граница остаются неизменными.

У reasoning-моделей (например, `deepseek-flash`) часть бюджета вывода уходит на скрытые reasoning-токены, поэтому «пустой» по видимому тексту обрыв возможен даже при короткой сводке. Чтобы это не блокировало обновления навсегда, сводка сначала запрашивается с базовым бюджетом (`SUMMARY_MAX_TOKENS`), а при обрыве делается **одна** повторная попытка с увеличенным бюджетом (`SUMMARY_RETRY_MAX_TOKENS`). Только если и повторная попытка оборвана, сводка считается неуспешной: показывается предупреждение, прежняя сводка и её граница сохраняются.

При этом провайдер тарифицирует каждую фактически выполненную попытку. Поэтому расход **всех** попыток — и оборванных, и успешных — попадает в накопительные счётчики сжатия (`summary_*`), даже если сводка не обновилась. В интерфейсе это показано раздельно: «всего на попытки сжатия» против «последнее успешное обновление сводки». Если API не вернул `usage`, поля остаются «нет данных» и нулём не подменяются.

## Токены: что чем измеряется

Важно не смешивать несколько разных величин.

| Показатель | Что это | Источник |
|---|---|---|
| Токены сообщения | Размер только последнего сообщения пользователя | локальная оценка, помечается `≈` |
| Контекст запроса | Всё, что фактически ушло модели: system prompt + сводка + непокрытая история + новое сообщение | точное `prompt_tokens` из `usage` API |
| Токены ответа | Сколько модель сгенерировала | точное `completion_tokens` из `usage` API |
| Токены обращения | Сумма входа и выхода за один ход | точное `total_tokens` из `usage` API |
| Токены создания сводки | Вход, выход и cache всех фактически выполненных попыток суммаризации, включая оборванные | точные значения из `usage` API (сумма по попыткам) |
| Накопительный расход чата | Сумма входных и выходных токенов по всем ходам **плюс** вызовы сжатия | сумма точных значений API |
| Уникальная история | Примерный размер сохранённых сообщений в базе | локальная оценка, помечается `≈` |
| Контекст до/после сжатия | Насколько меньше стало бы уходить в запрос | локальная оценка, помечается `≈` |
| Стоимость | Оценочная стоимость ходов и сжатия по отдельности и итого | расчёт по точным токенам и тарифу |

### История отправляется повторно

Каждый запрос отправляет модели контекст заново, а не только новое сообщение. Без сжатия это вся история, поэтому накопительный расход API растёт значительно быстрее, чем размер уникальной истории в базе. Со сжатием в запрос уходит сводка вместо старых ходов, поэтому контекст запроса стабилизируется, а не растёт бесконечно. Именно это сравнение видно в блоках «Сжатие истории» и «Сравнение диалогов».

### Уменьшение контекста не равно экономии денег

Сжатие уменьшает контекст **каждого** запроса, но само создание сводки — это отдельный платный вызов модели. Поэтому расход на сжатие учитывается отдельно (`summary_*`) и входит в итоговый расход чата. Экономия денег не равна разнице размеров контекста, и интерфейс говорит об этом прямо.

### Точные и оценочные значения

- Значения из `usage`, которые вернул провайдер, считаются **точными** и выводятся без пометки.
- Локально рассчитанные значения помечаются знаком `≈` и подписываются как оценка. Оценка никогда не выдаётся за официальный результат API и не используется для расчёта денег.
- Если провайдер не вернул поле, показывается «нет данных». Ничего не выдумывается.

Локальная оценка токенов (`tokens.py`) — детерминированная эвристика без внешних зависимостей: кириллица считается «дороже» латиницы. Она достаточно точна по порядку величины для учебного сравнения, но это не токенизатор.

### Cache hit / cache miss

Провайдер может вернуть `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens` — сколько входных токенов взято из кэша и сколько обработано заново. Кэшированный ввод тарифицируется заметно дешевле. Если разбивка есть, стоимость считается по двум разным ставкам; если её нет — весь вход консервативно оценивается по ставке cache miss, и это явно указано в поле «допущение».

## Стоимость

Стоимость всегда **оценочная** (`≈`). Тарифы хранятся централизованно в `pricing.py`, а не в интерфейсе или бизнес-логике. Расчёт идёт только от точных токенов API: если точных значений нет, стоимость не показывается. Стоимость ходов и стоимость сжатия считаются одним и тем же тарифом, но хранятся и показываются раздельно, а в итоге суммируются.

- Источник официальных тарифов: <https://api-docs.deepseek.com/quick_start/pricing>, проверено **2026-09-10**.
- Канонический технический ID модели — `deepseek-flash`; отображаемое название — **DeepSeek V4.1 Flash**. В API всегда уходит технический ID, а не отображаемое название.
- Легаси-имя `deepseek-v4-flash` обслуживается той же моделью DeepSeek-V4.1-Flash и тарифицируется по цене Flash. Оно распознаётся только для совместимости со старыми данными; новые настройки и запросы используют канонический `deepseek-flash`.
- Есть peak- и off-peak-окна: 01:00–04:00 и 06:00–10:00 UTC по будням (peak), остальное время — off-peak.
- Если для введённой модели тариф неизвестен, показывается «тариф неизвестен»; цена не придумывается.

## Лимит ответа и переполнение контекста — это разные вещи

- **`max_tokens`** ограничивает только длину генерируемого ответа. Если модель остановилась из-за этого, приходит `finish_reason="length"`, а интерфейс поясняет: достигнут лимит длины ответа, а не лимит всего контекста.
- **Переполнение контекстного окна** означает, что входной контекст вместе с запрошенным ответом не помещается в лимит модели. Запрос в этом случае отклоняется, и это настоящая ошибка, а не штатное завершение.

### Безопасный демо-лимит

Чтобы демонстрировать переполнение, не тратя реальные токены, у каждого чата есть настройка **«Демо-лимит контекста, токены»** (`0` = выключен). Перед запросом приложение локально оценивает вход **того самого payload, который будет отправлен выбранной стратегией** (полная история, сводка, скользящее окно, факты или линия ветки) и складывает его с `max_tokens`:

- если сумма превышает демо-лимит — показывается понятное предупреждение, а запрос в API **не отправляется**; история и база не меняются, сообщения не удаляются;
- автоматическое сжатие с последующим повтором возможно **только** для стратегии «Сводка»; остальные стратегии сразу показывают ошибку без вызовов API;
- реальная ошибка превышения контекста от API (если она всё же произошла) показывается отдельно, с текстом провайдера; история также откатывается, частичный ответ не сохраняется.

## Как устроено хранение

Хранение — отдельная ответственность (`storage.py`), в Streamlit-интерфейсе нет SQL. `ChatAgent` отвечает за стек сообщений, вызов API, сбор `usage`/`finish_reason`, выбор payload по стратегии, сжатие истории, обновление фактов и откат при ошибке. Чистая логика контекста вынесена в `context.py`, стратегии — в `strategies.py`, модель фактов — в `facts.py`; они не знают ни про SQL, ни про Streamlit, ни про клиента модели.

База: `week-02/first-agent/data/chat_history.db`. Схема:

- `chats` — чат: название, настройки (`system_prompt`, `model`, `temperature`, `max_tokens`, `stream`, `demo_context_limit`, `context_strategy`, `sliding_window_messages`, `facts_window_messages`), накопительные `input_tokens`/`output_tokens`, `history_tokens_est` (≈ уникальная история), `cost_usd` (≈ накопительная стоимость ходов), `last_context_tokens` (размер последнего основного payload), `summary_*` (накопительный расход на **все** попытки сжатия), `facts_ok_*`/`facts_fail_*` (расход успешных и оборванных вызовов фактов), `facts_anchor_message_id` и `active_branch_id`; `NULL` означает «нет данных»;
- `messages` — сообщения (`user`/`assistant`) с привязкой к чату (`ON DELETE CASCADE`) и к линии (`branch_id`; `NULL` = основная линия); здесь лежит **полная** переписка;
- `turns` — статистика одного обращения: связь с парой сообщений, оценка токенов сообщения, точные `request_tokens`/`response_tokens`/`total_tokens`, cache hit/miss, `finish_reason`, `cost_usd`, `cost_assumption`, время;
- `summaries` — актуальная сводка **линии**: `content`, `covered_messages_count` (якорь покрытия), `format_version`, агрегат токенов и стоимости последнего **успешного** обновления, `branch_id` (`NULL` = основная линия), время обновления. На каждую линию хранится одна актуальная строка; удаляется каскадно вместе с чатом;
- `facts` — память фактов: `category`, `fact_key`, `value`, `status` (`active`/`cancelled`/`replaced`), `reason`, время. Уникальный частичный индекс гарантирует не более одного активного факта на ключ; удаляется каскадно вместе с чатом;
- `branches` — ветки: `name`, `parent_branch_id`, `fork_message_id` (checkpoint — завершённый assistant-ход), время. Ветка удаляется по одной через UI (сообщения/ходы/сводка её линии удаляются в одной транзакции) либо каскадно вместе с чатом; `name` не имеет UNIQUE-ограничения, а дубли имён отсекаются на уровне операции создания;
- `app_state` — служебные ключи, включая последний выбранный чат.

Целостность:

- пустой запрос не обращается к API;
- при ошибке API частичный ответ не сохраняется;
- сообщения пары, строка `turns` и обновление накопительных счётчиков пишутся **одной транзакцией**;
- запись сводки и обновление накопительных счётчиков сжатия тоже выполняются **одной транзакцией**;
- применение набора операций с фактами и сдвиг якоря выполняются **одной транзакцией**: при любой ошибке откатываются и факты, и якорь;
- расход **всех** выполненных попыток (сжатия и фактов), включая оборванные и невалидные, сохраняется отдельными транзакциями, которые не меняют ни строку `summaries`, ни факты, ни якорь;
- сбой вспомогательного вызова не откатывает уже сохранённый ход и не портит прежнюю память;
- удаление чата каскадно удаляет его сообщения, статистику ходов, сводки, факты и ветки;
- **миграция старой базы** идемпотентна: при первом открытии добавляются новые колонки `chats`/`messages`/`summaries`, таблицы `facts`/`branches` и частичные индексы сводок; стратегия существующих чатов выводится из прежнего флага `summarize` (`0` → `full`, иначе `summary`) **только если она не задана**, поэтому вручную выставленная стратегия и старые данные не перезаписываются;
- миграция также нормализует точное legacy-значение модели: `deepseek-v4-flash` в `chats.model` заменяется на канонический `deepseek-flash`; другие (пользовательские) значения модели не изменяются, повторное открытие базы идемпотентно.

## Структура проекта

- `tokens.py` — детерминированная локальная оценка токенов (stdlib, без зависимостей).
- `strategies.py` — чистые константы и нормализация стратегий контекста: машинные значения, русские подписи, окна по умолчанию, `normalize_strategy`/`normalize_window`, `summary_compression_enabled`. Без I/O.
- `facts.py` — чистая модель памяти фактов: категории и статусы, бюджеты и системный промпт извлечения, `parse_facts_response`, `format_facts_block`, `build_facts_extraction_messages`, контейнеры `FactOperation`/`Fact`/`FactsOutcome`. Без I/O.
- `stats.py` — нейтральные контейнеры `TurnStats`, `AskResult` (включая `summary_error` и `facts_error`) и `SummaryOutcome` (попытки суммаризации), а также чистые агрегаторы `sum_optional`/`aggregate_stats`; не тянут зависимости агента, хранилища или UI.
- `pricing.py` — централизованные тарифы, peak/off-peak и расчёт оценочной стоимости.
- `context.py` — чистая логика управления контекстом: сборка payload со сводкой, полной историей, скользящим окном и блоком фактов, план сжатия, промпт суммаризации, валидация сводки. Без I/O и внешних зависимостей.
- `models.py` — единый реестр моделей: канонический ID по умолчанию (`deepseek-flash`), отображаемые названия (`DeepSeek V4.1 Flash`), безопасная нормализация точного legacy-alias. Без I/O и внешних зависимостей; отображаемое название никогда не уходит в API.
- `agent.py` — агент как отдельная сущность, **не зависит от Streamlit**:
  - `get_client()` — клиент DeepSeek API по `DEEPSEEK_API_KEY` из `.env`;
  - `AgentConfig` — `model`, `system_prompt`, `temperature`, `max_tokens`, `stream`, `demo_context_limit`, `summarize`, `keep_recent_turns`, `context_strategy`, `sliding_window_messages`, `facts_window_messages`;
  - `ChatAgent.ask(...) -> AskResult` — выбор payload по стратегии, демо-предпроверка по этому payload, отправка контекста, сбор точного `usage`/`finish_reason` (stream и non-stream), локальные оценки, расчёт стоимости, атомарное сохранение, откат при ошибке и пост-обработка строго по стратегии (сводка либо факты, иначе ничего); исключения `ContextLimitError` (демо-лимит) и `ApiContextOverflowError` (реальная ошибка провайдера).
- `storage.py` — `ChatStore`: схема и миграция, чаты (включая ручное переименование), настройки, сообщения и линии, статистика ходов, сводки по линиям, факты, ветки, накопительные счётчики, последний выбранный чат.
- `app_logic.py` — чистые помощники интерфейса без зависимости от Streamlit: сравнение настроек (учитывает `None`/`0` демо-лимита и эффективное значение `summarize`) и управление спиннером ожидания для потокового режима.
- `app.py` — Streamlit-интерфейс: список чатов с расходом и кнопками переименования/удаления, настройки (стратегия контекста и её окна, полное название модели), сообщения с токенами, панели «Сжатие истории»/«Sticky Facts»/«Ветки» по активной стратегии, «Статистика текущего чата» и «Сравнение диалогов», индикаторы ожидания, сжатия и обновления фактов, обработка ошибок.
- `tests/` — `test_strategies.py`, `test_facts.py`, `test_context.py`, `test_agent.py`, `test_storage.py`, `test_tokens.py`, `test_pricing.py`, `test_app_logic.py`, `test_app_ui.py` (unittest; UI-проверка через Streamlit `AppTest` с внедрёнными временным хранилищем и фиктивным клиентом; **без реальных сетевых запросов**, без настоящего ключа и без чтения `.env`).
- `requirements.txt` — зависимости: `openai`, `python-dotenv`, `streamlit` (SQLite и математика — стандартная библиотека; новых зависимостей нет).
- `run_app.bat` — запуск приложения двойным щелчком.
- `.env.example` — образец `.env` без настоящего ключа.

## Сценарий для видео: чат со сжатием против чата без сжатия

Цель — на одних и тех же вопросах показать разницу в качестве ответов и в расходе токенов/денег, включая стоимость создания сводки.

1. Создайте **два чата** с одинаковыми настройками: одна и та же модель, `temperature`, `max_tokens`, system prompt.
   - **Чат A «Со сжатием»**: стратегия «Сводка», «Последних ходов без сжатия» — `2` (чтобы сжатие сработало быстро и за видео прошло несколько сжатий).
   - **Чат B «Без сжатия»**: стратегия «Полная история». При желании задайте «Демо-лимит контекста», например `400`, чтобы в конце показать понятную ошибку переполнения без реального запроса.
2. Задайте в **оба чата** одну и ту же последовательность коротких сообщений, например:
   1. «Меня зовут Алекс. Запомни.»
   2. «Мой любимый цвет — синий.»
   3. «Название проекта — Орбита.»
   4. «Ограничение: отвечай не длиннее 20 слов.»
   5. «Решение: итоговые отчёты делаем по пятницам.»
   6. **Исправление**: «Нет, любимый цвет не синий, а зелёный.»
   7. Ещё 2–3 любых коротких вопроса (в чате A за это время пройдёт не одно сжатие).
3. Спросите в **оба чата**: «Что ты помнишь обо мне, моих ограничениях и решениях?»
   - Чат A должен сохранить факты (имя, проект), ограничение (не длиннее 20 слов) и **исправленный** цвет — зелёный, а не синий.
   - Сравните полноту и точность ответов A и B.
4. В чате A раскройте «Сжатие истории»:
   - покажите текст сводки и строку «Сводка заменяет первые N сообщений (M ходов)…» — видно, какую часть переписки она заменяет;
   - покажите «≈ Контекст запроса без сжатия: X ток. · со сжатием: Y ток.» — наглядная разница размера контекста;
   - покажите расход на создание сводки (последний вызов и накопительно).
5. Раскройте «Сравнение диалогов»:
   - у чата A контекст ходов стабилизируется, у чата B растёт с каждым ходом;
   - у чата A есть «≈ Стоимость сжатия» и «≈ Итого», куда она входит;
   - проговорите вывод: **уменьшение контекста не означает автоматически такую же экономию денег**, потому что создание сводки — отдельный платный вызов.
6. Если у чата B задан демо-лимит, доведите его до предупреждения о превышении: сообщения при этом не удаляются, а запрос в API не отправляется.
7. Дополнительно проверьте устойчивость: перезапустите приложение (`run_app.bat`) и откройте чат A — стратегия и сводка загрузятся из БД; переключите стратегию «Полная история» → «Сводка» — при возврате используется уже сохранённая сводка.

## Сценарий: остальные стратегии контекста

**Скользящее окно.** В настройках чата выберите «Скользящее окно» и задайте размер, например `3`. Задайте несколько вопросов и раскройте «Статистика текущего чата»: «Последний контекст запроса» стабилизируется, потому что в модель уходят только последние сообщения и текущий запрос. Затем увеличьте окно — контекст вырастет. Переключитесь на «Полная история» — окно перестанет действовать.

**Sticky Facts.** Выберите «Sticky Facts» и сообщите несколько фактов («Название проекта — Орбита», «Любимый цвет — синий»), затем исправьте один («Нет, зелёный»). После каждого хода приложение отдельным вызовом обновляет факты; в панели «Sticky Facts» видно:
- активные факты (должен остаться только актуальный цвет);
- отменённые и заменённые (старое значение с причиной);
- расход успешных и оборванных вызовов.
Задайте новый вопрос — блок фактов виден в контексте, а старые сообщения уже не нужны.

**Ветвление.** Выберите «Ветвление». После двух-трёх ходов откройте панель «Ветки»:
- в дереве видно основную линию и уже созданные ветки, у каждой — родитель по имени и checkpoint;
- в форме создания выберите «Родительская линия» (по умолчанию — активная) и checkpoint **этой** линии; до нажатия «Создать ветку» есть предпросмотр, поэтому видно, от какой линии и какого хода пойдёт ответвление;
- задайте имя и создайте ветку. Поле имени очистится, активной станет новая ветка. Повторное имя (даже с другим регистром/пробелами) и пустое имя будут отклонены.

Переключитесь по дереву на основную линию — её история не изменилась. Из того же checkpoint основной линии создайте вторую ветку: у обеих общий префикс, а продолжения разные и не пересекаются. Удалите ошибочную ветку через 🗑️: подтвердите удаление; её сообщения/ходы/сводка исчезнут, а основная линия и соседняя ветка останутся. Ветку, у которой есть дочерние, удалить нельзя — сначала удалите детей. Перезапустите `run_app.bat` — дерево, родительские связи и активная ветка сохранятся.

## Демонстрация: короткий, длинный и переполненный диалог

Короткий диалог:

1. Нажмите «➕ Создать чат» и отправьте короткое сообщение, например «Привет».
2. Под сообщением появится `≈ N ток. сообщения (оценка)`.
3. Под ответом — точные токены ответа и строка хода: контекст, всего, cache hit/miss, `≈` стоимость, `finish_reason`.
4. Раскройте «Статистика текущего чата» — там итоги и таблица ходов.

Длинный диалог и сжатие:

5. Продолжайте задавать вопросы в том же чате. Без сжатия «контекст» растёт: история отправляется заново целиком.
6. Со сжатием (по умолчанию) после 4-го хода в «Сжатии истории» появится сводка, а в следующих запросах старые ходы заменит она.
7. Раскройте «Сравнение диалогов» и сравните «Накопленный вход», «≈ Стоимость ходов», «≈ Стоимость сжатия» и «≈ Итого» между чатами.

Лимит ответа (`max_tokens`), не путать с контекстом:

8. В настройках чата задайте маленький `Max tokens` (например, 20) и попросите длинный ответ.
9. Под ответом появится `finish: length` и пояснение, что достигнут лимит длины ответа, а не контекста.

Переполнение контекста (безопасно, без реального запроса):

10. В настройках чата задайте `Max tokens` = 50, «Демо-лимит контекста» = 200 и стратегию «Полная история».
11. Отправляйте сообщения, пока локальная оценка полной истории + `max_tokens` не превысит лимит. Приложение покажет предупреждение и **не отправит** запрос; история и база не изменятся.
12. Чтобы снять ограничение, верните «Демо-лимит контекста» в `0`.

Стоимость и неизвестный тариф:

13. В настройках чата можно изменить модель. Для неизвестной модели стоимость показывается как «тариф неизвестен».

## Исправления после Дня 8

- При выключенном демо-лимите (`0` в интерфейсе, `None` в конфиге) обычный rerun больше не сохраняет настройки повторно: `None` и `0` считаются одним и тем же «выключено», а сохранение происходит только при реальном изменении любого поля. Переключение лимита `0 → положительное → 0` по-прежнему сохраняется.
- В потоковом режиме во время ожидания показывается спиннер «Ожидание ответа...» (поверх скелетон-плейсхолдера). После первого фрагмента спиннер исчезает, и вывод продолжается потоково; при ошибке или срабатывании демо-лимита спиннер также убирается. Непотоковый режим со своим индикатором не изменился.

## Ограничения и оговорки

- Локальная оценка токенов — эвристика, а не токенизатор; она может заметно отличаться от точных значений и всегда помечается `≈`. Сравнение «до/после сжатия» тоже построено на этой оценке.
- Условие сжатия — по числу ходов, а не по фактическому размеру контекста: это предсказуемо, но не оптимизирует каждый конкретный случай.
- Сжатие идёт порциями (по 3 хода), поэтому между сжатиями в запрос может уходить немного больше `N` ходов; последние `N` ходов при этом всегда передаются полностью.
- Предзапросное сжатие при переполнении возможно **только** для стратегии «Сводка» и опирается на **демо-лимит контекста** (другого известного лимита у приложения нет). Остальные стратегии сразу показывают ошибку; если демо-лимит выключен, а реальный запрос всё же переполнит окно модели, приложение честно покажет `ApiContextOverflowError` и не будет автоматически повторять запрос.
- Сводка хранится в одной актуальной версии **на линию** (основную или ветку); история прошлых сводок не ведётся.
- Факты хранятся в одной актуальной версии на ключ: старые значения сохраняются со статусом `replaced`, отменённые — `cancelled`, но история их изменений не ведётся. Категория и важность фактов определяются моделью; промпт требует не выдумывать факты, но не гарантирует этого.
- Извлечение фактов — отдельный платный вызов после пользовательского хода. Он делается только при стратегии «Sticky Facts» и никогда при открытии чата, rerun, смене настройки или ветки.
- Факты и якорь покрытия общие для чата (не привязаны к ветке): при переключении линии уже накопленные факты продолжают использоваться.
- Ветка создаётся только от завершённого хода (assistant + `turns`); checkpoint всегда лежит на выбранной родительской линии. Удаление отдельной ветки предусмотрено в интерфейсе и не каскадно: ветка с дочерними не удаляется, пока дети не удалены; удаление ветки не меняет основную линию, соседей и накопительные счётчики расхода чата (потраченные токены — исторический факт). `≈ Уникальная история` после удаления может выглядеть завышенной, так как это оценка.
- Имена веток уникальны в пределах чата без учёта регистра и лишних пробелов, но жёсткого UNIQUE-ограничения в БД нет: ветки-дубли, созданные до этого исправления, сохраняются и не мешают открытию, отображению и удалению через UI.
- Качество сводки и фактов зависит от модели: промпты требуют сохранять факты, ограничения, решения и исправления, но не гарантируют это.
- У reasoning-моделей скрытые reasoning-токены расходуют бюджет вывода. Базовый бюджет и одна повторная попытка покрывают обычную надбавку; если reasoning превысит и увеличенный бюджет, и сводка, и факты будут отвергнуты как настоящий обрыв — с предупреждением и сохранением прежней памяти.
- В накопительные счётчики (сжатия и фактов) попадает агрегат **всех** выполненных попыток, включая оборванные и невалидные; история попыток по отдельности не ведётся, а старые записи не пересчитываются.
- Редкий компромисс: если вызов прошёл, а запись в базу не удалась, результат теряется и при повторе вызов оплачивается снова. Данные при этом не повреждаются.
- Демо-лимит проверяется по оценкам фактического payload выбранной стратегии, поэтому его срабатывание приблизительное; настоящую защиту обеспечивает ошибка API, которая показывается честно.
- Определение реального переполнения контекста опирается на признак ошибки провайдера (`status_code` 400 и упоминание context); при другой формулировке ошибка покажется как обычная, без падения.
- Стоимость старых ходов, у которых нет точной статистики, не восстанавливается — для них «нет данных».
- Тарифы привязаны к официальной таблице DeepSeek на дату проверки; при изменении цен правится только `pricing.py`.
- UI-проверка стратегий автоматизирована через Streamlit `AppTest` с внедрённым временным хранилищем и фиктивным клиентом (без сети и `.env`); полноценная ручная проверка ответов модели и панелей на реальном ключе остаётся за пользователем.

> Файл `.env` содержит секретный API-ключ и не загружается в Git благодаря `.gitignore`. Файл базы `data/chat_history.db` и его `-wal`/`-shm` тоже исключены из Git.
