# D34 — Работа с файлами проекта в Developer Assistant

DESIGN_STATUS: READY_FOR_INDEPENDENT_STATIC_REVIEW  
SPEC_GATE_STATUS: NOT_ASSESSED  
TASK_CLASS: PRODUCT · стадия этого документа: SPECIFICATION

## 1. Задача и неизменные границы

В существующем чате добавить режим **Project files**: пользователь выбирает проект и Local либо DeepSeek и формулирует цель. Модель самостоятельно исследует несколько файлов, ищет факты, анализирует влияние изменений, создаёт или редактирует реальные файлы черновика. Пользователь видит сохранённые файлы, вычисленный diff, результаты проверок и отдельно применяет просмотренный черновик одной кнопкой **Apply**. **Undo** и восстановление прерванного применения защищают последующие изменения пользователя.

Исходное D34 требует чтение/поиск/анализ/создание/изменение файлов, инициативу модели по цели, минимум два разных сценария и работу с несколькими файлами, сохранённые изменения либо diff, повторяемость, код и видео. Согласованное расширение включает три настоящих сценария, все пять типов примеров задания в двух основных потоках, оба выбранных провайдера, русский учебный DOCX с реальными снимками и MP4. Третий сценарий выполняется после двух основных, но остаётся обязательным D34-06. Все D34-01..21 обязательны; старый предварительный список из 14 пунктов и формулировка optional не ослабляют замороженный контракт.

Авторизация полного цикла получена. Эта стадия ограничена тремя документами SPEC/PLAN/ACCEPTANCE: без кода продукта, тестовых изменений, запуска приложения, моделей и LIVE. До реализации нужен независимый статический PASS по текущим хешам документов и Implementation readiness. READY автора не является приёмкой.

Не создавать универсальную IDE, новый проект или новый стек. Сохраняются Python/FastAPI/Pydantic/SQLite, MCP SDK и статический English HTML/CSS/JS без сборки/CDN. Не менять защищённые правила, bat, настройки моделей, секреты, опубликованные недели и старые отчёты. Модель не получает shell, удаление, Git-публикацию, отправку сообщений или произвольный тестовый запуск.

## 3. Минимальные границы реализации

1. `assistant/maintenance.py`: scoped inventory, неизменный baseline, версии draft, реальный diff, фиксированные проверки, Apply/Undo и журнал восстановления. Один компонент владеет файловыми инвариантами.
2. `assistant/maintenance_mcp.py`: настоящий SDK stdio server с типизированными инструментами; client session переиспользуется в пределах run. Допустим небольшой client helper рядом с ним, если нужен для ясного lifecycle. Сервер получает от host только непрозрачный идентификатор run и host-controlled хранилище; root/draft не выбираются аргументами модели.
3. `assistant/maintenance_service.py`: model-led loop, бюджет, сообщения, шаги и отмена. Использует существующие Provider/Store и сохраняет task с `mode=files`, project_id, chat_id, provider, run_id.
4. Небольшая интеграция в `assistant/api.py`, `service.py`, `store.py`: маршрутизация режима, координация busy/Stop/restart, дополнительные таблицы/поля без изменения старых задач. UI в `static/maintenance.js` с малыми точками подключения в index/app/style. `review.js` и Support сохраняют свои обязанности.

Не вводить общий framework агентов, новый scheduler или второй универсальный executor. Готовый список подзадач Coordinator регистрирует только после независимого SPEC gate.

## 4. Хранение, версии и фактический поток

Локальные данные D34 находятся под ignored `local-data/maintenance/`, отдельно от индекса, пользовательских документов и Support. Для run сохраняются `manifest.json`, `baseline/`, `draft/`, неизменяемые revisions и журнал операций; SQLite хранит task/index и идентификаторы. Читаемые доказательства публикуются отдельно после обезличивания. Runtime-данные не коммитятся.

При старте host делает ограниченную snapshot разрешённых UTF-8 файлов выбранного корня: не более 2048 файлов, 512000 bytes каждый, суммарно 32 MiB. Baseline содержит точные исходные bytes и SHA-256; отсутствие файла — отдельная версия MISSING, а не пустой файл. Из inventory исключаются запрещённые объекты без чтения их содержимого; причины и счётчики известны. При превышении бюджета snapshot run получает явное incomplete/unsupported и не обещает полный проект. Создание snapshot не помещает файлы в prompt: модель получает только цель, общие правила, tool schemas и результаты собственных вызовов.

Операционный поток: цель → model plan/discovery → зависимые read/search → небольшие draft edits → readback/checks → вычисленный diff → draft ready → owner Apply → applied. Discovery начинается без обязательного RAG; индекс может помогать навигации, но актуальные source hashes и tool results авторитетны. Каждая запись draft создаёт новую revision и инвалидирует старые diff/check/review tokens. Файлы читаются как данные; внедрённые в них инструкции не меняют цель, инструменты и scope.

Run хранит оригинальную цель без сокращения, выбранные provider и проект, настройки бюджета без секретов, план с зависимостями, tool-call IDs/аргументы/результаты, file versions/ranges, read-set, search/list inventory dependencies, check receipts и все ошибки. Полные допустимые ответы и tool transcripts доступны независимо от сводки. Private reasoning не сохраняется в evidence/долговременном transcript и не выводится в UI; если протокол требует `reasoning_content`, он существует только в ephemeral обмене для refeed текущему провайдеру.

Для чтения используется overlay: draft version, если она существует, иначе baseline. Внешние исходные файлы не меняются во время исследования. Read/search возвращают явно `origin=baseline|draft`, hash, revision и стабильный evidence ID. Перед Apply host сверяет актуальный оригинал с baseline для всех прочитанных source-файлов и targets; для search/list сверяет inventory fingerprint/версии области поиска, чтобы новый или изменённый потребитель не пропал из проверки зависимости. Read-set нельзя сократить до изменяемых targets.

### 4.1. Неизменный host context budget конкретного files run

До создания/постановки generation job в очередь host валидирует выбор владельца и сохраняет в task `files_context_budget`: `schema_version=1`, `selection=profile_default|expanded_40000|expanded_100000`, `profile_default_chars`, `effective_chars`, `source=profile_default|explicit_run|retry_preserved|legacy_retry_profile_default`; только Retry содержит `retry_of`. `profile_default_chars` остаётся строгим целым 1000..40000; `effective_chars` — строгим целым, согласованным с selection: для `profile_default` равно сохранённому default, для `expanded_40000` равно 40000, для `expanded_100000` равно 100000. Bool/float/string, неизвестные selection/source и несогласованные значения не принимаются. Это расширение schema_version=1: ранее сохранённые default/40000 snapshots сохраняют прежний смысл; произвольные значения между 40000 и 100000 не разрешаются. Recorded Retry сохраняет исходные selection/default/effective и меняет только source на `retry_preserved` и `retry_of`. Несогласованная либо частично повреждённая metadata отклоняется, а не трактуется как legacy.

При создании manifest копируется тот же snapshot; task/run должны совпадать. Snapshot неизменяем: execution, сохранение task, checkpoint, Stop, reopen/restart, draft edit, Apply и Undo не меняют его. Старые задачи без metadata читаются как historical budget **unknown**; никакого backfill значением 18000. Для новой явно отправленной цели текущий default валидируется до queue даже при expanded выборе, неверный default даёт configuration error. Recorded Retry валидирует сохранённый snapshot, не требует нового default и не заменяет им старое число. Секретов и endpoint в snapshot нет.

## 5. Настоящие MCP-инструменты

Host делает реальный SDK `tools/list`, валидирует/allowlist-ит полученные schemas и предлагает их модели в формате существующего provider adapter. Только реальные model tool calls вызывают SDK `tools/call`; host не подставляет фальшивые assistant calls, не выбирает файлы по тексту цели и не выполняет заранее написанный сценарий вместо модели. Обязательные системные проверки/снимок можно выполнять host-ом, но в журнале они имеют отдельное происхождение и не считаются инициативой модели.

| Инструмент | Вход/смысл | Результат и ограничения |
|---|---|---|
| `list_files` | `cursor?`, `page_size` 1..100 | Относительные paths, sizes/hashes; next_cursor, complete, inventory_version, exclusions summary |
| `search_text` | Непустой literal query до 200 символов, `cursor?`, page_size 1..50, optional path prefix | Все строки поддерживаемых файлов, а не первые 200; matches с line/range/hash, next_cursor, scanned/eligible counts, exclusions и coverage_complete |
| `read_file` | path, start_line ≥1, count 1..200, optional continuation | UTF-8 text до 12000 chars, точный фактический range, total_lines, hash; next range/offset при длинной строке; oversized/binary/missing — явные состояния |
| `create_file` | path, content, expected_missing=true | Реальный файл draft, new hash/revision, bytes; отказ при существующем файле, даже если content совпадает |
| `apply_edit` | path, expected_hash, уникальный exact old_text/new_text; bounded content | Замена единственного совпадения в draft; conflict/ambiguous не меняют bytes; для новой версии используется её текущий hash |
| `get_diff` | optional path, cursor | Server-computed before/after/unified diff из baseline bytes и текущего draft, включая новые файлы, hashes, review revision; большие diff читаются страницами |
| `run_fixed_checks` | suite ID из host allowlist | Настоящий тип проверки, observed result, input revision/hashes, exit/result, limitations; неизвестный проект — NOT_ASSESSED/unsupported |

Строгие Pydantic/JSON schemas запрещают лишние поля, неверные типы/размеры; сервер повторно проверяет каждый аргумент. Чтобы модель не переписывала длинные hashes, допустим server-issued короткий version token: он однозначно привязан к полному hash/path/run/revision и проверяется сервером; произвольная или старая ссылка не принимается. Cursor непрозрачно привязан к run, query, inventory/revision и offset; устаревший cursor даёт conflict, а не смешанные страницы. Поиск регистронезависимый literal, deterministic order path/line/offset, читает полные разрешённые files по страницам. Повтор страницы не расходует факты заново; нет утверждения «все», пока coverage incomplete. Truncation, match cap, слишком длинные строки, запрещённые/нечитаемые файлы видны отдельно. No-match отличается от unsupported/missing и неполного поиска.

Проверки не принимают shell command, executable, test filename или произвольный module от модели. Для generic проектов доступны безопасные text/encoding/размер/diff и syntax/static проверки поддерживаемых форматов. Настоящие поведенческие проверки разрешены только из фиксированного owner-trusted registry и на разрешённой fixture, с проверкой доверенного checker/baseline test hashes и изолированными временными данными. Изменённые моделью tests/runners не становятся доверенным checker. Если безопасного trusted execution для выбранного проекта нет, execution остаётся NOT_ASSESSED. Самостоятельная проверка синтаксиса не означает прохождение тестов или верность цели.

## 6. Ограниченная итерация и контекст

Отдельный files workflow: до 48 model turns и 72 tools calls, до 24 edits, суммарно до 512 KiB полученных текстовых данных, до 15 минут wall time на run; один provider request до 360 секунд, read/search до 15 секунд, fixed check до 60 секунд. Бюджет редактируемого файла остаётся 512000 bytes; общий draft не превышает snapshot ceiling. Все бюджеты фиксируются до run; изменение требует актуального design review при изменении контрактов и не скрывается в отчёте. Это operational limits, а не новые произвольные пороги приёмки.

Шаги investigation/edit/check строятся и уточняются моделью в коротком JSON plan с depends_on; host валидирует размер и ацикличность, не подсказывает fixture-specific решение. Следующий шаг получает неизменную цель, явные пользовательские ограничения, план, hashes/read ledger, текущие edit targets и нужные excerpts. Окончательный ответ ссылается на версии evidence; обновлённый файл инвалидирует старую ссылку для текущего содержания.

Рабочий context ограничен сохранённым immutable effective_context_chars конкретного run; без явного expanded выбора это snapshot существующего context_chars (§4.1, §6.1). Перед переполнением host сохраняет полный transcript, завершает зависимый шаг и продолжает с компактным проверяемым ledger; оригинальная цель и ограничения никогда не отрезаются. Сводка не заменяет источник факта: необходимые excerpts модель повторно читает по hash/range; при невозможности поместить цель/schema/обязательный ledger — incomplete. Нельзя молча резать конец текста и продолжать как будто всё прочитано. Все вызовы/bytes/time учитываются между шагами, а не обнуляются.

Повтор одинакового неуспешного вызова без новой версии/аргумента останавливается после второго результата; третье одинаковое действие не исполняется. Валидное продолжение другой страницы и readback изменившейся версии не считаются бесполезным повтором. При ошибке модели можно дать один bounded correction с конкретной validation error, сохранив ошибку в transcript. Истечение бюджета/провайдера или незавершённый stream — incomplete/failed, с сохранением уже созданного draft, без fabricated completion и auto-Apply.

### 6.1. Явный выбор host envelope, без изменения модели

Действующий application/profile `context_chars` остаётся default (сейчас 18000), а не фиксированным порогом приёмки. Для нового files run владелец может до Send явно выбрать `Expanded (40,000 characters)` либо `Large (100,000 characters)`. Default и существующий выбор 40000 остаются доступны и не меняются; 100000 разрешается только новым явным выбором владельца до queue. Это предел сериализованного host context в символах, не число model tokens и не physical context window. Не менять Settings, shared Provider, temperature, thinking, max_tokens, выбранные модель/provider, runtime/template либо другие глобальные параметры; не увеличивать бюджет автоматически после ошибки или по тексту цели.

Единственная authority для files execution — локальный immutable `effective_context_chars`, прочитанный из сохранённого snapshot и сверенный с manifest. Применять его ко всем normal requests вместе с schemas, planning, checkpoint source bundles, compaction/pressure lower bound/target/candidate, точному резерву repair request, полному последнему actual assistant с ephemeral private reasoning и всеми actual/deferred IDs/results. Тот же предел используется при расчёте read/search/list/diff allowances и post-write acknowledgement/ledger **до** побочного эффекта. Нельзя оставлять отдельные files ветки на shared `settings.context_chars`. Mandatory goal/constraints/versioned evidence не отрезаются; tool page/file/result ceilings не растут. Все прежние 48 turns/72 calls/24 edits/512 KiB/900s и request/tool limits сохраняются, auxiliary/repair считаются в общие бюджеты. Недостаточное место, physical-context rejection провайдера, неуспешный repair или исчерпание лимитов остаются явным incomplete/failed без fallback. Увеличенный envelope не доказывает правильность результата.

## 7. Scope и инварианты безопасности

Scope привязан к выбранному разрешённому проекту/run сервером. Внешний root, draft directory, абсолютный path и executable не передаются через model tool args. Разрешены только относительные POSIX paths; reject `..`, `.`, empty components, backslash, drive/UNC, colon/ADS, Windows reserved names, trailing dot/space и case aliases. Каноническая проверка containment использует case-aware platform semantics; каждое существующее звено и создаваемый parent проверяются lstat/reparse перед чтением и mutation. Symlink/junction, linked root/ancestor, hardlinked write target и неоднозначные case collisions запрещены. Проверка повторяется при Apply/Undo/recovery; остаётся риск гонки с внешним процессом, поэтому небезопасное/изменившееся состояние приводит к conflict, без обещания полноценной ОС-песочницы.

Исключены `.git`, `.venv`, dependencies, caches/build outputs, local-data, скрытые конфигурационные каталоги, `.env*`, ключи/credentials/tokens/secrets, settings/config files и служебные launch/permission files. Содержимое реальных секретов не читается даже ради теста. Защищённые project rules допускаются только для чтения явных ограничений и запрещены как edit/apply targets. Fixture использует обычный `PROJECT_GUIDE.md` с требованиями продукта. Любая исключённая область отражается в coverage, без раскрытия её содержимого. Prompt injection не может расширить эту policy; negative tests используют синтетические маркеры вместо реальных секретов.

## 8. Apply, Undo и прерывание нескольких файлов

Apply — host API, не MCP-tool модели. Запрос несёт project_id/chat_id/run_id и exact reviewed revision/diff digest. Одна кнопка применяет весь выбранный reviewed draft; применение произвольного поднабора не входит в минимальный дизайн. Устаревшая вкладка, revision или hash дают 409; UI предлагает заново прочитать diff. Любая ручная правка draft через небольшой owner editor с expected_hash создаёт новую revision и требует нового просмотра/проверок. Apply не зависит от утверждения модели «готово».

Одновременно допускается один writer на канонический project root: генерация edits, owner draft edit, Apply, Undo и recovery сериализованы. Использовать общий maintenance coordinator и межпроцессную OS-lock/lease на workspace: lock удерживается живым owner, освобождается ОС после crash; PID-файл сам по себе не является достаточным lock. MCP child работает только по run token/generation. Другие чаты могут читать историю, но не изменять этот workspace. Existing help/review/scheduler занятость учитывается при мутациях проекта; автоматическое планирование files не разрешается в D34.

Порядок Apply:

1. Acquire writer; revalidate run generation/scope/revision and всех read/inventory dependencies/target baseline hashes (для новых файлов — MISSING). Никакой записи до полного preflight всего batch. Существующие пользовательские edits baseline сохраняются; появившиеся после baseline блокируют применение.
2. Persist durable journal `prepared`: paths, точные before bytes/hashes/отсутствие, after bytes/hashes, revision, intent, результаты guard. Подготовить temp файлы в разрешённых target directories. Журнал нельзя строить только после записи первого файла.
3. Для каждого файла: повторный guard, journal intent, атомарная замена одного файла, durable receipt. Многофайловая замена не объявляется общей атомарной транзакцией. При проверяемом изменении target до записи — остановка/conflict. Если состояние изменилось прямо во время записи, receipt фиксирует неоднозначность; complete не выставляется.
4. Readback всех applied targets; только при точном after-state всего batch → `applied`. No-op имеет отдельный outcome и ничего не перезаписывает. Ошибка/Stop/crash между файлами → `interrupted/recovery_required`, никогда applied/completed.

При restart reconcile journal с фактическими bytes: before, after или foreign. Pending записи нельзя слепо повторять. Recovery по умолчанию предлагает **Recover rollback**: вернуть только targets, которые всё ещё равны записанному after-hash; untouched before оставить. Foreign paths приводят к recovery_conflict и сохраняются. Owner видит per-file исход; unresolved journal удерживает workspace от нового writer. Resume вперёд не требуется минимальному решению. Новый файл удаляется при guarded Undo/rollback только как внутреннее восстановление MISSING и только при exact after-hash; у модели нет delete-tool.

Undo доступен для последнего применённого batch данного workspace, проверяет все targets до начала: current==recorded after, новый файл не имеет чужих изменений. При конфликте всего preflight никаких записей; при interruption восстановления тот же журнал/guard rules. Undo не трогает source-only dependencies и не перезаписывает последующие edits пользователя. Длительная mutation не держится на сетевом ожидании модели; Stop перед следующим write инвалидирует generation. Уже выполненный системный write не исчезает: после Stop показывается частичное состояние и recovery.

## 9. Состояния, API и UI

Для совместимости task.status остаётся queued/running/completed/cancelled/failed, а maintenance.stage хранит `investigating`, `editing`, `checking`, `draft_ready`, `incomplete`, `applied`, `conflict`, `interrupted`, `recovery_required`, `undone`. completed означает законченное исполнение, не accepted. Отдельные поля: syntax/static, trusted_tests, draft_readiness, application, quality/goal_review. Последние оценочные поля по умолчанию NOT_ASSESSED. Wrong-but-valid output не принимается автоматически из-за citations/зелёного syntax.

Существующий `/api/tasks` принимает `mode=files` и отправляет в новый service. Дополнительные scoped endpoints получают `pid/tid`, проверяют task→project/chat/root binding и revisions: получить manifest/files, читать persisted draft/diff страницами; owner edit; review token; Apply; Undo; recovery. Полные пути сервера не должны попадать в модельные labels/публичные отчёты. API остаётся loopback с existing origin boundary; body schemas forbids extra fields. Project switch не переназначает уже сохранённый run; stale request не применяется к новому проекту.

English UI: селектор Project files рядом с Project /help и Web, явный provider, естественная цель, waiting/streaming indicator, Stop. В карточке результата collapsible **Activity**, **Files**, **Diff**, **Checks**; relative paths, evidence versions, before/after с new-file status, readback, exact check type/revision, limitations. **Edit draft**, **Apply**, **Undo**, **Recover rollback** доступны по фактическому состоянию. История сохраняет цели, failed/cancelled/incomplete runs, файлы и receipts после reopen. Cancel queued run отменяет его до старта; running Stop инвалидирует token, отменяет provider/MCP pending tasks, закрывает owned stdio, поздние callbacks не пишут draft/task/apply. Смена чата/проекта использует existing epoch и binding и не скрывает активную работу; архивирование активного чата по-прежнему блокируется.

### 9.1. API, UI и Retry для context budget

`POST /api/tasks` получает optional `files_context_chars`: omitted/JSON null означает snapshot текущего валидного profile/application default; допустимые ненулевые внешние значения — **строго integer 40000 либо 100000**. Другие integer (включая 40001, 99999, 100001), float (включая `40000.0` и `100000.0`), bool, string, array/object отклоняются без coercion/clipping и до создания task/job. Ненулевое значение разрешено только при `mode=files`; omitted/null сохраняет прежнее help/web/review поведение. Повторить strict validation на service creation boundary для внутренних callers. Существующие project/chat/provider validation и extra-fields-forbid сохраняются. Поле не входит ни в один MCP schema и не может задаваться моделью/файлом/feedback.

`POST /api/tasks/{tid}/retry` сохраняет нынешнее отсутствие override body и refusal при active task. Для recorded files run новый task копирует ранее валидный immutable budget: сохранённые default (1000..40000), expanded_40000 (40000) и expanded_100000 (100000) воспроизводятся внутренним согласованным snapshot replay, не расширяя внешний выбор beyond integer40000/100000. Изменившиеся текущие настройки/composer не переопределяют recorded budget. Для подлинного legacy run без snapshot новый Retry фиксирует текущий default с `source=legacy_retry_profile_default`, `retry_of`; исходный historical budget остаётся unknown. Это новый run, не обещание воспроизведения неизвестного старого бюджета. Изменить recorded budget можно лишь новой явно отправленной целью.

Небольшой English **Advanced** control показывается только в Project files composer: `Profile default (N characters)` / `Expanded (40,000 characters)` / `Large (100,000 characters)`. N берётся из публичного валидированного default, не hardcoded. Начальный/new composer context выбирает default; failure не выбирает expanded. Send единым snapshot захватывает mode/project/chat/provider/budget до async work; поздние UI selections относятся только к следующей новой цели. Существующие epoch/binding проверки остаются. Saved run details показывают `Context budget: N characters` и origin (`profile default`, `explicitly selected`, `retry preserved`); legacy — `unknown`. Retry help явно объясняет recorded-budget preservation и legacy current-default правило независимо от выбора composer. Files scheduling остаётся запрещённым; глобальный settings editor не добавляется.

## 10. TicketDesk: воспроизводимые предметные сценарии

Небольшой нейтральный пример `examples/maintenance_demo/` с настоящим Python API-контрактом, pure client adapter, tests и документацией. Baseline read-only; сценарии копируют только эту собственную fixture в TEMP/локальный workspace и никогда не reset пользовательский проект. Нет готового отчёта/правильного patch внутри prompt. Независимый oracle находится в tests/evidence, вне файлов, предлагаемых модели. Generic engine проходит дополнительную проверку на другом маленьком проекте с другими именами/API без изменения routing.

Предметные факты фиксируются до LIVE: current `POST /api/tickets/{ticket_id}/resolve`, тело `resolution` (непустое после trim) + `expected_version`, успешный ответ со status/resolution/version, version conflict, already-resolved policy, отсутствие автоматического reopen. Unrelated list/filter behavior сохраняется. README/API и старый client содержат реалистично устаревший `/close` и старые имена полей. `PROJECT_GUIDE.md` требует optimistic concurrency, запрет журналирования чувствительного текста, сохранение unrelated filters и отсутствие неподтверждённых release/test claims. `RELEASE_NOTES.md` даёт только проверяемые текущие факты, без выдуманной даты/истории.

Fixture содержит несколько естественных consumers (client, CLI/view adapter), contract tests, актуальный implementation, stale docs; значимая resolve validation/consumer fact располагается после строки 200 в содержательном API-модуле, без padding. Natural references в tests/docs/consumers дают больше одной search page. Особые binary/oversized/missing/no-match fixtures отделены от предметной истины. До модели независимый checker читает весь fixture source и фиксирует expected invariants/known conflicts. Если объём fixture мешает ограниченному run, упрощают несущественную структуру до LIVE, сохранив late-line/page/consumer requirements и новый baseline hash.

| Сценарий и пример цели без указания файлов/шагов | Необходимый результат | Содержательная оценка |
|---|---|---|
| Impact: «Оцени влияние изменения API завершения обращений и сохрани план миграции с опорой на проект» | Модель читает ≥3 разных files, сама обнаруживает implementation, consumers, tests/docs и правила; создаёт настоящий migration report | Полный oracle inventory: правильные route/fields/version/error policies, все релевантные consumers, конфликты docs/client/rules; source version/ranges; unknown отдельно; отчёт не исправляет молча API |
| Documentation: «Подготовь документацию текущего API обращений к выпуску и запиши только подтверждённые изменения» | ≥3 реально прочитанных files; реальные edits README и API docs, создание/обновление changelog; readback, computed diff, trusted/static checks | Каждое утверждение сверено с полным кодом/фактами; Unreleased для текущих изменений, без выдуманных endpoint/test success/history; второй запуск не дублирует changelog |
| Client: «Приведи клиент к текущему API обращений, сохранив остальное поведение» | ≥3 прочитанных files; узкие реальные edits client и при необходимости caller; проверки version conflict/success и unchanged filters | Exact request/response semantics, existing unrelated behavior, никакой подмены API ради старого client; поведенческие checks на applied bytes; ограничения запуска явны |

Первые два потока покрывают find API uses, check explicit rules, create file, update docs from code и changelog/diff. Третий обязательный поток подтверждает правку кода. Для каждого из Local и DeepSeek выполнить все три полных цели на чистых копиях. Затем повторить основные потоки с чистого baseline и повторить documentation/client на уже обновлённом workspace: нужна семантическая корректность и отсутствие ненужных изменений, а не byte-identical слова. Исторический failed run не удаляется при исправлении.

Oracle semantics v2 — уточнение без изменения D34-01..21: route/body/status/resolution/version и trim являются контрактом SERVER wire. Adapter обязан строить правильный resolve request, использовать показанную expected_version и читать новые wire поля, но может передавать исходный непустой padded text на сервер, который сам trim-ит его, либо выполнять эквивалентный trim. Публичный результат adapter может сохранять прежние state/note через чтение body.status/body.resolution; новая status/resolution projection допустима только при совместимости actual consumers. Не требовать конкретного слоя нормализации или переименования публичного результата при одинаковой API-семантике. Сигнатуры, реальные значения id/version/text/status, явные ошибки/concurrency/no automatic retry/reopen и unrelated filters/order/inputs сохраняются. Baseline fingerprint RELEASE_NOTES остаётся проверкой происхождения fixture/release facts; сам draft RELEASE_NOTES не является запрещённым contract edit. Truthful related Unreleased updates допустимы и проверяются отдельно целиком; это не утверждение их истины. Draft server/tests/PROJECT_GUIDE остаются запрещёнными для оправдания старого клиента. Старые checker verdicts сохраняются с прежним hash; после независимого static gate используется явная новая версия oracle и новый hash, а не переписывание доказательств.

## 12. Риски и точки независимого review

- Native tool calling выбранной Local — самый ранний implementation probe; несовместимость не скрывается prompt routing.
- Per-run context snapshot обязан быть сохранён до queue и неизменен; Retry, legacy unknown и current task/run agreement проверяются независимо. Host characters не подменяют model window и не гарантируют семантический успех.
- Snapshot/inventory/search budget, compaction и optimistic guards должны сохранять происхождение и честную полноту; это содержательная проверка, а не наличие полей.
- Несколько файлов не атомарны как один FS transaction; crash/restart проверяются между отдельными replacements и receipt writes. External concurrent writers не обязаны соблюдать app lock; guard/recovery конфликтуют безопасно.
- Нельзя запускать произвольный код выбранного проекта под видом trusted suite. Registry/fixture checker — явная ограниченная граница, generic execution может быть NOT_ASSESSED.
- Состояние task и filesystem journal расходятся при crash; authoritative reconciliation по bytes и journal, никакого silent reset.
- Итоговый PASS исходной задачи требует всех 21 критериев, полного реального UI/LIVE/артефактов/публикации. Этот дизайн ещё не утверждает работоспособность и независимую приёмку.
