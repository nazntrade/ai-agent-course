# D34 — Работа с файлами проекта

**Project files** расширяет существующий чат. Пользователь выбирает проект,
Local/DeepSeek и цель; приложение сохраняет исходное задание, небольшой зависимый
план, фактические вызовы MCP, draft, diff, проверки и журнал применения.
Предварительный RAG-индекс для этого режима не обязателен. Старые режимы D31–D33
сохраняют свои маршруты и данные.

## Цель, инструменты и данные

`maintenance_service` ведёт конечный модельный цикл, `maintenance_mcp` предоставляет
настоящий SDK stdio server, `maintenance` хранит baseline/draft и применяет операции,
`maintenance_evidence` учитывает полученные доказательства. Корень проекта, run и
generation назначает host; модель не передаёт произвольный корень или команду.

| Инструмент | Фактическое действие |
| --- | --- |
| `list_files` | Страница поддержанных файлов с явными исключениями |
| `read_file` | Версионированный текст исходника или draft с диапазоном и продолжением |
| `search_text` | Постраничный поиск, включая строки после 200 |
| `create_file` | Сохранение нового UTF-8 draft при подтверждённом отсутствии файла |
| `apply_edit` | Одно уникальное точное замещение с проверкой текущей версии |
| `get_diff` | Настоящий постраничный baseline-to-draft diff |
| `run_fixed_checks` | Фиксированные static либо поддержанные TicketDesk checks |

Схемы проверяются на обеих сторонах. Пути относительные, с проверками containment,
Windows aliases/ADS/reserved names, links/reparse ancestors и hardlinked targets.
Секреты, конфигурации, Git, dependencies, caches и runtime-данные исключены. Правила
проекта доступны для чтения, но не для изменения. Текст файлов — untrusted data.
Инструменты не дают shell, произвольного исполнения Python, публикации или сообщений.

Baseline неизменяем; draft и revision сохраняются отдельно от рабочего проекта.
Предел snapshot: 2048 поддержанных UTF-8 файлов, 512 000 bytes на файл, 32 MiB суммарно.
Постраничные ответы сообщают реальные диапазоны, версии и неполноту. Continuation
продолжает свой проверенный исходный диапазон; точный `next_call` не требует угадывать
параметры. Search сообщает окончательный итог лишь после завершения сканирования;
завершённое сканирование и полнота покрытия с учётом исключений различаются.

## Конечный цикл и контекст

Общие ограничения запуска: **48 model turns, 72 tool calls, 24 edits, 512 KiB
полученных результатов и 900 секунд**. Один запрос провайдера ограничен 360 секундами.
Инструментальный результат сохраняет отдельный предел 16 000 символов; checkpoint
ограничен 5000 символами исходного и сериализованного содержимого.

Рабочий контекст — точный сериализованный envelope приложения: исходная цель,
host ledger, схемы, сообщения, результаты и private ephemeral reasoning актуального
assistant turn. Исходные 18 000 символов, явные 40 000 и 100 000 — host allowances,
а не tokens/max_tokens модели. Явный выбор допустим только до нового файлового
запуска. Сохранённый snapshot определяет все normal/auxiliary/prewrite проверки;
очередь и Retry не подхватывают позднейший выбор composer. Исторический запуск без
метаданных сохраняет unknown; его новый Retry явно фиксирует тогдашний default.
Глобальные настройки и параметры выбранного провайдера не изменяются. В браузере
выбор находится в **Options → Working context**.

Каждый запрос имеет один ведущий System. Исходный user goal остаётся в истории.
Фактические assistant/tool groups сохраняются целиком с каждым tool ID; host выполняет
одну допустимую операцию из batch, остальным честно отвечает deferred/not executed.
Последствия операции запрещены, если её полный следующий envelope не помещается.
Нельзя молча обрезать reasoning, терять tool reply или выдумывать assistant prefill.
Private reasoning используется только для совместимого живого протокола и не
сохраняется в публичной истории.

Перед вытеснением нового evidence модель может составить ограниченный фактический
checkpoint по реестру реально полученных source refs. Допустима одна настоящая
коррекция некорректного auxiliary ответа в общих бюджетах. Active memory содержит
facts/conflicts, а не новую повестку: исходная цель и фактический план остаются
отдельными. Структурно валидный checkpoint не доказывает истинность или полноту.
План и checkpoint JSON не транслируются как обычный ответ пользователю.

Дополнительный **UNTRUSTED** cache может вернуть буквальные уже полученные и
вытесненные фрагменты текущей версии. Он использует реальные canonical refs,
вычитает текст актуальной группы, проверяет перекрытия и явно отмечает пропуски.
Не доставленный модели, устаревший или выдуманный текст туда не попадает. Cache
уступает место обязательной группе, schemas, reasoning и резервам и может вернуться
позже; это не новый вызов инструмента и не новая семантическая гарантия.

Успешные повторы чтения и реальные ошибки учитываются отдельно. Полезное новое
покрытие отличается от смены requested page size. Deferral не превращается в
неудавшуюся попытку исполнения. Непродуктивные повторы, исчерпание лимитов и
невместимый обязательный контекст завершаются явной неполнотой.

## Apply, Undo, Recover и интерфейс

Один OS-held workspace lock координирует writers между процессами. Generation и
run lock ограждают Stop/поздние callbacks. **Apply** требует просмотренного текущего
revision/digest и повторно проверяет targets, прочитанные источники и зависимости
инвентаризации/поиска. Чужие изменения вызывают conflict. No-op Apply не отнимает
Undo у последнего реально применённого batch.

Многофайловая запись не является одной атомарной транзакцией файловой системы.
До замен сохраняется durable journal с before/after bytes/hashes; результаты
записей проверяются. Частичный исход остаётся `PARTIAL_OR_UNCERTAIN` с recovery.
**Undo** отменяет последний applied batch только после проверки targets.
**Recover rollback** откатывает именно прерванную операцию: после частичного Undo
он возвращает её before-state, то есть ранее применённые файлы. Чужие позднейшие
правки сохраняются. Новый файл удаляется лишь как guarded rollback к `MISSING`.

При обычной перехватываемой ошибке запись очищает только собственный staging file,
успешно созданный через exclusive creation и сохранивший проверенную identity.
Collision/подмена/чужие объекты не удаляются. Исходная ошибка сохраняется; неудачная
очистка фиксирует известный residue в journal как при применении, так и при Recover.
Пока известный residue существует, чистый rollback не объявляется. Это не гарантия
очистки при произвольном hard exit, аварийном убийстве процесса или потере питания.

После обоих исходов Apply/Undo/Recover UI получает точную сохранённую задачу.
Проверяются project/chat/task, epoch, card identity, action sequence, revision и
terminal status; captured render key сбрасывается и для изменений внутри journal
при прежнем общем статусе. Общий generation fence не позволяет старому poll,
missing-busy-task GET или странице истории затереть новое состояние. Оригинальная
ошибка операции остаётся видимой. При ошибке самого refresh UI требует reload,
не выдумывая успешное применение или восстановление.

## Проверки и доверенная граница

Static checks проверяют синтаксис/формат без исполнения произвольного кода проекта.
TicketDesk — чистый учебный API/client/CLI/view fixture; его route strings не означают
развёрнутый HTTP-сервис. Фиксированный checker интерпретирует реальные client bytes
в закрытом AST subset без exec/eval/import и произвольных attributes.

`client-oracle-wire-equivalence-v2` проверяет route/body/response/version/errors,
порядок/фильтры/входы и сохранение публичного контракта. Допустимы серверная
нормализация resolution и согласованное отображение нового wire response в прежний
публичный result. API/tests/guide обязаны соответствовать доверенным baseline hashes
и effective bytes; точное восстановление этих bytes не считается tamper лишь из-за
сохранившейся записи draft. Release notes — изменяемое содержимое, а не обязательный
fingerprint fixture. Их правдивость проверяется отдельно. Unsupported AST даёт
`NOT_ASSESSED`. Версия/identity checker сохраняются в receipt; старые FAIL не стираются.

В проверенном DeepSeek code-only случае изменён только `ticket_client.py`, а
server/tests/docs сохранены. Новый wire response с `status`/`resolution` согласованно
отображается в прежний публичный результат `state`/`note`. Этот частный успех не
утверждает обновление документации: на той рабочей копии две docs-правки уже были
применены до старта клиентской цели. Клиентская цель и исходное состояние учитываются
отдельно от документационного сценария на другой копии.

Execution, static, trusted behavior, draft readiness, application, quality и goal
review разделены. Ни наличие citations, ни зелёный checker не заменяют независимую
проверку всего текста и исходной цели. Общий runtime выбранной Local-модели также
не является HTTP-runtime учебного TicketDesk: ownership/lease/finally проверяются
отдельно, внешний borrowed runtime не останавливается как собственный.

## Воспроизведение

`test.bat` выполняет весь offline suite; `smoke_test.bat` проверяет запуск без ключей.
Фиксированные сценарии `d34-files-controls`, `d34-apply-controls`,
`d34-workflow-controls`, `d34-content-controls` запускаются через
`test.bat scenario <slug>`. LIVE сценарии `d34-capability`, `d34-goals`, `d34-repeat`
требуют разрешённого полного selected profile и guarded lifecycle. `D34_CASE` выбирает
только impact/documentation/client; без него выполняется полная матрица.
`D34_FILES_CONTEXT_CHARS=40000` либо `100000` передаёт тот же явный аргумент новой
задаче; это не изменение Settings. `d34-artifact-audit` проверяет реальные файлы/хеши
и QA manifest и не заменяет визуальную проверку материалов.

Реальные отдельные Local/DeepSeek запуски дали проверенные impact/doc/client результаты.
Local compact impact сохранил один новый отчёт; полный его текст получен через
фактический `get_diff`, а отдельный post-write `read_file` не заявляется. Static check
прошёл автоматически; модель не вызывала тестовый инструмент, trusted tests для
отчёта остались `NOT_ASSESSED`. У DeepSeek проверен также чистый Retry impact на
исходных девяти файлах с сохранённым явным host budget 100000. Отдельные реальные
docs/client no-op на обновлённой копии дали нулевой draft и пустой diff без
create/edit calls. Клиентский no-op Apply сохранил последнюю реально применённую
клиентскую batch и её Undo, записав собственный NOOP journal с пустым files.

Актуальные измерения, артефакты и ограничения приведены в [RESULTS](RESULTS.md).
При публикации отдельно проверяются конечные материалы и состояние remote;
source review, тесты и завершённая задача не заменяют эти проверки.
