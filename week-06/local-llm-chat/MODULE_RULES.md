# Правила модуля `local-llm-chat`

Универсальные правила живут в курсовом корне, а не дублируются здесь. Этот файл содержит только дельту к правилам курсового корня.

## 1. Цель модуля

Учебный чат-модуль курса (этап D26): диалог с локальной моделью Gemma 12B и с сетевым DeepSeek, сравнение и переключение провайдеров в учебных целях. Модуль демонстрирует единый интерфейс к разным провайдерам LLM и различие локального и сетевого режимов.

## 2. Границы и не-цели

Входит: чат-интерфейс, выбор/переключение провайдера, работа с локальной и сетевой моделью, хранение истории диалога в SQLite.

На первоначальном GOVERNANCE-этапе создаются только правила и каркас. В PRODUCT/SPECIFICATION готовятся или сверяются SPEC/PLAN/ACCEPTANCE, без кода и тестов приложения; IMPLEMENTATION начинается после проверенной SPEC. Команды приложения согласуются по PLAN.

RAG: инструменты индексации, поиска, фильтрации, query rewrite, вывода источников и цитат переносятся из `week-05/knowledge-agent` и сохраняются как **отдельный включаемый RAG-режим**. По умолчанию чат работает без RAG; включение RAG активирует поиск по индексу и проверку цитат (SPEC R1.3, R5.1, R5.2). Инструменты знания не вырезаются.

## 3. Стек и версии

Python + FastAPI + Pydantic + SQLite; статический HTML/JS UI без сборки и без CDN; тесты — Pytest. Точные версии фиксируются в `requirements.txt` на этапе реализации. Стек наследуется из `week-05/knowledge-agent`.

## 4. Структура модуля

- `MODULE_RULES.md` — правила модуля (этот файл).
- `MODULE_STATE.md` — текущее состояние работ модуля.
- `README.md` — накопительный отчёт по этапам.
- `.env.example` — заглушки переменных окружения без секретов.
- `setup.bat`, `test.bat`, `smoke_test.bat`, `run_app.bat` — точки запуска.
- `harness/scenario_runner.py` — раннер сценариев проверки.
- `app/` (на этапе реализации) — исходный код FastAPI-приложения.

## 5. Общие правила модуля

- Существующий модуль развивается на месте.
- Временные и архивные копии модуля запрещены.
- Завершённый и опубликованный этап модуля не изменяется, кроме точечного исправления фактической ошибки; отчёты прошлых этапов не переписываются.

## Классификация задач

- Модуль не имеет собственных ролей, `AGENTS.md` и `PROJECT_RULES.md`: они наследуются из курсового корня.
- Классификация `PRODUCT` / `GOVERNANCE` / `MIXED` / `DIAGNOSTICS` и маршрутизация определяются правилами курсового корня (`TASK_CLASS`); модуль эти правила не переопределяет.
- `MIXED`-задача останавливается Coordinator до делегирования со статусом `TASK_STATUS: STOPPED_FOR_SPLIT`.
- `DIAGNOSTICS` — полностью read-only задача с маршрутом Coordinator → Tester: файлы модуля не создаются, не изменяются, не удаляются и не переименовываются.
- Каждый новый запрос пользователя классифицируется заново.

## 6. Документация модуля

- В модуле один постоянный `README.md`.
- Главный заголовок `README.md` — постоянное название модуля; он не меняется от этапа к этапу.
- Новый этап добавляется в `README.md` новым разделом; номер этапа указывается в заголовке раздела.
- `README.md` обновляется после каждого этапа; отчёт ведётся накопительно.
- Отчёты и `README.md` — по-русски, пользовательский UI — по-английски.

## 7. Запуск и интерфейс

- Для запускаемого модуля сохраняется доверенный `run_app.bat`.
- Для человеческого AI-интерфейса показывается индикатор ожидания; при поддержке streaming ответ выводится потоково, иначе — итоговым ответом после завершения запроса.
- Тесты запускаются прямой командой без лишних pipeline; удаление файлов — только отдельной командой с подтверждением.
- Игнорируемые артефакты тест-раннера (кэши, временные базы данных, coverage) вручную не удаляются.

## 8. Команды

Команды выполняются из каталога модуля. Тела команд настроены по утверждённому PLAN (GOVERNANCE-этап E1); заглушки `CONFIGURE_ME` удалены.

- `setup.bat` — установка окружения и зависимостей (коды `0`/`1`/`2`).
- `test.bat` — прогон Pytest: режимы `unit` (по умолчанию), `integration`, `live`, фиксированная ветка `scenario <slug>` (коды `0`/`1`/`2`/`3`).
- `smoke_test.bat` — дымовая проверка backend на loopback (`/api/health` и корневая страница), останавливает только свой процесс (коды `0`/`1`/`2`).
- `run_app.bat` — запуск приложения в foreground (коды `0`/`1`/`2`).

## 9. Окружение и секреты

Переменные окружения модуля: доступ к сетевому DeepSeek и адрес/имя локальной модели. Секреты хранятся только в `.env`; в `.env.example` — заглушки без реальных значений.

## 10. Данные и миграции

Данные модуля: история диалога и выбранный провайдер — в SQLite. Схема и правила миграций фиксируются на этапе реализации; изоляция тестовых данных от пользовательской БД обязательна.

## 11. API и сеть

Внутренний FastAPI-интерфейс между UI и сервером. Внешние границы: локальная модель Gemma 12B и сетевой DeepSeek; адаптеры провайдеров изолированы от бизнес-логики, секреты — только в окружении.

## 12. UI/UX

Статический HTML/JS без сборки и CDN. Пользовательские состояния: выбор и индикация активного провайдера; индикатор ожидания ответа; потоковый вывод ответа при поддержке streaming, иначе итоговый ответ после завершения запроса.

## 13. Дисциплина тестирования

- Обычные UNIT/INT не читают настоящий `.env` и не зависят от реального API-ключа; сетевые вызовы изолированы или замоканы. LIVE — отдельный ограниченный сценарий по разделу ниже.
- Обязательные LIVE-вызовы local/remote, включая платный remote, уже разрешены выбором модели с policy=allowed; forbidden запрещает реальные вызовы. Standalone-авторизация и границы — по разделу ниже.
- Не ослаблять и не удалять проверки ради успешного прогона; изменение ожидаемого поведения должно следовать из задания.
- Проверять наблюдаемое поведение и требования, а не устройство реализации.
- Уровень проверки должен соответствовать Task Contract; unit-тест с моками не подтверждает реальный контракт внешнего провайдера.
- Tester возвращает `TEST_STATUS: PASS` только после проверки всех обязательных критериев на достаточном уровне; иначе `FAIL` или `BLOCKED`.

## 14. Definition of Done

Проверяемые условия завершённости задачи модуля: пройдены обязательные UNIT/INT; подтверждён выбранный режим провайдера на требуемом уровне; Tester вернул `TEST_STATUS: PASS` по всем обязательным критериям; README обновлён; конфигурация runtime перечитана после GOVERNANCE-изменений.

## 15. Уровни тестирования

- UNIT — логика без сети, изолированные данные.
- INT — взаимодействие компонентов модуля и хранения на тестовой БД.
- LIVE — ограниченный сценарий против выбранной модели при policy=allowed; unit-тесты с моками не подтверждают реальный контракт внешнего провайдера.

## 16. Регистрация в корневом `opencode.json`

Доверенные bat-файлы модуля (`setup.bat`, `test.bat`, `smoke_test.bat`, `run_app.bat`) обслуживает Configurator. В Центре после проверенной SPEC и корневого ДЕЛАЕМ штатная настройка запуска выполняется через ограниченный project_setup внутри текущего PRODUCT; чувствительные изменения вне этой возможности требуют GOVERNANCE. Их запуск и запрет редактирования уже покрыты действующими рекурсивными правилами корневого `opencode.json` (`**/setup.bat`, `**/test.bat`, `**/smoke_test.bat`, `**/run_app.bat` в `edit: deny` и `bash: allow`); отдельная регистрация путей модуля не требуется.

## 17. Что нельзя менять

`MODULE_RULES.md` изменяется в GOVERNANCE. `MODULE_STATE.md` и штатные точки запуска обслуживает Configurator через разрешённый project_setup по правилам корня; PRODUCT-подготовка запуска не требует отдельной GOVERNANCE-задачи. `.env.example` — несекретный пример конфигурации, его может обновлять Developer в PRODUCT при сохранении действующих permissions. Секреты в репозиторий не вносятся.

## 18. Известные ограничения

Тип локальной модели и доступность сетевого провайдера зависят от учебного окружения; команды приложения согласованы и точки запуска настроены (GOVERNANCE E1, заглушки `CONFIGURE_ME` удалены); SPEC создан, код приложения — на стадии IMPLEMENTATION; инструменты RAG/индексации из `week-05/knowledge-agent` переносятся и сохраняются как отдельный включаемый RAG-режим (SPEC R1.3, R5.2).

## Универсальный процесс и приёмка

Применяются AGENTS.md и .opencode/WORKFLOW.md в корне репозитория. В этом файле остаются только факты проекта; LIVE-политика, профиль/lease, trusted scenario, acceptance-contract/evidence и независимая содержательная проверка не дублируются. Результат обычных unit-тестов не подтверждает LIVE или качество ответа.
