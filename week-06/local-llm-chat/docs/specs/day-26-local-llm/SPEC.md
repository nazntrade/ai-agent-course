# SPEC — day-26-local-llm (local-llm-chat)

Статус документа: спецификация стадии SPECIFICATION. Источник требований — задание пользователя D26 (разделы 1–7),
`MODULE_RULES.md` модуля `local-llm-chat` и правила курсового корня (`AGENTS.md`, `PROJECT_RULES.md`,
`.opencode/WORKFLOW.md`). Секреты и приватные endpoint в этот документ не вносятся.

Документ описывает **требуемое поведение** (что), а не устройство реализации. Инварианты пронумерованы `I-*`
и обязательны к сохранению на всех этапах. Требования пронумерованы `R-*`; прослеживаемость к исходным пунктам 1–8
приведена в §14.

## 1. Цель и результат

Модуль `week-06/local-llm-chat` — учебный чат D26, развиваемый **переносом** рабочего чата
`week-05/knowledge-agent` (D21–D25): тот же стек и тот же работающий чат не переписываются с нуля.
Новое по сравнению с week-05:

- двухпозиционный переключатель провайдера ответа: **локальная модель Gemma 12B** и **сетевой DeepSeek**;
- собственный жизненный цикл локального процесса `llama-server.exe` для Gemma;
- независимость от «Центра» (внешнего менеджера моделей/процессов);
- режимы ответа **с RAG** и **без RAG** поверх сохраняемого retrieval;
- разделение адаптера модели ответа, управления локальным процессом, сборки контекста, RAG и хранения диалогов;
- проверенная точка подключения MCP без полной интеграции.

Наблюдаемый результат: пользователь в зафиксированном локальном окружении поднимает Gemma своим процессом,
делает ≥3 реальных запроса с проверяемыми свойствами, переключается Local→Network→Local, вручную выгружает и
повторно загружает Gemma; при этом приложение работает независимо от Центра, а фоновые лишние процессы не остаются.

Документ **не является** разрешением реализации; реализация начинается только после отдельного шага PRODUCT/IMPLEMENTATION
(bootstrap-guide шаг 5) и настройки точек запуска (шаг 4, GOVERNANCE).

## 3. Требования (R-*)

### R1. Перенос из week-05 и сохранение возможностей

- R1.1. Стек и архитектурное членение week-05 сохраняются: Python + FastAPI + Pydantic + SQLite; статический HTML/JS UI
  без сборки и без CDN; тесты Pytest. Работающий чат не переписывается с нуля.
- R1.2. Сохраняются диалоговые возможности: создание, переименование, удаление диалогов; лента сообщений; память задачи
  (контекст диалога); увеличивающееся поле ввода; скрываемая правая панель.
- R1.3. Сохраняются инструменты работы со знанием: индексация документов, поиск, фильтрация, query rewrite, вывод
  источников и цитат, сравнение результатов (в объёме, использовавшемся в week-05).
- R1.4. Модуль имеет собственные БД, настройки и диагностику; перенос не переносит пользовательские данные и окружение.
- R1.5. Из week-05 **не копируются**: `.env`/ключи, `.venv`, пользовательская история, индексы, сохранённые прогоны,
  управляющие файлы (bat/MODULE_RULES/MODULE_STATE).
- R1.6. `week-05/**` не изменяется ни при переносе, ни при последующей работе.

### R2. Независимость от Центра

- R2.1. Приложение не использует API, прокси, настройки, каталог моделей, PID-файлы и менеджер процессов Центра.
- R2.2. Приложение не изменяет выбор моделей Центра и не останавливает его процессы (никаких `Stop-Process`,
  mass-kill по имени, глобального unload).
- R2.3. Настройки приложения (base URL, model ID, endpoint, ключ) задаются собственным окружением приложения и **не
  подменяются** переменными `AI_TEST_MODEL_*` Центра/раннера; эти переменные используются только как профиль тестов.
- R2.4. Приёмка локального режима — именно **модель Gemma самого приложения** (не заимствованная/лизинговая модель Центра).
- R2.5. Разрешено читать файл GGUF модели и запускать `llama-server.exe` своим отдельным процессом.
- R2.6. Конфигурация Центра и его `ai-server-model.json` не изменяются.
- R2.7. Приложение обязано работать при выключенном Центре (проверяется на уровне ACCEPTANCE).

### R3. UI и выбор провайдера

- R3.1. Единственный элемент выбора — двухпозиционный переключатель:
  «Локально — Gemma 12B» | «Сеть — DeepSeek». Без списка моделей и без автообнаружения.
- R3.2. Пути задаются отдельными настройками: локальная модель —
  `D:\AI\Models\LLM\Gemma-4-12B-IT\gemma-4-12b-it-qat-q4_0.gguf`; runtime —
  `D:\AI\Runtimes\llama.cpp\b10809\llama-server.exe`; оба настраиваются независимо друг от друга.
- R3.3. Backend приложения и локальный сервер Gemma используют **разные loopback-порты**; порты настраиваются.
- R3.4. Перед запуском проверяются конфликты портов. Занятый порт не даёт права останавливать чужой процесс;
  показывается конкретная ошибка.
- R3.5. DeepSeek — собственная серверная конфигурация приложения (base URL, model ID, ключ). Ключ не берётся из Центра,
  не попадает в браузер и в отчёты; при отсутствии конфигурации сообщаются **конкретные недостающие параметры** без секретов.

### R4. Жизненный цикл Gemma

- R4.1. При выборе локального режима приложение стартует собственный `llama-server.exe` и показывает состояние загрузки.
- R4.2. «Готово» объявляется только после подтверждённого ответа сервера о доступности (готовность по факту, а не по факту запуска процесса).
- R4.3. Повторный выбор того же режима, refresh страницы и вторая вкладка **не создают** лишних процессов.
- R4.4. Переключение на DeepSeek останавливает **только собственный** процесс Gemma.
- R4.5. Кнопка «Выгрузить Gemma» освобождает собственный процесс и память; после выгрузки возможна повторная загрузка.
- R4.6. Свой процесс освобождается при завершении приложения и при неуспешном старте (без «осиротевших» процессов).
- R4.7. Запрещены массовые kill по имени образа, поиск/остановка чужих моделей, глобальный unload.
- R4.8. Переключения сериализуются; защита от потери состояния и от запоздалого ответа, попавшего в чужой диалог.
- R4.9. Состояния провайдера явно различаются: `загрузка`, `готово`, `генерация`, `выгружено`, `ошибка`.
- R4.10. При OOM/ошибке/timeout сообщается причина; приложение не освобождает чужую память и **не переключается скрытно**
  на сетевой режим.

### R5. Режимы RAG / no-RAG и данные

- R5.1. По умолчанию чат работает **без RAG**, с сохранением истории и памяти задачи.
- R5.2. RAG — отдельный включаемый режим с поиском, источниками и проверкой цитат; включение/выключение пользователем.
- R5.3. Без-RAG режим **не приписывает** документальные источники к ответу.
- R5.4. Embedding-модель и модель ответа — разные независимые зависимости.
- R5.5. Переключение Gemma/DeepSeek не перестраивает индекс, пока embedding-конфигурация не изменилась.
- R5.6. История диалога сохраняется при переключении провайдера.
- R5.7. Для каждого ответа сохраняется **фактическая модель ответа** (идентичность модели).

### R6. Архитектурное разделение и MCP

- R6.1. Разделены ответственности: (a) адаптер модели ответа, (b) управление локальным процессом,
  (c) сборка контекста, (d) RAG/retrieval, (e) хранение диалогов. Адаптеры изолированы от бизнес-логики.
- R6.2. Изучается MCP-адаптер и ограниченный цикл вызова инструментов в `week-04/day-16-mcp-agent`; описывается
  **проверенная точка подключения** MCP (см. §9). Полная MCP-интеграция не реализуется.
- R6.3. Архитектура должна допускать совместную работу памяти + RAG + результатов MCP с любой из моделей ответа
  (точка расширения, без реализации полной интеграции).

### R7. Проверка реальной модели

- R7.1. Сначала — **свой** запуск Gemma и один реальный запрос (preflight рабочей конфигурации).
- R7.2. Затем через приложение ≥3 реальных запроса с заранее зафиксированными ожидаемыми свойствами (§8.5):
  факт/арифметика с известным ответом; JSON с заданными полями; рассуждение с проверяемым решением.
- R7.3. Пустой ответ, обрыв, битый JSON, ошибка транспорта — **не успех**.
- R7.4. Сохраняются полные ответы, идентичность модели, параметры, времена, доступные `usage`/`finish_reason`.
  Метрики не выдумываются; ключи и скрытые рассуждения не сохраняются.
- R7.5. Проверяются Local→Network→Local, ручная выгрузка, повторный запуск, отсутствие лишних процессов.
- R7.6. DeepSeek проверяется теми же тремя запросами **при наличии конфигурации**; при её отсутствии фиксируется
  конкретная недостающая конфигурация.
- R7.7. Независимость от Центра проверяется работой при выключенном Центре.
- R7.8. PASS не выводится из моков и не получается через прокси/подмену другой моделью.
- R7.9. Для RAG: регрессия сохранённого retrieval и реальный контрольный вопрос по небольшому проверяемому документу.
- R7.10. Наследованный код не выдаётся за новую приёмку старых сценариев week-05.

### R8. Порядок работ и GOVERNANCE

- R8.1. Bootstrap выполняется штатным генератором; отдельный GOVERNANCE-маршрут нужен для настройки четырёх bat.
- R8.2. После review PLAN `PLAN.md` содержит **точное короткое поручение** для настройки точек запуска со ссылкой на
  утверждённую спецификацию (см. PLAN §6).
- R8.3. **Порядок обязателен и следует из исполняемости через штатные точки входа**: сначала GOVERNANCE-настройка
  четырёх bat, затем preflight Gemma (свой запуск + один реальный запрос) **через настроенные bat**, затем перенос
  и реализация, затем LIVE-проверка. До настройки bat заглушки `CONFIGURE_ME` не позволяют исполнить `setup.bat`,
  `run_app.bat`, `smoke_test.bat`, `test.bat scenario`, поэтому preflight не может предшествовать этому шагу
  (PLAN §1, §2 E1–E2, §6).
- R8.4. Совместная работа памяти + RAG + результатов MCP (R6.3) не отменяет сохранения инструментов индексации/RAG
  из week-05 (R1.3, R5.2). Историческое расхождение с формулировками `MODULE_RULES.md` §2/§18 и `MODULE_STATE.md`
  **уже устранено** отдельным GOVERNANCE-этапом Configurator: защищённые правила теперь закрепляют RAG как отдельный
  включаемый режим, а не вырезают retrieval (PLAN §4.1). Повторная правка защищённых правил для этого не требуется.

## 5. Детальные контракты поведения

### 5.1. Модель ответа (адаптер)

- Единый интерфейс адаптера модели ответа с двумя реализациями: локальная (OpenAI-совместимый endpoint
  `llama-server.exe`) и сетевая (DeepSeek, OpenAI-совместимый endpoint).
- Каждый адаптер сообщает: доступность, идентичность фактической модели, поддерживаемые параметры, результат генерации,
  метрики (`usage`, `finish_reason`, время) при их наличии.
- Ошибки типизированы: недоступность, таймаут, невалидный/битый ответ, превышение контекста, отсутствие конфигурации.
- Сообщения об ошибках не содержат ключей, заголовков и переменных окружения.

### 5.2. Управление локальным процессом

- Единственный владелец процесса `llama-server.exe`: запускает, ждёт готовности, останавливает только свой PID.
- Состояния: `unloaded` → `loading` → `ready` → `generating` → (`unloading`) → `unloaded`; ветвь `error`.
- Идемпотентность: повторный запрос в состоянии `ready`/`loading` не порождает второй процесс.
- Выгрузка и остановка — только по собственному PID/дескриптору процесса, сохранённому при старте.
- Поиск, остановка и «unload» чужих процессов запрещены.

### 5.3. Сборка контекста

- Контекст собирается из: памяти диалога (история задачи) и — только в RAG-режиме — найденных фрагментов документов.
- Без-RAG не добавляет документы и не порождает ссылки на источники.
- Бюджет контекста учитывается; превышение обрабатывается явной ошибкой/усечением, а не молчаливым искажением.

### 5.4. RAG/retrieval

- Сохраняется retrieval week-05 (индексация, поиск, фильтрация, rewrite, цитаты, сравнение).
- Включение RAG активирует поиск по индексу и проверку цитат; выключение возвращает режим no-RAG.
- Embedding-конфигурация независима от модели ответа; при неизменной embedding-конфигурации индекс не перестраивается.

### 5.5. Хранение диалогов

- Диалоги и сообщения — в SQLite приложения; хранится фактическая модель ответа для каждого ассистентского сообщения;
  выбранный провайдер сохраняется как состояние.
- Схема версионируется; неизвестная версия — честный отказ без молчаливого продолжения.
- Тестовые данные изолированы от пользовательской БД.

### 5.6. Переключение и конкурентность

- Переключение провайдера сериализуется (очередь/мьютекс на уровне сервиса).
- Запоздалый ответ генерации, завершившейся после смены диалога/провайдера, не записывается в активный чужой диалог.
- Состояние приложения не теряется при смене режима.

## 6. Состояния и переходы

| Состояние | Условие входа | Разрешённые переходы |
| --- | --- | --- |
| `unloaded` | старт; после выгрузки | `loading` (выбор Local) |
| `loading` | выбран Local, процесс запущен | `ready` (подтверждена доступность), `error` |
| `ready` | сервер отвечает | `generating`, `unloading`, `error` |
| `generating` | идёт запрос к модели | `ready`, `error` |
| `unloading` | нажата «Выгрузить Gemma» / выбран Network | `unloaded` |
| `error` | OOM/таймаут/ошибка старта | `unloaded`, повтор `loading` |

Правила: из `error` возможен явный повтор; скрытый переход в сеть запрещён; `ready` объявляется только по §R4.2.

## 7. Данные

- Хранилище: локальный SQLite (WAL, `foreign_keys=ON`), без Docker/кластера/внешней векторной БД.
- Сущности: провайдер (local/network), диалог, сообщение (роль, текст, фактическая модель, время, метрики при наличии),
  настройки индекса/embedding (наследуемые от retrieval).
- Секреты (ключ DeepSeek) только в `.env`; в БД и UI не хранятся; приложение не печатает их значения.
- Пути к GGUF и runtime — настройки окружения, не пользовательские данные.

## 8. API, UI, проверка

### 8.1. API

- HTTP API (FastAPI) между UI и сервером; граница с UI отделена от сервисов.
- Операции (имена уточняются на реализации, контракт — обязателен):
  - выбор/чтение текущего провайдера (`local`|`network`);
  - текстовая генерация с указанием режима (`rag`|`no_rag`) и контекста диалога;
  - состояние локального процесса (состояние провайдера, причина ошибки без секретов);
  - явная выгрузка Gemma и повторная загрузка;
  - CRUD диалогов и сообщений (перенос из week-05);
  - retrieval-операции (перенос из week-05).
- Ошибки возвращаются структурированно, с категорией и безопасным сообщением.

### 8.2. UI

- Двухпозиционный переключатель провайдера (R3.1); индикация активного режима и состояния локального процесса
  (`загрузка`/`готово`/`генерация`/`выгружено`/`ошибка`).
- Кнопка «Выгрузить Gemma».
- Индикатор ожидания ответа; streaming при поддержке, иначе итоговый ответ.
- Панель RAG-режима (источники/цитаты) только в режиме RAG.
- Диалоги: создание/переименование/удаление, лента, память задачи, увеличивающееся поле ввода, скрываемая правая панель.
- Пользовательский UI — на английском (по `MODULE_RULES.md` §6).

### 8.3. Порты и сеть

- Backend приложения и `llama-server.exe` — на разных loopback-портах, оба настраиваемые.
- Конфликт портов — явная ошибка; чужие процессы не останавливаются.
- Сеть ограничена loopback для локального режима; сетевой режим — только собственный DeepSeek-конфиг приложения.

### 8.4. Хранение фактической модели и метрик

- Для каждого ассистентского сообщения сохраняется идентичность фактической модели и доступные метрики.
- Пустой ответ/битый JSON/ошибка транспорта помечаются как неуспех и не маскируются под валидный ответ.

### 8.5. Зафиксированные проверочные вопросы (LIVE)

Вопросы и ожидаемые свойства фиксируются заранее (детали и ID — `ACCEPTANCE.md` §3). Три обязательных запроса:

1. **Факт/арифметика** с известным заранее ответом.
2. **JSON** с заданными полями (валидный JSON, заданные ключи присутствуют, значения непусты).
3. **Рассуждение** с проверяемым решением (шаги/итог проверяемы, не только форма).

## 9. Точка подключения MCP

Источник: `week-04/day-16-mcp-agent/agent/mcp_adapter.py` (единственный модуль, знающий MCP; транспорт-агностичные
объекты `McpTool`/`McpStatus`/`McpCallResult`, интерфейс `McpClient` с `probe`/`status`/`list_tools`/`call_tool`).

- **Проверенная точка подключения**: узкий порт `McpClient` (Protocol) с операциями probe/status/list_tools/call_tool;
  ошибки — типизированные категории (`unreachable`/`timeout`/`protocol`/`invalid_response`/`tool_error`/`not_configured`),
  сообщения без секретов.
- Точка подключения в D26 описывается как **расширение** сборки контекста: результаты MCP могут добавляться в контекст
  наряду с памятью и RAG-фрагментами (R6.3). Полная интеграция и новый фреймворк не реализуются.
- Проверка ограничивается статическим описанием точки подключения по исходному коду week-04; реальные MCP-вызовы
  в D26 не выполняются.
