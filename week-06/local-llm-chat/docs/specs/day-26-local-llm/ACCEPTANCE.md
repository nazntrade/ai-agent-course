Критерии приёмки спецификации `SPEC.md` и плана `PLAN.md`. Уровни соответствуют `MODULE_RULES.md` §15 и
`.opencode/WORKFLOW.md`. Таблица содержит уникальные ID, уровень, источник (пункт задания/требование) и проверку.

На стадии SPECIFICATION критерии ниже — **проектные**; реальная приёмка выполняется на стадии реализации независимым
Tester. Статическая приёмка самих документов задаётся specification-contract (S01–S03) и не заменяется этой таблицей.

## 1. Шкала уровней

- **UNIT** — логика без сети, изолированные данные.
- **INT** — взаимодействие компонентов и хранения на тестовой БД/stub.
- **LIVE** — ограниченный сценарий против реальной Gemma и (при наличии) DeepSeek.
- **MANUAL** — ручная проверка процессов и жизненного цикла.
- **UI** — проверка интерфейса в браузере.

mock/stub **никогда** не выдаётся за inference и не подтверждает LIVE-контракт (SPEC §11).

## 3. Три фиксированных реальных вопроса (LIVE, D26-09 / D26-10)

Вопросы и ожидаемые свойства зафиксированы **заранее** (до запроса). Формулировки одинаковы для Gemma и DeepSeek.

### Q1. Факт/арифметика с известным ответом

- **Свойства**: ответ содержит заранее вычисленный корректный результат; лишние числа не подменяют его.
- **Ожидаемый итог**: один проверяемый факт/число, совпадающий с известным заранее.

### Q2. JSON с заданными полями

- **Свойства**: ответ — валидный JSON-объект; присутствуют все заданные поля; значения непусты и имеют ожидаемый тип;
  JSON парсится без «починки» вручную. Битый/пустой/невалидный JSON — **не успех**.
- **Ожидаемый итог**: заданные поля на месте, значения соответствуют запросу.

### Q3. Рассуждение с проверяемым решением

- **Свойства**: ответ содержит решение, шаги/итог которого проверяемы; итог не противоречит условию. Оценивается
  **смысл**, а не только форма.
- **Ожидаемый итог**: корректное проверяемое решение.

Общие правила сохранения (R7.4): полные ответы, идентичность модели, параметры, времена, доступные
`usage`/`finish_reason`; метрики не выдумываются; ключи и скрытые рассуждения не сохраняются.

## 4. RAG-контроль (D26-12)

- Зафиксировать небольшой проверяемый документ и вопрос с известным ответом в нём.
- В режиме RAG ответ опирается на найденный фрагмент; цитата/источник указывает на этот документ.
- Регрессия сохранённого retrieval: ранее работающий поиск/фильтрация/цитаты не сломаны переносом.
- В режиме no-RAG этот же вопрос **не** сопровождается документальными источниками (I8).

## 5. Сценарии MANUAL/UI

1. Выбрать Local → наблюдать `загрузка` → `готово`.
2. Выполнить один запрос → наблюдать `генерация` → `готово`.
3. Переключить на Network → убедиться, что процесс Gemma остановлен; сделать запрос к DeepSeek (при конфигурации).
4. Переключить обратно на Local → убедиться в корректном повторном старте.
5. «Выгрузить Gemma» → убедиться в освобождении; снова Local → повторная загрузка и запрос.
6. Проверить отсутствие лишних процессов приложения/осиротевших процессов.
7. Refresh и вторая вкладка в режиме Local не создают второй процесс.

## 6. Ограничения и зависимости приёмки

- Доступность `llama-server.exe`/GGUF и сетевого DeepSeek зависит от учебного окружения; отсутствие конфигурации
  DeepSeek фиксируется как конкретный блокер D26-10, а не обходится моком.
- Приёмка локального режима выполняется именно на Gemma приложения; заимствованные/лизинговые процессы не считаются (I4).
- LIVE-критерии выполняются как ограниченные сценарии при действующей политике LIVE; офлайн-прогоны не закрывают LIVE.
- Итоговую приёмку проводит независимый Tester; Developer собственную реализацию не принимает.
