# PLAN — day-26-local-llm (local-llm-chat)

План реализации спецификации `SPEC.md` (D26). Учебная задача — перенос и расширение чата
`week-05/knowledge-agent`. Документ описывает этапы, карту файлов/компонентов, зависимости, план тестов с ID
требований и отдельный GOVERNANCE-этап настройки bat.

Реализация начинается только после отдельной стадии IMPLEMENTATION (bootstrap-guide шаг 5) и разрешения пользователя.
Настоящий PLAN перечисляет требуемое; точные имена модулей/полей уточняются на реализации, границы компонентов обязательны.

---

## 1. Ключевая последовательность (порядок обязателен)

Порядок отражает требования R7 и R8 и учитывает, что **все проверочные команды исполняются через доверенные bat**:
пока bat не настроены по утверждённому PLAN, preflight нечем запустить.

1. **GOVERNANCE: настройка четырёх bat** (R8) — отдельный маршрут Configurator; без этого шага недоступны
   `setup.bat`, `run_app.bat`, `smoke_test.bat`, `test.bat scenario`.
2. **Preflight локальной модели** — свой запуск `llama-server.exe` и один реальный запрос к Gemma (R7.1)
   **через настроенный bat**.
3. **Перенос ядра чата и retrieval** из week-05 (R1).
4. **Адаптер модели ответа + локальный процесс** (R4, R5.4, R5.5, R5.7).
5. **RAG/no-RAG режимы и хранение** (R5).
6. **API + UI переключатель и выгрузка** (R3, §8).
7. **Точка подключения MCP (описание)** (R6.2).
8. **LIVE-проверка Gemma и DeepSeek** (R7).

Обоснование порядка:
- **GOVERNANCE bat идёт первым**: preflight и проверки выполняются только штатными точками входа
  (`setup.bat`, `run_app.bat`, `smoke_test.bat`, `test.bat scenario`). До их настройки заглушки `CONFIGURE_ME`
  не дают исполнить ни одну проверку, поэтому их нельзя поставить после preflight. GOVERNANCE — отдельный маршрут
  Configurator; Developer защищённые bat не редактирует (R8.1).
- **Preflight Gemma идёт после bat, но до массового переноса**: рискованная внешняя граница (запуск своего сервера
  и реальный ответ) проверяется минимальным реальным preflight, чтобы не строить перенос на неподтверждённой
  интеграции.
- **LIVE-проверка (п.8) идёт последней**: она требует и настроенных bat, и реализованного приложения.

## 2. Этапы (E-*)

### E0. Готовность и предпосылки

- Проверить актуальную готовность стадии SPECIFICATION (bootstrap-guide шаг 3) до записи документов.
- Зафиксировать, что изменяются только `docs/specs/day-26-local-llm/{SPEC,PLAN,ACCEPTANCE}.md` (R8, SPEC §2.3).
- Проверить наличие `llama-server.exe` и GGUF Gemma по настроенным путям; при отсутствии — конкретный блокер без секретов.

### E1 (GOVERNANCE). Настройка четырёх bat

- **Отдельный GOVERNANCE-маршрут** (Configurator): настроить `setup.bat`, `test.bat`, `smoke_test.bat`, `run_app.bat`
  по утверждённому PLAN; убрать заглушки `CONFIGURE_ME`; зарегистрировать пути в корневом `opencode.json` при
  необходимости (R8.1, `MODULE_RULES.md` §16).
- Developer защищённые bat не редактирует; после изменения конфигурации требуется перезапуск/переподключение runtime.
- Проверка: `-Stage Implementation -SpecPath docs/specs/day-26-local-llm` подтверждает готовность файлов, но **не**
  фактический запуск ещё не готового приложения.
- Точное короткое поручение для этого этапа — §6.
- **Почему первым**: до настройки bat заглушки `CONFIGURE_ME` не позволяют выполнить ни `setup.bat`, ни `run_app.bat`,
  ни `smoke_test.bat`, ни `test.bat scenario`, поэтому preflight E2 неисполним без этого этапа.

### E2. Preflight локальной модели (minimal, real)

- Через настроенные bat поднять окружение и запустить собственный процесс `llama-server.exe` с GGUF Gemma
  на loopback-порту приложения (R2.5, R3.2).
- Дождаться подтверждённой доступности (R4.2) и выполнить один реальный запрос (R7.1).
- Проверить: непустой ответ; идентичность модели; время; не-успех на пустом ответе/обрыве (R7.3).
- Убедиться, что процесс только собственный; завершить его (R4.6).
- **Выход этапа**: реальный ответ Gemma получен; зафиксированы конфигурация, параметры и наблюдаемое поведение.

### E3. Перенос из week-05 (без переписывания)

- Перенести рабочее приложение week-05 (D21–D25) в структуру модуля `week-06/local-llm-chat`, сохранив стек и поведение (R1.1).
- Сохранить диалоговые возможности и инструменты знания (R1.2, R1.3).
- Создать собственные БД/настройки/диагностику модуля; **не** копировать `.env`, ключи, `.venv`, историю, индексы,
  сохранённые прогоны, bat/MODULE_RULES/MODULE_STATE (R1.4, R1.5).
- `week-05/**` не изменять (R1.6).

### E4. Адаптер модели ответа и управление локальным процессом

- Единый интерфейс адаптера модели ответа с реализациями local (llama-server) и network (DeepSeek) (SPEC §5.1).
- Менеджер локального процесса: единственный владелец PID; состояния SPEC §6; идемпотентный старт (R4.1–R4.3).
- Освобождение своего процесса при завершении/неуспехе (R4.6); запрет mass-kill/чужих процессов (R4.7).
- Типизированные ошибки без секретов (SPEC §5.1); OOM/timeout с причиной (R4.10).

### E5. Режимы RAG/no-RAG и данные

- Default no-RAG; RAG — отдельный включаемый режим с источниками и проверкой цитат (R5.1, R5.2).
- Без-RAG не приписывает источники (R5.3).
- Embedding и модель ответа независимы; смена модели ответа не перестраивает индекс (R5.4, R5.5).
- История сохраняется при переключении (R5.6); хранится фактическая модель ответа (R5.7).
- Хранение диалогов/сообщений в SQLite; версия схемы; изоляция тестовых данных (SPEC §5.5, §7).

### E6. API и UI

- API-операции по SPEC §8.1; ошибки структурированы.
- UI: двухпозиционный переключатель, индикация состояний, кнопка «Выгрузить Gemma», RAG-панель, перенесённый чат
  (SPEC §8.2). Пользовательский UI — English.

### E7. Точка подключения MCP (только описание)

- Описать проверенную точку подключения по `week-04/day-16-mcp-agent/agent/mcp_adapter.py` (источник: `McpClient`
  Protocol, категории ошибок) (R6.2, SPEC §9).
- Показать точку расширения контекста (память + RAG + MCP) без реализации полной интеграции (R6.3).

### E8. LIVE-проверка реальной Gemma и DeepSeek

- Через приложение выполнить три фиксированных запроса (SPEC §8.5, ACCEPTANCE §3) на локальной Gemma (R7.2).
- Проверить Local→Network→Local, ручную выгрузку, повторный запуск, отсутствие лишних процессов (R7.5).
- DeepSeek — те же три запроса при наличии конфигурации; иначе зафиксировать недостающую конфигурацию без секретов (R7.6).
- Проверить работу при выключенном Центре (R7.7).
- Сохранить полные ответы, идентичность модели, параметры, времена, доступные `usage`/`finish_reason` (R7.4).
- RAG: регрессия сохранённого retrieval и реальный контрольный вопрос по небольшому документу (R7.9).

### 4.1. Соответствие защищённых правил модуля (устранено GOVERNANCE)

Историческое контрактное противоречие между защищёнными файлами модуля и заданием D26 **уже устранено отдельным
GOVERNANCE-этапом** Configurator; на момент текущей подготовки SPECIFICATION расхождения нет:

- Ранее `MODULE_RULES.md` §2 и §18 и `MODULE_STATE.md` («Решения») заявляли, что RAG и индексация документов из
  `week-05/knowledge-agent` **не переносятся** — это противоречило заданию D26 (п.1 и п.5), требующему **сохранить**
  инструменты индексации/RAG как отдельный включаемый режим (`SPEC.md` R1.3, R5.2).
- GOVERNANCE-правка выполнена: теперь `MODULE_RULES.md` §2 и §18 и `MODULE_STATE.md` («Решения») фиксируют, что
  инструменты индексации, поиска, фильтрации, query rewrite, источников и цитат **переносятся и сохраняются как
  отдельный включаемый RAG-режим** (по умолчанию — без RAG); формулировки не вырезают retrieval и согласуются с
  заданием D26 и `SPEC.md` R1.3/R5.1/R5.2.

Следствия:

1. **Действующей остаётся формулировка задания** (и согласованный `SPEC.md` R1.3/R5.2): retrieval не вырезается.
2. Оба защищённых файла уже приведены в соответствие; **повторный GOVERNANCE-этап правки `MODULE_RULES.md`/`MODULE_STATE.md`
   не требуется** и не планируется.
3. **В этой PRODUCT-задаче** `MODULE_RULES.md` и `MODULE_STATE.md` не изменяются (они уже корректны); Developer
   защищённые файлы не редактирует.
4. Реализация (E5) следует `SPEC.md`; блокирующего расхождения правил нет.

## 7. Риски и обработка

- **Локальный runtime недоступен** (нет GGUF/`llama-server.exe`) → E0/E2 фиксируют конкретный блокер; реализации без
  способа проверки не выполняется.
- **OOM при загрузке 12B** → явная причина, выгрузка, повтор; скрытый переход в сеть запрещён (I7).
- **Занятый порт** → явная ошибка, без остановки чужого процесса (R3.4).
- **Нет конфигурации DeepSeek** → D26-10 фиксирует недостающие параметры; полная приёмка не закрывается на выдуманных данных.
- **Заимствованные процессы/лизинг Центра** → не использовать для приёмки Gemma (R2.4, I4).
