# Правила модуля `private-llm-service`

Модуль наследует AGENTS.md, PROJECT_RULES.md, конфигурацию и пять ролей курсового корня. Этот файл содержит только факты и дельту нового учебного модуля.

## 1. Цель модуля

День 30: отдельный лёгкий Android-клиент и приватный HTTP-сервис выбранной локальной языковой модели. Сервис хранит беседы, обслуживает несколько клиентов через ограниченную очередь и контролирует скорость запросов и точный размер контекста.

## 2. Границы и не-цели

Включены APK, создание/переименование/удаление бесед, история, потоковый ответ или честное ожидание, отмена, восстановление соединения, изоляция владельцев, локальный доступ и защищённый внешний маршрут, воспроизводимая сборка и демонстрация. Не включены RAG, голос, изображения, выполнение команд модели, публичная регистрация, несколько генераторов или облачная замена. Существующие модули, данные и прошлые отчёты сохраняются.

## 3. Стек и версии

Для этого нового модуля выбран минимальный учебный стек, а не обязательная миграция других модулей или включение полного мобильного профиля каталога.

- Gateway: Python 3.11 или совместимая более новая установленная версия; FastAPI, Pydantic 2, httpx, стандартный sqlite3; Pytest для автономных тестов. Один процесс и один worker генерации. SQLite с версионированными SQL-миграциями — допустимое локальное учебное хранилище. Отдельные ORM, PostgreSQL и брокер задач не требуются.
- Android: Kotlin, XML Views, Coroutines/Flow, ViewModel, OkHttp, локальный кэш и Android Keystore; один app-модуль и явная передача небольшого набора зависимостей. XML и ручная передача зависимостей выбраны для малого учебного APK; полный профиль Android Native с Compose/Hilt здесь не выбран. Room допускается при полезности для устойчивого кэша, без второго источника истины.
- Сборка Android: JDK 17, минимальный Android API 26 как исходный совместимый предел. Точные Kotlin/Gradle/AGP/SDK и версии библиотек определяются статическим аудитом доступного toolchain и фиксируются в утверждённом PLAN и build/lock-файлах до сборки; произвольные «latest» недопустимы.
- Контракт HTTP: OpenAPI 3.1 в репозитории; обычные клиентские DTO/API генерируются из контракта. SSE parser и восстановление потока реализуются отдельно с явной схемой событий.

## 4. Структура модуля

`gateway/app` — сервис; `gateway/tests` — независимые от реального провайдера проверки; `android` — приложение; `docs/specs/d30-private-llm` — SPEC/PLAN/ACCEPTANCE; `docs/operations` — воспроизводимые инструкции; `harness` — доверенные тестовые сценарии. Сгенерированный bootstrap и фиксированная scenario-ветка test.bat сохраняются.

## 5. Общие правила модуля

Модуль развивается на месте. Копии и архивы существующих учебных модулей не создаются. Корневые правила, роли и permissions не переопределяются. Публичные материалы содержат нейтральные примеры без персональных путей, адресов, оборудования, названий и архитектуры частной инфраструктуры.

## 6. Документация модуля

Один постоянный README.md с названием «Приватный LLM-чат». День 30 добавляется отдельным разделом. README и отчёты пишутся по-русски; UI и технические имена — по-английски. Спецификация самодостаточна; локальные приватные сведения хранятся вне публичного репозитория.

## 7. Запуск и интерфейс

Сохраняются доверенные setup.bat, test.bat, smoke_test.bat, run_app.bat. До независимого review PLAN допустимы исходные CONFIGURE_ME; команды настраивает Configurator после review. UI показывает ожидание, очередь, terminal outcome, частичный ответ, усечение истории/ответа и восстанавливает состояние по серверу.

## 8. Команды

Команды выполняются из каталога модуля. setup.bat подготавливает зависимое окружение; test.bat запускает автономные тесты и сохраняет `scenario <slug>`; smoke_test.bat проверяет готовность; run_app.bat запускает сервис с понятной ошибкой конфигурации. Код 0 означает успех, 1 ошибку, 2 ненастроенный режим. Точный состав аргументов и build-режимов закрепляется в проверенном PLAN перед настройкой команд.

## 9. Окружение и секреты

Профиль выбранной модели передаётся через AI_TEST_MODEL_* и разрешение LIVE через AI_TEST_LIVE_POLICY; содержимое credentials не выводится. APP_BIND_HOST, APP_PORT, APP_DATA_DIR и отдельные переменные лимитов задают конфигурацию gateway; точная схема закрепляется SPEC и .env.example. Пустой профиль требует явной настройки, частичный отвергается. Токен устройства не равен ключу провайдера; ключ провайдера не попадает в APK. Примеры используют заглушки.

## 10. Данные и миграции

SQLite gateway — источник истины для владельцев, устройств, бесед, сообщений и jobs. Миграции версионируются; история сохраняется независимо от snapshot контекста. После рестарта незавершённые jobs получают честный terminal error, без автоматического повторного inference. Тесты используют изолированные временные данные. Базы, токены, keystore, веса и личные беседы исключаются из кода и архивов.

## 11. API и сеть

Версионированный /v1 API включает status, операции бесед и истории, admission jobs, lookup по id/key, cancel, snapshot и SSE. Ownership выводится из аутентификации; клиент не задаёт владельца, модель, upstream URL или системный prompt. Внешний маршрут использует HTTPS с корректной проверкой сертификата; локальный HTTP разрешается только явно для локального маршрута. Административный интерфейс провайдера наружу не раскрывается.

## 12. UI/UX

Три экрана: Conversations, Chat, Settings. Английские строки в ресурсах. Новая беседа, rename, delete с подтверждением, отправка, Stop, pending/queued/loading/running/error/completed и восстановление после поворота/перезапуска. Настройки сохраняют выбранный gateway и защищённый токен устройства. Серверный partial snapshot заменяет локальный текст при reset, предотвращая дублирование.

## 13. Дисциплина тестирования

UNIT/INT не читают настоящий .env и не используют реальный ключ; провайдер изолируется fake. LIVE и устройство — отдельные уровни по корневому регламенту. Моки проверяют scheduler и отказные ветки, но не реальный tokenizer, модель, LAN, внешний маршрут или установку APK. Проверяются границы, повторность, отмена и гонки, без ослабления критериев.

## 14. Definition of Done

Все обязательные требования и критерии текущего SPEC имеют независимые достаточные доказательства; выбранная модель фактически отвечает, APK собран и установлен, два клиента обслужены, лимиты измерены, данные и секреты защищены, воспроизводимые инструкции/код/видео подготовлены. Непройденный обязательный внешний или аппаратный критерий остаётся явным BLOCKED/NOT_ASSESSED и не заменяется статусом полной готовности.

## 15. Уровни тестирования

Статические проверки доказывают каркас и спецификацию. UNIT/INT доказывают состояние, persistence, ownership и scheduler с изолированным провайдером. LIVE доказывает выбранную модель, template/token count, lifecycle и streaming. Android UI доказывает операции на приложении; NETWORK доказывает фактические маршруты. Видео и архив проверяются по содержимому и актуальному состоянию.

## 16. Регистрация в корневой конфигурации

Модуль наследует существующие разрешения курсового корня на вложенные {setup,test,smoke_test,run_app}.bat. Configurator имеет точечный ask для MODULE_RULES/MODULE_STATE и точек запуска; Developer не редактирует эти файлы; Developer/Tester имеют разрешение запускать доверенные bat. Новых разрешений и собственной конфигурации модуля не требуется. Bootstrap независимо проверяет фактическое наследование.

## 17. Что нельзя менять

Служебные правила, состояние, bootstrap, роли и точки запуска изменяются только в предусмотренном корнем Configurator-маршруте. Продуктовые файлы создаются после готовности и независимого review SPEC/PLAN/ACCEPTANCE. Старые модули и приватный профиль модели не изменяются этим bootstrap. Commit, push и публикация не выполняются.

## 18. Известные ограничения

Текущий этап — bootstrap и подготовка к спецификации. Продуктовый код, SPEC, окончательные версии toolchain и фактические LIVE/Android/NETWORK доказательства ещё отсутствуют. Однопроцессная очередь и SQLite — учебный предел; увеличение процессов требует другой архитектуры. Внешний маршрут и настоящее устройство проверяются в рамках реализации, без выдуманного PASS.

## Универсальный процесс и приёмка

Применяются AGENTS.md и .opencode/WORKFLOW.md курсового корня. Подробные процедуры, LIVE policy, contract/evidence и независимые оценки не дублируются. Готовность bootstrap не доказывает готовность продукта.
