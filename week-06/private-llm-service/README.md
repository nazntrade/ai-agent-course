# Приватный LLM-чат

## День 30 — собственный HTTP-сервис локальной модели

Сервис хранит беседы и историю в SQLite, а задания выполняет один worker через ограниченную FIFO-очередь. Клиент получает полный авторитетный snapshot и поток SSE; повтор запроса с прежним ключом не создаёт вторую генерацию. Ответ локальной модели действительно читается потоково. Частичный ответ ошибочного или отменённого задания не попадает в следующий контекст.

Серверная часть — Python 3.12, FastAPI, Pydantic, httpx и стандартный sqlite3. Один процесс, один worker; второй процесс с той же рабочей БД запрещает process lock. Android — Kotlin/XML с тремя экранами Conversations, Chat и Settings. Беседы, история, черновики и точный payload ожидающего запроса сохраняются локально; device token защищён Android Keystore. Фактические результаты проверок и ограничения приёмки находятся в `docs/artifacts`; наличие сборки не подтверждает внешний маршрут.

### Подготовка и проверки

Из каталога этого модуля:

```text
setup.bat
test.bat unit
test.bat integration
smoke_test.bat
test.bat scenario queue-rate-context
```

Setup устанавливает только зафиксированные зависимости с SHA256 из `requirements.lock`. Повторная установка не меняет версии. UNIT/INT используют временную БД и fake provider, удаляют выбранный реальный profile из дочерней среды и не запускают модель. Smoke экспортирует `docs/api/openapi.json` версии 3.1 из фактических HTTP-моделей, используя отдельную временную БД.

### Запуск

Сервер чата запускается только явно вручную: именованным профилем Центра или доверенным `run_app.bat`. Запуск самой панели не запускает gateway или модель. Автозапуска, scheduled task, Windows service и startup hook нет. Автоматизацию можно добавить только по отдельному будущему запросу владельца.

```text
run_app.bat stub
run_app.bat local
run_app.bat network
```

Stub — изолированная демонстрация без модели. Local — loopback; network — явный сетевой bind. При полном разрешённом profile network запускает gateway в том же процессе. При отсутствии всех model fields он требует явный исключённый из Git `.runtime/center-test-selection.json` и уже запущенный Центр, затем вызывает только именованный `private-llm-service` profile. Центр передаёт настоящие credentials своему child; внешний launcher их не получает. Partial profile и forbidden/неизвестный policy отклоняются до сетевых запросов.

Launcher ожидает health readiness конкретного запуска. Ctrl+C завершает только собственный run ID штатным stop; уже работающий профиль сохраняется без присвоения ownership. Недоступный Центр означает ошибку: сначала вручную запустите AI-SERVER. Обычный старт не загружает модель: первая принятая работа выполняет cold acquire. HTTP health при этом доступен раньше загрузки модели. Health checks, reconnect и replay старого задания не создают новую генерацию.

Устройство использует URL gateway и собственный device token. Ключ провайдера и адрес управления моделью не передаются Android. Доступ из другой сети требует отдельно настроенного HTTPS с проверяемым сертификатом. Доступ эмулятора к хосту не доказывает внешний маршрут.

### Локальное устройство

Административного HTTP API нет. Инструкции [provisioning](docs/operations/provisioning.md) описывают доверенные `device-provision` и `device-revoke` scenarios. Одноразовый pairing payload защищён Windows DPAPI текущего пользователя и ограниченным ACL; token никогда не выводится в журнал. Срок неиспользованного pairing — 15 минут. На сервере остаётся только SHA256 token hash.

Обычная установка на имеющийся эмулятор выполняется явно сценарием `test.bat scenario android-normal-setup` с собственным строгим ignored request. Он требует уже вручную запущенный сервис и выбранное ожидающее устройство, нажимает настоящую Save в Settings, проверяет `/v1/me`, удаляет helper и повторно открывает обычный APK. Точные поля и порядок приведены в provisioning. Существующая настройка обычного APK сохраняется.

Изолированные Android проверки используют отдельный package suffix `.e2e`, собственную TEMP БД/устройство и явно выбранный Center test profile. Тестовый loopback relay создаёт ограниченные транспортные ошибки только для UI regression; эти контролируемые ответы не подтверждают реальную квоту или стабильность модели. Normal APK и normal gateway не содержат relay или тестового listener.

### Ограничения и поведение

- FIFO: 8 ожидающих заданий, не больше 2 ожидающих заданий владельца, одна активная генерация.
- Token bucket: burst 2, пополнение 5/min; 429 содержит Retry-After. Повтор старого idempotency key не тратит новую quota.
- Тело HTTP: максимум 128 KiB фактических bytes, текст 32000 chars, заголовок беседы 80 chars, page максимум 100.
- Точный prompt: не более 6144 tokens и фактической вместимости slot минус 1024 output и 512 safety. Удаляются старейшие завершённые пары только из prompt; история не удаляется.
- Отмена и удаление побеждают поздний ответ. Перезапуск превращает незавершённые задания в failed `service_restarted`; автоматического повторного inference нет.
- SSE snapshots заменяют весь partial content; `state_version` и cursor предотвращают повтор текста. Revocation проверяется в потоке; heartbeat каждые 10 s, максимум 3 подключения устройства.

Для запуска с несколькими процессами или общим публичным доступом нужна другая архитектура. Базы, pairing payload, keys и личная история исключены из Git. APK, внешняя сеть, стабильность настоящей модели и демонстрационное видео проверяются отдельно до полной сдачи.
