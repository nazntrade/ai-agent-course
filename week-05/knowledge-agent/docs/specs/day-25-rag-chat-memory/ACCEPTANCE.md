## 1. Легенда уровней и правило «mock/stub ≠ LIVE»

Каноническая шкала уровней: **UNIT / INT / LIVE / MANUAL / UI**.

| Уровень | Что подтверждает | Изоляция |
| --- | --- | --- |
| **UNIT** | Логика ядра на моках/fake, без сети и `.env` | `test.bat unit` |
| **INT** | Реальные процессы сервиса + HTTP loopback + `harness/embed_stub.py` и `harness/chat_stub.py` (без внешней сети); фактический перезапуск приложения | `test.bat integration`, `smoke_test.bat` |
| **LIVE** | Реальный retrieval через embedding и генерация выбранной реальной моделью в двух сценариях | `test.bat scenario d25-scenario-a` / `-b`; `MODEL_CHECK_KIND: LOCAL` для local / `NETWORK` для remote |
| **UI** | Фактическая проверка интерфейса в браузере | браузер через `run_app.bat` |
| **MANUAL** | Ручной прогон/инспекция Developer и Tester | вручную |

**Правило:** mock/stub/fake **никогда** не маркируется как inference и не выдаётся за LIVE.
Unit-тест с fake/stub подтверждает логику, но не реальный контракт провайдера, не переживание
перезапуска и не качество ответов на реальном корпусе.

### 1.1. Среда и LIVE-политика (нормативно)

* `AI_TEST_LIVE_POLICY=allowed` (явный выбор пользователя). Выбранная модель приложения:
  актуальный выбранный профиль Центра (local или remote). Embeddings — независимый прежний
  `embeddinggemma:300m`. `MODEL_CHECK_KIND: LOCAL` для local / `NETWORK` для remote; при реальном запуске локальной модели
  выводятся `LOCAL_MODEL_START`/`LOCAL_MODEL_INFERENCE`/`LOCAL_SCENARIO_TEST`.
* `harness/scenario_runner.py` требует ровно `allowed` и полный `AI_TEST_MODEL_*`; иначе
  `BLOCKED`, реальные вызовы `NOT_RUN`, без fallback. `forbidden`/невалидная policy →
  offline-часть выполняется, LIVE фиксируется `BLOCKED`/`PARTIAL`, mock не выдаётся за PASS.
* Lease acquire/use/release в `finally`; чужая/заимствованная модель не выгружается.
* Tavily в окружении включён, но D25 не добавляет веб-функцию: используются только реальный
  локальный корпус и выбранная модель; секреты/base URL/lease ID не публикуются.

### 1.2. Провайдерская граница

Разработчик моделирует реальные граничные ответы (`finish_reason`, `usage`, пустой ответ,
обрыв, ошибка/таймаут) постоянными regression-тестами. Критерий, зависящий от фактического
поведения внешней границы, считается проверенным на достаточном уровне только после
LIVE-проверки Tester-ом на выбранной реальной модели.

| Обязательная часть (цель/условия) не помещается в бюджет | `context_overflow` до вызова модели; цель не отброшена молча | UNIT |
| Пустой/усечённый/невалидный ответ | не `ok`; видимая ошибка; не засчитывается как успех | UNIT + INT |
| Ошибка/таймаут провайдера | типизированная ошибка, видимая; не маскируется под «не знаю» | UNIT + INT + LIVE |
| Перезапуск приложения | история/память сохранены; диалоги изолированы | INT + UI |
| Смена активного индекса | старый ход показывает свои сохранённые источники | INT |
| Неизвестная версия схемы разговоров | `conversation_store_schema_unsupported`; без молчаливого продолжения | UNIT/INT |
| Миграция на существующих данных | `chat-run-v1` не превращаются в диалоги; индекс не изменён | INT |
| Межчатовая изоляция в сценариях | данные сценария A не появляются в сценарии B | LIVE |
| Регрессия D21–D24 | существующие UNIT/INT/smoke зелёные; `chat*`/`index*`/`search` не изменены | UNIT + INT |

Примеры успешных ответов и «счастливого пути» не заменяют эти граничные и противоречивые
сценарии.

## 5. Раздельная оценка качества (D25-23)

Оцениваются независимо:

1. **Retrieval/источники** — относится ли `sources` к `passed`; совпадают ли `source`/`section`
   с `metadata`; выполняется ли новый retrieval на каждом ходу.
2. **Разрешение ссылок** — корректно ли `search_query` отражает отсылку; сохранён ли
   `original_query`; не выдана ли неоднозначность за ответ.
3. **Память задачи** — удержана ли цель; соблюдены ли активные условия; точечно ли меняется
   условие; есть ли основания.
4. **Ответ и цитаты** — формальные проверки D24 (`source_exists`/`quote_verbatim`), отсутствие
   выдуманных цитат; смысловая поддержка оценивается вручную.
5. **Отказы и ошибки** — обоснованы ли отказы при слабом контексте/вопрос вне корпуса;
   отделены ли технические ошибки; не выданы ли за содержательный успех.

Явно фиксируется: непустой ответ, существующий `chunk_id` и успешная команда сами по себе не
доказывают качество; `grounding.status="verified"` доказывает только формальные проверки.
Независимая оценка сохраняется в `local-data/d25/quality-assessment.md` Tester-ом; отказ на
всех вопросах не объявляется улучшением.

## 6. Измерения LIVE

При реальном прогоне измеряются и указываются:
