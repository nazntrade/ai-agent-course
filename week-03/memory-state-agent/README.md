- Миграции схемы SQLite: идемпотентное добавление колонок и таблиц без потери данных.

Полное описание Дней 6–10 приведено в `week-02/first-agent/README.md`; новый проект сохраняет эти функции и тесты (все проверки адаптированы под английские подписи).

## День 11. Модель памяти агента

### Задача

Реализовать три раздельных слоя памяти:

- Short-Term Memory — история текущего диалога;
- Working Memory — состояние текущей задачи, чата и линии;
- Long-Term Memory — явно сохранённые знания, доступные между чатами.

Пользователь должен контролировать, какие данные сохраняются и передаются модели.

### Что реализовано

- три слоя памяти;
- добавление, редактирование и удаление записей;
- Include для включения записи в контекст;
- Promote для переноса Working Memory в Long-Term Memory;
- изоляцию Working Memory между чатами и ветками;
- общую Long-Term Memory;
- сохранение после перезапуска;
- System Prompt и Invariants, которые не являются памятью;
- сжатие длинной истории.

### Как это работает

| Механизм | Назначение |
|---|---|
| Short-Term Memory | История текущего диалога |
| Working Memory | Состояние текущей задачи |
| Long-Term Memory | Общие знания между чатами |
| Include | Передача выбранной записи модели |
| Promote | Перенос рабочего знания в долгосрочное |
| System Prompt | Роль и стиль поведения агента |
| Invariants | Постоянные правила и ограничения |

Перед каждым запросом приложение формирует контекст из System Prompt, Invariants, включённых записей Working Memory и Long-Term Memory, истории текущего диалога и нового сообщения пользователя.

### Трудности

- после переноса основы предыдущего учебного проекта обнаружились конфликты унаследованных permissions;
- общие и ролевые permissions были разделены;
- для тестовых точек входа добавлены точные разрешения;
- после исправлений проведена полноценная приёмка памяти.

### Проверка

- 371 автоматический тест — PASS;
- smoke_test.bat — PASS;
- health-check и корневая страница — PASS;
- Short-Term Memory — PASS;
- изоляция Working Memory — PASS;
- Long-Term Memory между чатами — PASS;
- Include — PASS;
- Promote — PASS;
- Edit и Forget — PASS;
- сохранение после перезапуска — PASS.

### Итог

Создан агент с явно управляемой памятью. Приложение определяет область действия, хранение и передачу данных модели, а пользователь контролирует сохранение, включение, перенос и удаление записей. Решение демонстрирует базовый подход к управлению памятью AI-агента и может переиспользоваться в других проектах.

## День 11 — explicit Memory Layers

### Три слоя и их области

| Слой | Что хранит | Область действия | Где хранится |
|---|---|---|---|
| **Short-term** | историю активного чата и активной ветки | активная линия | `messages` (`branch_id`) |
| **Working** | структурированные данные текущей задачи | чат + конкретная ветка (`NULL` = основная линия) | таблица `working_memory` |
| **Long-term** | устойчивые предпочтения, решения и знания | глобально, между всеми чатами | таблица `long_term_memory` |

Слои хранятся раздельно: элементы Working и Long-term не смешиваются с перепиской и не влияют на неё. Слои пишутся в SQLite и переживают перезапуск.

**Invariants и System Prompt не являются памятью.** Это отдельные настройки чата, они не становятся элементами слоёв и учитываются в статистике токенов отдельно.

### Явные операции

- **Add** — добавить элемент в Working или Long-term.
- **Edit** — изменить ключ и значение элемента.
- **Promote** — перенести элемент из Working в Long-term (операция «move»: исходный элемент удаляется, а не дублируется).
- **Forget** — окончательно удалить элемент из слоя.
- **Include in prompt** — чекбокс: включён ли элемент в блок, который уходит модели. Исключённые элементы видны в интерфейсе, но не попадают в запрос.

Операции выполняются **вручную**. Автоматических записей в слои памяти нет: ни одна стратегия контекста не создаёт и не меняет элементы памяти, автоподсказок и автоматического сохранения нет. RAG не используется.

Ветка не наследует Working основной линии: у новой ветки свой пустой Working-слой, который заполняется вручную. Long-term при этом остаётся общим.

### Как слои попадают в запрос

Блоки вставляются в payload **любой** стратегии сразу после system prompt в порядке:

1. инварианты (если заданы);
2. Working-память активной линии;
3. Long-term-память.

Каждый блок — отдельное `system`-сообщение. Если память пуста и инварианты не заданы, payload полностью совпадает с payload Дней 9–10 — поведение прежних стратегий не меняется. Демо-лимит контекста считается по финальному payload, поэтому включённые элементы памяти и инварианты участвуют в предпроверке переполнения.

### Ветвление

Short-term и Working расходятся по ветке, Long-term остаётся общим:

- история у каждой ветки своя (как и раньше);
- Working-элементы принадлежат конкретной линии: `NULL` — основная линия, иначе id ветки; sibling-ветки не видят элементы друг друга;
- Long-term виден из любого чата и любой ветки и переживает удаление чата или ветки.

Удаление ветки удаляет только её Working-элементы; удаление чата каскадно удаляет его Working; Long-term не затрагивается.

### Интерфейс слоёв

В основной области под историей чата есть секция **Memory layers** с четырьмя раскрывающимися панелями:

- **Short-term memory · current line** — активная линия, число сообщений и приблизительный размер её истории в токенах, компактная таблица сообщений.
- **Working memory · this chat & line** — область (чат и линия), приблизительный вклад слоя в prompt tokens, число включённых из общего числа элементов, чекбоксы `Include`, кнопки `Promote`/`Edit`/`Forget` и форма `Add`.
- **Long-term memory · shared across chats** — то же без `Promote`; пометка, что слой общий для всех чатов.
- **System prompt & invariants (not memory)** — отдельные оценки токенов и текст system prompt и инвариантов; здесь ничего не хранится как память.

Приблизительный вклад слоя в prompt tokens считается той же локальной эвристикой (`tokens.estimate_tokens`) и тем же форматированием блока, что и реальный payload; значение помечается `≈`. Оценка токенов — не токенизатор.

## System prompt и Invariants

System prompt задаётся в `Chat settings`. Рядом добавлено поле **Invariants** — правила, которые модель должна соблюдать всегда; они отправляются отдельным system-блоком и показаны отдельно от памяти. Инварианты хранятся в колонке `chats.invariants` и переживают перезапуск. Пустые инварианты не влияют на payload.

Изменение инвариантов (как и прочих настроек) сохраняется в SQLite и не вызывает платных вызовов модели.

## Хранение

Хранение по-прежнему отделено от интерфейса (`storage.py`, в `app.py` нет SQL). Схема Week 2 дополнена:

- `chats.invariants` — текст инвариантов (миграция добавляет колонку идемпотентно, у старых строк значение пустое);
- `working_memory` — `chat_id`, `branch_id` (`NULL` = основная линия), `item_key`, `value`, `included`, время; уникальность ключа в пределах линии обеспечивается двумя частичными уникальными индексами (отдельно для основной линии и для веток);
- `long_term_memory` — `item_key`, `value`, `included`, время; уникальный индекс по ключу, глобальная область.

Миграция совместима с базой финальной Week 2: старые таблицы и строки не изменяются, новые таблицы создаются при первом открытии, повторное открытие идемпотентно. Для чатов, перенесённых из Week 2, авто-заголовок по первой реплике работает и со старым значением `"Новый чат"`, и с новым `"New chat"`; пользовательский заголовок не перезаписывается.

## Иконки чатов в сайдбаре

В строке каждого чата — кнопки-иконки: карандаш (`Rename chat`) и корзинка (`Delete chat`). Иконка имеет по 4 пикселя внутренних отступа слева и справа до края кнопки, а ширина кнопки задаётся её содержимым (`width="content"`), поэтому при сворачивании и разворачивании боковой панели ширина кнопки не меняется. Удаление по-прежнему требует подтверждения.

## День 12. Персонализация ассистента

### Задача

Добавить поверх модели памяти персонализацию: профиль пользователя, который автоматически подключается к каждому обычному запросу, чтобы один и тот же вопрос получал разные ответы для разных профилей.

### Что реализовано

- отдельная сущность `UserProfile` (не элемент памяти): `id`, `name`, `addressing`, `style`, `format`, `constraints`, `domain_context`, время создания и обновления;
- хранение профилей в SQLite и восстановление после перезапуска;
- активный профиль назначается **отдельно для каждого чата**;
- создание, просмотр, редактирование, клонирование, удаление, выбор активного профиля, состояние `No profile`, preview блока и оценка его токенов;
- два обычных редактируемых демо-профиля `Concise engineer` и `Detailed tutor` — не жёстко зашитые исключения в логике запроса;
- секция **User profiles** в интерфейсе и постоянная строка активного профиля в сайдбаре;
- чистая точка расширения `ChatAgent._resolve_active_profile` — единственное место выбора профиля и место для будущего router/resolver;
- иконки чатов в сайдбаре прижаты к правому краю одной группой с фиксированным зазором, поэтому расстояние до правого края не меняется при расширении и сужении сайдбара.

### Поля профиля

Профиль описывает, **как** отвечать конкретному пользователю, а не что агент знает или помнит. Профиль можно создать, изменить, клонировать и удалить в разделе **User profiles**; активный профиль выбирается отдельно для каждого чата и автоматически участвует в каждом следующем запросе этого чата.

| Поле | Что задаёт |
|---|---|
| **Name** (`name`) | имя профиля; обязательное, дубликаты имён отклоняются (сравнение без учёта регистра и лишних пробелов) |
| **Addressing** (`addressing`) | как обращаться к пользователю |
| **Style** (`style`) | стиль ответа |
| **Format** (`format`) | формат ответа |
| **Constraints** (`constraints`) | ограничения, которые модель должна соблюдать в ответе |
| **Domain context** (`domain_context`) | предметный контекст пользователя |

`id`, `created_at` и `updated_at` — служебные поля: они не редактируются и не показываются в блоке. В profile-блок уходят только непустые поля, а профиль без имени в запрос не добавляется.

### Как профиль отличается от памяти

| Сущность | Отвечает на вопрос | Область |
|---|---|---|
| Short-term / Working / Long-term memory | «Что агент знает и помнит?» | история, задача, знания |
| **User profile** | «Как отвечать именно этому пользователю?» | обращение, стиль, формат, ограничения |
| System prompt | «Какая у модели общая роль?» | настройка чата |
| Invariants | «Что обязательно соблюдать всегда?» | настройка чата; выше профиля |

Профиль не становится элементом ни одного слоя памяти, не входит в `AgentConfig`, поэтому смена настроек чата не перезаписывает активный профиль. При конфликте профильных ограничений с инвариантами побеждают инварианты.

### Как собирается запрос к модели

При каждом пользовательском сообщении приложение формирует запрос из нескольких независимых слоёв. В `messages` они идут в таком порядке:

1. **system prompt** — общая роль модели (настройка чата);
2. **активный пользовательский профиль** — ровно один блок, если профиль выбран;
3. **invariants** — постоянные правила чата, если заданы;
4. **working memory** — только элементы активной линии с включённым `Include`;
5. **long-term memory** — только общие элементы с включённым `Include`;
6. **история разговора** — та её часть, которую выбирает стратегия контекста;
7. **текущее сообщение пользователя**.

Профиль добавляется только к основному запросу. Внутренние служебные вызовы (сводка, извлечение sticky facts, оценка токенов и статистика) его не получают, чтобы стиль пользователя не ломал структурированные операции. При `No profile` и пустых блоках payload полностью совпадает с Днём 11.

Приоритет инвариантов зафиксирован детерминированно: заголовок profile-блока прямо сообщает модели, что инварианты выше профиля и не могут быть им отменены, а блок инвариантов всегда идёт после профиля.

**Важно:** в запрос уходит не «вся информация всегда». Какую часть истории увидит модель, определяет выбранная стратегия контекста, а какие элементы памяти — флаг `Include`: элемент с выключенным `Include` остаётся в интерфейсе и в базе, но в запрос не попадает. System prompt, инварианты и профиль — это настройки, а не память.

Схема одного пользовательского хода:

```text
Пользовательское сообщение
→ System prompt
→ Active profile (если выбран)
→ Invariants (если заданы)
→ Included working / long-term memory
→ History selected by the context strategy
→ DeepSeek API
→ Streaming response
→ Сохранение завершённого ответа и статистики
```

### Стратегии контекста

Стратегия выбирается в `Chat settings` и влияет только на то, какая часть истории уходит в очередной запрос. Полная переписка при этом всегда хранится в SQLite и показывается в чате.

| Стратегия | Что уходит модели | Зачем |
|---|---|---|
| **Full history** | вся история активной линии без сжатия | нужен полный контекст без потерь |
| **Window** (`Sliding window`) | только последние N сообщений плюс текущий запрос | ограничить размер запроса в длинном диалоге |
| **Summary / compression** | накопительная сводка старых ходов плюс несколько последних ходов без сжатия | сжать длинную историю, чтобы уложиться в контекст и снизить стоимость |

Дополнительно доступны `Sticky Facts (fact memory)` и `Branching`; их устройство описано в разделах Дней 10–11 и в `week-02/first-agent/README.md`.

### Режимы интерфейса

- **Chat** — обычное общение: история сообщений, поле ввода и выбор активного профиля с кнопкой `Manage profiles`; технических панелей здесь нет.
- **Diagnostics / Memory** — просмотр и управление памятью, профилями, сжатием, ветками и статистикой.

Поле ввода и выбор активного профиля находятся в режиме `Chat`. Подробнее — в разделе «Разделение интерфейса Chat и Diagnostics».

### Проверенное поведение

- **Потоковый вывод**: при включённом `Streaming output` ответ появляется по мере генерации.
- **Персистентность**: история сообщений, элементы working- и long-term-памяти, инварианты, активный профиль и активная линия хранятся в SQLite и восстанавливаются после перезапуска приложения.
- **Ошибка API**: частичный ответ не сохраняется, а существующая история не теряется — неполный ход откатывается из памяти и в базу не пишется, прежние сообщения, память и профиль остаются на месте.
- **Профили и память — разные сущности**: профиль хранится в отдельной таблице, не превращается в элементы working- или long-term-памяти и не смешивается с ними.

### Трудности

- профиль нужно было провести отдельным слоем, не смешав его с памятью, system prompt и invariants;
- удаление активного профиля не должно ломать чат: ссылка обнуляется в одной транзакции, а агент перечитывает профиль перед каждым запросом и безопасно переходит в `No profile`;
- важно было структурно исключить профиль из служебных вызовов — это достигнуто тем, что сводка и факты собираются отдельными builder-ами, а не через `_build_payload`;

## День 13. Task State Machine

Задача дня — превратить агента с памятью в агента с **формализованным и сохраняемым состоянием задачи**: поставить работу на паузу, полностью закрыть и заново запустить приложение и продолжить с того же места, не объясняя цель повторно и не выполняя заново уже завершённые шаги. Разделение интерфейса на `Chat` и `Diagnostics / Memory` (раздел выше) — внутренний этап проекта; официальный День 13 — этот раздел.

### Что реализовано

- домен `Task`/`TaskArtifact`/`TaskEvent`/`WorkflowProfile` в чистом слое без Streamlit и SQL;
- конечный автомат `planning → execution → validation → done` с проверяемыми preconditions и запретом недопустимых переходов;
- независимые статусы `active / paused / blocked / completed / cancelled`;
- хранение задач, артефактов, событий и workflow-профиля в SQLite (`data/chat_history.db`);
- optimistic locking через `version`, append-only журнал событий и неизменяемые артефакты;
- `Pause` и `Resume`, переживающие полный перезапуск приложения;
- продолжение после перезапуска без повторного выполнения завершённых шагов;
- принятие и отклонение плана (`Accept plan` / `Reject plan`) и повторное планирование;
- валидация отдельным действием; возврат только к дефектным шагам после провала;
- `Retry` после ошибки API без сохранения частичного результата;
- отдельный context packet для каждой стадии; task-вызовы не попадают в историю, память и статистику обычного чата;
- режим `Diagnostics / Task` с журналом, артефактами, workflow, preview пакета и суммарной статистикой задачи;
- компактный вертикальный индикатор стадий и карточка задачи в `Chat`, компактный итог и `Open full result`;
- один default workflow (`Default workflow`) с возможностью добавления других без миграции схемы.

### Стадия и статус — разные измерения

`stage` отвечает на вопрос «на каком этапе работа», `status` — «в каком она состоянии». Новая задача создаётся как `stage = planning`, `status = active`. Пауза не становится отдельной стадией.

| Измерение | Значения |
|---|---|
| `stage` | `planning`, `execution`, `validation`, `done` |
| `status` | `active`, `paused`, `blocked`, `completed`, `cancelled` |

При паузе сохраняются текущая стадия, текущий шаг, ожидаемое действие, результаты предыдущих стадий, причина паузы и версия задачи. `done` допустим только при `completed`; `paused`, `blocked` и `cancelled` не меняют стадию.

### Доменные сущности

| Сущность | Что хранит |
|---|---|
| `Task` | `id`, `chat_id`, `workflow_profile_id`, `title`, `goal`, `stage`, `status`, `current_step`, `current_step_index`, `expected_action_type`, `expected_action_text`, `pause_reason`, `version`, время создания и обновления |
| `TaskArtifact` | результаты стадий: `task_brief`, `specification`, `plan`, `execution_result`, `validation_result`, `final_result`; у каждого вида своя ревизия, артефакты не перезаписываются |
| `TaskEvent` | append-only журнал: `TASK_CREATED`, `PLAN_CREATED`, `PLAN_REJECTED`, `PLAN_ACCEPTED`, `STEP_COMPLETED`, `EXECUTION_FINISHED`, `VALIDATION_PASSED`, `VALIDATION_FAILED`, `PAUSE`, `RESUME`, `BLOCK`, `UNBLOCK`, `CANCEL`, `API_ERROR`, `RETRY` |
| `WorkflowProfile` | набор и порядок стадий, инструкции стадий, исполнитель, validation policy и будущие модели; в UI называется workflow |

`specification`, acceptance criteria, план и шаги появляются только как результат стадии `planning`: при создании задачи сохраняется только её постановка (необязательный `task_brief`), фиктивная спецификация не создаётся.

### Схема переходов

| Событие | Условие | Изменение | version |
|---|---|---|---|
| `TASK_CREATED` | задачи ещё нет | `planning` / `active`, ожидается `run_planning` | 1 |
| `PLAN_CREATED` | ожидается `run_planning` | остаётся `planning`; появляются `specification` и `plan`, ожидается `confirm_plan` | +1 |
| `PLAN_REJECTED` | ожидается `confirm_plan` | остаётся `planning`; ожидается `run_planning`, отклонённый план сохраняется в истории | +1 |
| `PLAN_ACCEPTED` | ожидается `confirm_plan` | `planning → execution`; текущий шаг — первый незавершённый | +1 |
| `STEP_COMPLETED` | `execution`, ожидается `run_step`, шаг не завершён | остаётся `execution`; новая ревизия `execution_result`, переход к следующему шагу или к `finish_execution` | +1 |
| `EXECUTION_FINISHED` | `execution`, ожидается `finish_execution`, все шаги завершены | `execution → validation` | +1 |
| `VALIDATION_PASSED` | `validation`, ожидается `run_validation`, вердикт пройден | `validation → done`, статус `completed`, появляется `final_result` | +1 |
| `VALIDATION_FAILED` | `validation`, ожидается `run_validation`, есть дефекты | `validation → execution`; текущим становится минимальный дефектный шаг | +1 |
| `PAUSE` | `active` на любой рабочей стадии | статус `paused`, стадия и шаг сохраняются | +1 |
| `RESUME` | `paused` | тот же статус `active`, та же стадия и тот же шаг | +1 |
| `BLOCK` | `active` или `paused` | статус `blocked`; требуются причина и ожидаемое действие пользователя | +1 |
| `UNBLOCK` | `blocked` | статус `active`, ожидаемое действие пересчитывается по состоянию | +1 |
| `CANCEL` | явное подтверждение | статус `cancelled`, стадия сохраняется | +1 |
| `API_ERROR` | рабочая стадия | только запись в журнал, задача не меняется | 0 |
| `RETRY` | последнее событие `API_ERROR`, задача `active` | только запись в журнал, затем повтор текущего действия | 0 |

Любая другая комбинация отклоняется доменным слоем и не оставляет записей. `done` и `cancelled` — терминальные состояния. UI не является источником истины: даже если кнопка скрыта, недопустимый переход отклоняется.

### Pause, Resume и восстановление после перезапуска

1. Задача ставится на паузу на любой рабочей стадии (`planning`, `execution`, `validation`) — `PAUSE` сохраняет стадию, текущий шаг и ожидаемое действие.
2. Приложение полностью закрывается, `run_app.bat` запускается заново.
3. Состояние читается из SQLite: цель, стадия, статус, текущий шаг, ожидаемое действие, артефакты, версия и полный журнал. Активная задача чата хранится в `app_state` (`active_task:<chat_id>`), поэтому после перезапуска открывается та же задача.
4. `Resume` возвращает **ту же задачу и ту же стадию** в `active`; новая задача не создаётся, завершённые шаги повторно не выполняются.
5. Повторный `Resume` или повторная отправка события не создают дублей: переход проверяется доменом до записи, изменение состояния защищено optimistic locking по `version`, ревизии артефактов уникальны, повторный ключ идемпотентности отклоняется.

### Validation как отдельное действие и переделка

- `Run validation` — отдельное действие, поэтому задачу можно поставить на паузу прямо в стадии `validation`.
- При провале сохраняется `validation_result` с перечнем дефектов, задача возвращается в `execution`, текущим становится минимальный дефектный шаг, а дефекты попадают в context packet следующего шага.
- Ранее успешно завершённые шаги не повторяются: завершённость шага определяется только по артефактам. Исправление сохраняется новой ревизией `execution_result`, после чего валидация запускается повторно. При нескольких дефектах они исправляются по одному.

### Ошибки API и Retry

- Ошибка до первого токена, обрыв во время stream, обрезанный или невалидный ответ модели, превышение контекста — это `API_ERROR`: задача не меняется, `stage` и текущий шаг остаются прежними, артефакт не создаётся, частичный ответ не сохраняется, история чата и память не теряются.
- Структурированные ответы стадий делают один повтор с увеличенным бюджетом; если снова обрезка или невалидный JSON — записывается ошибка соответствующего вида.
- `Retry` доступен, только когда последнее событие — `API_ERROR` и задача активна; повтор выполняется ровно для текущего действия и даёт ровно одну новую ревизию артефакта.
- В событии сохраняются вид ошибки, усечённое сообщение, `finish_reason` и usage; секреты и полные служебные промпты в журнал не пишутся.
- Потоковый вывод: при `Streaming output` шаг исполнения стримится, индикатор ожидания показывается до первого чанка, в базу попадает только успешно завершённый результат.

### Сборка контекста для модели (context packet)

Служебный контекст задачи собирается приложением перед каждым stage-вызовом и передаётся модели как структурированный пакет, но **не записывается в историю или память обычного чата**. Порядок блоков:

1. базовый system prompt;
2. invariants;
3. активный пользовательский профиль;
4. инструкции текущего workflow и стадии;
5. task snapshot: цель, стадия, статус, текущий шаг, ожидаемое действие, версия;
6. только необходимые артефакты прошлых стадий (для `execution` — принятый план, для `validation` — спецификация, acceptance criteria и результат исполнения);
7. релевантные элементы working- и long-term-памяти;
8. часть истории, выбранная текущей стратегией контекста (вся история автоматически не отправляется);
9. текущее действие (шаг, валидация или планирование).

Порядок task-пакета отличается от порядка обычного чата: в пакете задачи инварианты идут перед профилем. Это расширение Дня 12: профиль участвует в stage-вызовах, но по-прежнему не участвует во внутренних служебных вызовах сводки и извлечения фактов. Payload обычного чата не изменился. `Diagnostics / Task` показывает preview пакета следующего вызова с ≈ токенами и ≈ стоимостью каждого блока; preview не выполняет ни одного запроса к API.

### Учёт task-вызовов

Task-вызовы не пишут сообщения и ходы в таблицы чата, не меняют его счётчики и статистику и не запускают сжатие истории или извлечение фактов. Их usage (модель, токены, cache hit/miss, `finish_reason`, ≈ стоимость, число попыток) сохраняется в событии задачи, а суммарная статистика стоимости задачи показывается в `Diagnostics / Task` отдельной строкой.

### Интерфейс

- **Chat** — история, компактная карточка задачи и поле ввода. В карточке: вертикальный индикатор стадий (`planning`, `execution`, `validation`, `done` столбиком), badge `RUNNING`/`PAUSED`/`BLOCKED`/`COMPLETED`/`CANCELLED`, текущий шаг и ожидаемое действие под текущей стадией, кнопка `Details` с полным текстом задачи и только те действия, которые допустимы в текущем состоянии; для `blocked` дополнительно показываются причина и ожидаемое действие пользователя. Пока план ждёт подтверждения, рядом с `Accept plan`/`Reject plan` есть кнопка `Review plan` с полным планом.
- Результаты выполнения шагов остаются в основной области `Chat` читаемой панелью `Execution results`: заголовок `Step N of M: <title>`, текст шага и строка следующего действия. Вызов модели идёт в фоновом потоке процесса, поэтому перерисовка страницы и повторный клик не отменяют уже начатый шаг. Во время вызова виден статус `Running step N of M` и потоковый текст, кнопка шага недоступна; на завершённую запись панель строится из сохранённых артефактов и потому переживает перезапуск приложения. После перезапуска процесса реестр пуст, поэтому ложного busy нет.
- Индикатор различает состояния не только цветом: пройденные стадии бледные, уменьшенные и зачёркнутые с отметкой `✓`; текущая — яркая, крупнее и полужирная с маркером `●`; будущие — бледные, уменьшенные и не зачёрнутые с маркером `○`. Пауза и блокировка не меняют подсвеченную стадию.
- `Create task` открывает диалог с полями Title (обязательно), Goal (обязательно), Task brief (необязательно) и Workflow. В чате может быть несколько задач: `New task` создаёт новую, прежние остаются в списке. Если активной задачи нет, вместо индикатора показывается компактное приглашение создать или выбрать задачу.
- После завершения задачи показываются компактный итог, badge `COMPLETED`, кнопка `Open full result` (полный `final_result` с возможностью скопировать и перейти в `Diagnostics / Task`) и кнопка `New task`.
- **Diagnostics / Task** — список задач чата, поля задачи, читаемая секция `Plan` (summary, критерии приёмки, шаги; сырой JSON — по переключателю `Show raw JSON`), читаемая секция `Execution results` с результатами шагов, журнал событий, артефакты по видам и ревизиям, workflow (read-only), preview context packet и суммарная статистика задачи. Артефакты остаются техническим журналом: raw JSON теперь не единственный способ прочитать результат. Управление пользовательскими профилями осталось в `Diagnostics / Memory` и не смешивается с задачами.
- Карточка рассчитана на компактную высоту (ориентир — не более ~150 px): длинный текст сокращается, полный открывается кнопкой `Details`. Если на узком экране карточка мешает истории, предусмотрен fallback: карточка переносится в компактную секцию сайдбара (константа `TASK_CARD_LOCATION` в `app.py`).

### Хранение и миграция

Новые таблицы `workflow_profiles`, `tasks`, `task_artifacts`, `task_events` создаются в той же базе `data/chat_history.db` при первом запуске. Существующие таблицы не меняются, поэтому данные Дней 10–12 не теряются, а старая база открывается как раньше: у прежних чатов просто нет задач. Миграция идемпотентна, повторный запуск ничего не меняет; `default workflow` добавляется один раз. Удаление чата каскадно удаляет его задачи, артефакты и журнал; long-term memory при этом не затрагивается. Журнал append-only: события нельзя обновлять, обычный код только добавляет их, публичного удаления задач и событий нет.

4. ## Ограничения и оговорки

- **Автоматических записей памяти и автоподсказок нет**, RAG отсутствует — всё, что попадает в слои, добавляет пользователь вручную.
- `Promote` — это перенос, а не копирование: после него элемент существует только в Long-term.
- Ветка не наследует Working родительской линии; общий только Long-term.
- Ключ элемента уникален в пределах слоя и линии; ключи сравниваются точно (с учётом регистра).
- Приблизительный вклад слоя в prompt tokens — локальная оценка (`≈`), а не точный подсчёт провайдера.
- Русскими остаются служебные блоки, которые уходят модели (память, инварианты, сводка, факты, профиль); это сделано для сохранения поведения Дней 9–10. Значение по умолчанию для system prompt переведено на английский и касается только новых чатов.
- Перенос старой базы из Week 2 возможен вручную (копирование `data/chat_history.db`), но автоматически данные Week 2 в Week 3 не переносятся.
- Точная ширина иконок-кнопок и фактические 4px отступы проверяются визуально в браузере; автотесты подтверждают только CSS-правило и способ задания ширины.
- Привязка иконок чатов к правому краю сайдбара и внешний вид секции **User profiles** проверяются визуально: автотесты подтверждают структуру элементов, но не пиксельную вёрстку.
- Уникальность имени профиля обеспечивается проверкой на уровне приложения (без уникального индекса по нормализованному имени); при одновременной записи из нескольких сессий теоретически возможен дубль, для одного пользователя это не воспроизводится.
- Приоритет инвариантов над профилем закреплён детерминированно (порядок блоков и явное правило в заголовке); фактическое поведение модели на внешнем API не проверялось, так как реальные вызовы не выполнялись.
- Реальный вызов API при проверке не выполнялся: сетевые сценарии покрыты фиктивным клиентом, таймаутом и пустым ответом.
- День 13: автоматические сценарии используют FakeClient и моделируют граничные ответы (`finish_reason`, usage, обрезка, невалидный JSON, обрыв stream, превышение контекста); ручная live-приёмка с реальным провайдером пройдена (`LIVE_API_STATUS: PASS`).
- День 13: восстановление после перезапуска доказано интеграционно (новые экземпляры `ChatStore`/`TaskRepository` на том же файле базы) и запуском приложения через `smoke_test.bat`; ручной перезапуск с кликом `Resume` в браузере выполняет пользователь.
- День 13: бюджет высоты карточки задачи и fallback в сайдбар проверяются визуально в браузере на обычной и уменьшенной ширине; автотесты подтверждают структуру и текст, но не пиксельную вёрстку.
- День 13: доступен один `Default workflow`; добавление других профилей предусмотрено схемой, но в интерфейсе не реализовано.
- День 13: публичного удаления задач и событий нет — журнал append-only, задачи удаляются только каскадом вместе с чатом. Прямой `UPDATE` события отклоняется триггером, а обычный код журнала использует только `INSERT`; защита от `INSERT OR REPLACE` обеспечивается API репозитория и тестом.
- День 14: структурные инварианты — отдельная сущность, а не память, профиль или task state; они не становятся артефактами, не пишутся в `messages`/`turns` и не извлекаются из сообщений чата.
- День 14: `hard`-триггеры — это регистронезависимая подстрока. Формулировка с отрицанием («we should not skip validation») тоже может получить отказ. Это осознанное перестрахование (over-blocking), а не семантический разбор: провайдер не вызывается, ничего не сохраняется, задача и чат не портятся, а правило можно отредактировать или деактивировать.
- День 14: `advisory`-правила честно не считаются гарантией — они только уходят в контекст модели (self-check/review); проверить их программно на 100% нельзя.
- День 14: `INV-NO-DATA-RESET` запрещает массовый сброс/удаление данных по запросу пользователя; ручное удаление **одного** чата или ветки с явным подтверждением остаётся разрешённым и не изменилось. Разрушительного массового reset в приложении нет, поэтому проверка `no_bulk_reset` на стадии commit — объявленная страховка, а не рабочий путь.
- День 14: журнал конфликта хранит усечённый до 200 символов исходный запрос (`details_json`), чтобы зафиксировать сработавший триггер; сообщение при отказе в обычную историю не сохраняется.
- День 14: реальный внешний API для проверки инвариантов не требуется — поведение не зависит от ответа провайдера. Автоматические тесты изолированы от сети и `.env`; реальный браузерный F5 и полный перезапуск приложения — ручная проверка пользователя (машинная часть: AppTest rerun, повторное открытие SQLite и `smoke_test.bat`).

> Файл `.env` содержит секретный API-ключ и не попадает в Git благодаря `.gitignore`. База `data/chat_history.db` и её `-wal`/`-shm` также исключены из Git.

## День 13 — мини-отчёт и мини-пособие по теме

Это краткий отчёт о Дне 13 и одновременно пособие: что за задача дня, как устроено состояние, как пройти основной пользовательский путь и как проверить результат. Подробные технические детали остались в разделе «День 13. Task State Machine» выше; здесь они собраны компактно и дополнены темой состояния, статусов и Spec-Driven Development.

### Задание дня

Превратить агента с памятью в агента с **формализованным и сохраняемым состоянием задачи**: поставить работу на паузу, полностью закрыть приложение, запустить его снова и продолжить с того же места — без повторного объяснения цели и без повторного выполнения уже завершённых шагов. Предыдущие дни дали агенту память и персонализацию; День 13 добавляет durable-состояние самой работы.

### Что реализовано

- домен `Task`, `TaskArtifact`, `TaskEvent`, `WorkflowProfile` — чистый слой без Streamlit и без SQL;
- FSM `planning → execution → validation → done` с проверяемыми preconditions и запретом недопустимых переходов;
- независимые статусы `active`, `paused`, `blocked`, `completed`, `cancelled`;
- SQLite-хранилище задач, артефактов и append-only журнала в `data/chat_history.db` с идемпотентной миграцией;
- optimistic locking по `version`, неизменяемые артефакты с ревизиями, идемпотентность переходов;
- `Pause`/`Resume`, переживающие полный перезапуск; продолжение без повторного выполнения завершённых шагов;
- `Accept plan`/`Reject plan` с повторным планированием; валидация отдельным действием с возвратом только к дефектным шагам;
- `Retry` после ошибки API без сохранения частичного результата;
- per-stage context packet; task-вызовы не попадают в историю, память и статистику обычного чата;
- режим `Diagnostics / Task`; карточка задачи и вертикальный индикатор стадий в `Chat`; читаемые секции `Plan` и `Execution results`;
- фоновое выполнение шага (подробнее ниже).

### Состояние задачи (state)

Состояние задачи — это не только текущая стадия. В любой момент времени оно описывается набором согласованных данных, которые лежат в SQLite и переживают перезапуск приложения:

| Часть состояния | Что хранит |
|---|---|
| Постановка | `title`, `goal`, необязательный `task_brief` |
| Позиция в работе | `stage` (этап) и `status` (состояние) |
| Текущий шаг | `current_step`, `current_step_index` и ожидаемое действие `expected_action_type` / `expected_action_text` |
| Пауза и блокировка | `pause_reason` и ожидаемое от пользователя действие |
| Версия | `version` — счётчик успешных изменений состояния |
| Артефакты | последние и предыдущие ревизии результатов стадий |
| Журнал | полная история событий задачи |

У чата может быть несколько задач; активная задача хранится в `app_state` (`active_task:<chat_id>`), поэтому после перезапуска открывается та же задача. Источник истины — домен и БД, а не интерфейс: даже если кнопка скрыта, недопустимый переход отклоняется доменным слоем.

### Статусы задач

`stage` отвечает на вопрос «на каком этапе работа», `status` — «в каком она состоянии». Это два независимых измерения.

| Измерение | Значения |
|---|---|
| `stage` | `planning`, `execution`, `validation`, `done` |
| `status` | `active`, `paused`, `blocked`, `completed`, `cancelled` |

- `active` — работа идёт, ожидается обычное следующее действие;
- `paused` — работа приостановлена, стадия, шаг и ожидаемое действие сохранены; `Resume` возвращает ту же задачу и стадию;
- `blocked` — нужен пользователь: сохраняются причина и ожидаемое действие;
- `completed` — итог получен, возможен только на стадии `done`; терминальное состояние;
- `cancelled` — задача отменена с подтверждением, стадия сохраняется; терминальное состояние.

Новая задача создаётся как `stage = planning`, `status = active`. Пауза, блокировка и отмена не меняют стадию; они меняют только состояние.

### Конечный автомат (FSM)

Переходы выполняются только событиями и только при выполнении условий; любая другая комбинация отклоняется доменом и не оставляет записей.

| Событие | Условие | Что меняется |
|---|---|---|
| `TASK_CREATED` | задачи ещё нет | `planning/active`, ожидается `run_planning` |
| `PLAN_CREATED` | ожидается `run_planning` | появляются `specification` и `plan`, ожидается `confirm_plan` |
| `PLAN_REJECTED` | ожидается `confirm_plan` | ожидается новое планирование, старый план сохранён |
| `PLAN_ACCEPTED` | ожидается `confirm_plan` | `planning → execution`, текущий — первый незавершённый шаг |
| `STEP_COMPLETED` | `execution`, ожидается `run_step` | новая ревизия `execution_result`, переход к следующему шагу или к `finish_execution` |
| `EXECUTION_FINISHED` | все шаги завершены | `execution → validation` |
| `VALIDATION_PASSED` | вердикт пройден | `validation → done/completed`, появляется `final_result` |
| `VALIDATION_FAILED` | есть дефекты | `validation → execution`, текущий — минимальный дефектный шаг |
| `PAUSE` / `RESUME` | `active` / `paused` | меняется только `status` |
| `BLOCK` / `UNBLOCK` | `active`/`paused` / `blocked` | `status = blocked` / `active`, ожидаемое действие пересчитывается |
| `CANCEL` | явное подтверждение | `status = cancelled`, стадия сохраняется |
| `API_ERROR` | рабочая стадия | только запись в журнал, задача не меняется |
| `RETRY` | последнее событие `API_ERROR` | только запись в журнал, затем повтор текущего действия |

Состояние меняющие события увеличивают `version` на 1; `API_ERROR` и `RETRY` версию не меняют.

### Хранение в SQLite

- В той же базе `data/chat_history.db` создаются таблицы `workflow_profiles`, `tasks`, `task_artifacts`, `task_events`.
- Миграция идемпотентна: существующие таблицы не меняются, старая база открывается как раньше — у прежних чатов просто нет задач, данные Дней 10–12 не теряются.
- Артефакты неизменяемы: повторный шаг создаёт новую ревизию, а не перезаписывает старую.
- Журнал append-only: события только добавляются, `UPDATE` отклоняется триггером, публичного удаления задач и событий нет (задачи удаляются каскадом вместе с чатом).
- Изменение состояния защищено optimistic locking по `version` и ключом идемпотентности, поэтому повторная отправка не создаёт дублей.

### Фоновое выполнение шага

Обычный Streamlit rerun не должен влиять на сетевой вызов. Поэтому вызов провайдера для шага вынесен в **фоновый поток** процессного реестра (`task_runner.py`): реестр живёт в памяти процесса, а не в `st.session_state`, и запускает поток `step-run-<task_id>` под замком.

- первый `Run step` гарантированно продолжается, даже если страница перерисовалась или пользователь нажал F5;
- кнопка шага становится недоступной на время вызова, а повторный клик не может создать второй вызов;
- UI лишь следит за записью реестра: показывает `Running step N of M` и потоковый текст, а после завершения перечитывает результат из артефактов — поэтому он остаётся в панели `Execution results`;
- после перезапуска процесса реестр пуст, поэтому ложного «step is already running» нет; оборванный вызов можно запустить заново;
- фоновый поток не обращается к Streamlit — он только вызывает оркестратор и коммитит результат в SQLite.

### Пользовательский путь

1. `Create task` — Title и Goal (необязательно Task brief).
2. `Run planning` → `Review plan` — прочитать полный план, затем `Accept plan` или `Reject plan` (при отклонении план планируется заново).
3. `Run step` — фоновое выполнение шага: статус `Running step N of M`, потоковый текст, результат в `Execution results` вместе со строкой следующего действия.
4. `Finish execution` — после всех шагов стадия переходит в `validation`.
5. `Run validation` — при успехе `done`/`COMPLETED`, при провале возврат в `execution` только к дефектным шагам.
6. `Open full result` — полный финальный результат; затем `New task` или `Diagnostics / Task`.
7. В любой момент: `Pause`/`Resume`, `Block`/`Unblock` (с причиной и ожидаемым действием), `Cancel` (с подтверждением), `Retry` после ошибки API.

### Как запустить и проверить

Из `week-03/memory-state-agent`:

```powershell

.\test.bat        # полный unittest — 761 тест
.\smoke_test.bat  # поднимает приложение и проверяет health-check и корневую страницу
```

### Ручная приёмка

Пройдена с реальным провайдером:

- `Pause` → полное закрытие и повторный запуск → `Resume`: та же задача, стадия и шаг, завершённые шаги не повторяются;
- `Run step` во время выполнения: кнопка недоступна, идёт потоковый текст, результат остаётся в `Execution results`;
- F5 во время запуска и повторный клик: первый вызов не отменяется, второй не создаётся, вечного busy нет;
- состояние задачи и чаты в SQLite сохраняются, `execution_result` доступен;
- визуально проверены бюджет высоты карточки и раскладка на обычной и уменьшенной ширине (в т.ч. 1024×768).

## День 14. Инварианты и ограничения состояния

День 14 добавляет агенту **инварианты** — устойчивые правила, которые он не имеет права нарушать, даже если пользователь прямо просит обратного. Это не память, не профиль и не состояние задачи: инвариант отвечает на вопрос «какие решения и действия запрещены вообще».

### Задача

- хранить структурные инварианты отдельно от диалога, в SQLite, без извлечения из последних сообщений чата;
- дать каждому правилу стабильный код, название, текст, область действия, тип, способ проверки, версию, активность и источник;
- поддержать минимум два scope — `global` и `task`;
- передавать применимые правила в контекст модели и проверять `hard`-правила кодом до действия и до сохранения результата;
- при конфликте объяснить отказ, не выполнять запрещённое и не создавать ложный успех;
- не ломать FSM и данные Дней 10–13.

### Что реализовано

- чистый домен `invariants.py`: `Invariant`, `InvariantConflict`, `InvariantConflictError`, валидация, `select_applicable`, `format_structural_invariants_block`, `find_request_conflict` / `find_action_conflict` / `find_transition_conflict`, `evaluate_check`, `format_conflict_message`;
- `InvariantRepository` (`invariant_storage.py`): таблицы `invariants` и append-only `invariant_events`, идемпотентная миграция, сидирование дефолтов, CRUD без удаления, `record_conflict`;
- `hard`-enforcement в `ChatAgent.ask` (запрос), `TaskOrchestrator._guarded`/`retry` (действие) и `TaskOrchestrator._commit` (переход до записи);
- инжекция применимых правил в chat payload и в task context packet;
- секция `Invariants` в `Diagnostics / Task`, компактная строка ограничений в карточке задачи, событие конфликта в журнале;
- тесты unit / integration temp SQLite / FakeClient / AppTest и комплект спецификации `docs/specs/day-14-invariants/`.

### Чем инвариант отличается от памяти, профиля и FSM

| Сущность | Отвечает на вопрос | Область | Кто проверяет |
|---|---|---|---|
| Short-term / Working / Long-term memory | «Что мы узнали и хотим помнить?» | линия, чат, глобально | пользователь включает/выключает `Include` |
| User profile | «Как отвечать этому пользователю?» | активный профиль чата | стиль и ограничения ответа |
| Task state / FSM | «Где задача и что разрешено дальше?» | конкретная задача | домен (`tasks.py`), `can_apply` |
| **Invariant** | «Какие решения и действия запрещены вообще?» | `global` или `task` | `hard` — код; `advisory` — контекст/self-check |

Инвариант не становится элементом памяти, не превращается в артефакт и не пишется в `messages`/`turns`. Он живёт в отдельных таблицах и проверяется кодом до побочных эффектов. Свободнотекстовое поле **Invariants** в `Chat settings` (День 11) остаётся настройкой чата и никуда не исчезает; структурные инварианты — отдельная сущность рядом с ним.

### Модель правила

| Поле | Смысл |
|---|---|
| `code` | стабильный код, уникален и неизменяем после создания |
| `title`, `text` | название и текст правила |
| `scope` | `global` (вся система) или `task` (конкретная задача) |
| `task_id` | обязателен для `scope=task`, запрещён для `global` |
| `kind` | `guard`, `data` или `policy` |
| `enforcement` | `hard` или `advisory` |
| `check_kind` | структурная проверка (`no_validation_bypass`, `no_bulk_reset` или пусто) |
| `triggers` | фразы запроса, на которые срабатывает `hard`-правило |
| `guard_actions` / `guard_events` | запрещённые действия / переходы FSM |
| `alternative` | допустимый безопасный путь вместо отказа |
| `version` | растёт при каждом изменении |
| `is_active` | активность правила |
| `source` | `seed` (системное) или `user` (создано/изменено владельцем) |

### Hard и advisory правила

- **`hard`** — правило реально проверяется кодом до действия или до сохранения результата. Только активные `hard`-правила создают конфликт. В проекте есть три точки проверки: запрос, действие и commit.
- **`advisory` / semantic policy** — правило уходит в контекст модели как объяснение и учитывается в рассуждении, но стопроцентно доказать его выполнение программно нельзя. Оно **никогда не блокирует** запрос или действие и в интерфейсе не выдаётся за гарантию.

Из коробки сидируются три правила (один раз по маркеру `default_invariants_seeded`):

| Код | Scope | Enforcement | Что делает |
|---|---|---|---|
| `INV-NO-FSM-BYPASS` | global | hard | запрещает пропуск validation и завершение задачи без успешной проверки |
| `INV-NO-DATA-RESET` | global | hard | запрещает массовый сброс/удаление сохранённых данных по запросу агента |
| `INV-ADV-CONFIRM-DESTRUCTIVE` | global | advisory | напоминает уточнять последствия разрушительных действий; только контекст |

Правило можно создать, отредактировать и деактивировать во владельческом разделе `Diagnostics / Task → Invariants`. Редактирование повышает версию и меняет источник на `user`; удаления правил нет — деактивация сохраняет правило и его историю. После деактивации запрещённое действие проходит штатно.

### Точки enforcement

| Точка | Фаза | Что проверяется | Поведение при конфликте |
|---|---|---|---|
| `ChatAgent.ask` | `request` | `triggers` против текста сообщения | `InvariantConflictError` до payload/провайдера/`save_turn`; ничего не сохраняется |
| `TaskOrchestrator._guarded` | `action` | `guard_actions` против действия | `REFUSED` до вызова провайдера |
| `TaskOrchestrator.retry` | `action` | `guard_actions` против повторяемого действия | `REFUSED`, событие `RETRY` не пишется |
| `TaskOrchestrator._commit` | `commit` | `check_kind`/`guard_events` против перехода | `REFUSED` до `apply_transition`/`commit_transition`; ни одной записи в `tasks`, `task_artifacts`, `task_events` |

Проверка на фазе `request` использует `triggers`, на фазе `action` — `guard_actions`, на фазе `commit` — `check_kind` или `guard_events`. `advisory` не участвует ни в одной из них. FSM `tasks.py` не изменён: `hard`-правило может отказать в уже разрешённом по FSM действии, но не расширяет и не меняет сам автомат.

### Хранение и миграция

- Таблицы `invariants` и `invariant_events` создаются в той же `data/chat_history.db` через `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS` (без `ALTER`), поэтому миграция идемпотентна, а база Дня 13 открывается без потери данных.
- `invariant_events` — append-only: создание, изменение, активация, деактивация и конфликт; `UPDATE` отклоняется триггером. Внешних ключей на `chats`/`tasks` нет, поэтому удаление чата не стирает историю инвариантов.
- Конфликт сохраняет фазу, сработавший триггер/поверхность, действие или событие, решение `refused`, альтернативу и усечённый до 200 символов запрос.
- Публичного удаления правил нет; массового удаления или сброса данных не добавлено. Ручное удаление **одного** чата или ветки с подтверждением сохранено без изменений.

### Как инварианты попадают в контекст

- **Обычный чат**: блок структурных инвариантов добавляется после профиля и свободнотекстовых инвариантов и перед памятью. Без репозитория инвариантов payload остаётся прежним (Дни 10–13 не затронуты).
- **Task packet**: блок `structural_invariants` идёт сразу после свободнотекстовых `invariants` и перед профилем. Пустой блок пропускается, поэтому пакет без правил совпадает с Днём 13.

## День 15. Контролируемые переходы состояний

День 15 делает уже существующий автомат состояний **контролируемым снаружи**: недопустимый переход нельзя выполнить ни из UI, ни внешним вызовом, а отказ обрабатывается понятно, безопасно и наблюдаемо. Вторая машина состояний не создаётся — источник истины остаётся прежним.

### Задача

- у задачи есть допустимые состояния, между ними — только разрешённые переходы;
- ассистент, UI или внешний вызов не могут «перепрыгнуть» этап;
- нельзя начать execution до утверждённого плана;
- нельзя завершить задачу без успешной validation;
- корректно работают `Pause → restart → Resume`;
- попытка недопустимого перехода обрабатывается понятно и безопасно;
- нужны как положительные, так и отрицательные (red-path) сценарии.

### Что уже было и что реально добавлено

FSM, статусы, события, optimistic locking и append-only журнал появились в Дне 13, а `hard`-инвариант запрета обхода validation — в Дне 14. День 15 усиливает именно пробелы, не переписывая рабочее ядро.

| Уже было (Дни 13–14) | Реально добавлено в Дне 15 |
|---|---|
| FSM `planning → execution → validation → done`, `can_apply` как источник истины, `apply_transition` с preconditions | — (ядро не переписывалось) |
| `InvalidTransitionError` без записи при запрете | `TransitionDecision`, reason-коды и `explain_transition` — структурированное объяснение отказа на базе `can_apply` |
| Отказ возвращался как `noop` с кратким текстом | Понятная причина + **список действий, разрешённых сейчас** |
| Успешные переходы — `task_events`; конфликты инвариантов — `invariant_events` | Отдельная append-only таблица `task_transition_attempts` — аудит отказов FSM, не смешанный ни с успешными переходами, ни с конфликтами инвариантов |
| В `Chat` показывались только допустимые действия | Read-only панель `Transition guard` в `Diagnostics / Task`: состояние, allowed, решения по каждому действию, последние отказы |
| Активный чат помечался символом `▶` | Активная кнопка чата мягко подсвечена зелёным, `▶` убран |
| Рекомендованные кнопки визуально не отличались | `Review plan` и действие под текущий `expected_action_type` мягко подсвечены зелёным |

### Как устроены контролируемые переходы

- **Один источник истины.** `tasks.can_apply` возвращает точный набор действий для текущего состояния, `tasks.apply_transition` повторно проверяет preconditions и при нарушении бросает `InvalidTransitionError`, ничего не записывая. Это ядро Дня 13 не изменено.
- **Один вход для действий.** `TaskOrchestrator._guarded` спрашивает `can_apply` до любого шага. Если действие не разрешено — провайдер не вызывается, задача не меняется, возвращается `noop`.
- **Структурированный отказ.** `tasks.explain_transition(task, action, ...)` берёт allowed-набор из `can_apply` и добавляет причину: `task_not_found`, `task_is_terminal`, `status_paused`, `status_blocked`, `expected_action_mismatch`, `progress_incomplete`, `retry_requires_api_error`, `confirmation_required`, `action_not_allowed`, `invalid_transition`, `invalid_payload`. Обязательный unit-тест гарантирует, что `allowed` в decision никогда не расходится с `can_apply`.
- **Понятное сообщение.** `format_refusal` собирает английскую фразу: что за действие, почему отказано и что разрешено сейчас. То же сообщение видит пользователь, а действие остаётся неизменным.
- **Отдельный аудит.** Каждый отказ FSM best-effort добавляется в append-only таблицу `task_transition_attempts` (действие, состояние «откуда», причина, allowed-набор, время). Аудит не влияет на задачу: ни `stage`, ни `status`, ни `current_step`, ни артефакты, ни `version`, ни успешный журнал `task_events` не меняются. `UPDATE` аудита запрещён триггером, при удалении чата записи уходят каскадом.
- **Конфликты `hard`-инвариантов не дублируются.** Они по-прежнему пишутся в `invariant_events` (День 14) и не попадают в аудит переходов — это разные классы отказа.
- **`Retry` не ломается.** Отказы не пишутся в `task_events`, поэтому `latest_event_type` (по которому разрешён `Retry` после `API_ERROR`) работает ровно как раньше.

### Негативные сценарии: что запрещено и что происходит

| Попытка | Где отклоняется | Результат |
|---|---|---|
| `Run step` / `Run validation` до утверждения плана | `_guarded` (`run_step`/`run_validation` не в `can_apply`) | `noop`, провайдер не вызван, состояние не изменено, отказ `expected_action_mismatch` записан в аудит |
| `Finish execution` с незавершёнными шагами | `_guarded` + `apply_transition` | `noop` с причиной `progress_incomplete`; домен также требует завершённости всех шагов |
| Завершить задачу без успешной validation | `apply_transition` (`VALIDATION_PASSED` только из стадии `validation`) + `hard`-инвариант `INV-NO-FSM-BYPASS` | отказ до записи; задача не доходит до `done` в обход проверки |
| Любое доменное действие после `done`/`cancelled` | `can_apply` возвращает пустой набор | `noop` с причиной `task_is_terminal`, провайдер не вызван |
| `Cancel` без подтверждения | оркестратор | `noop` с причиной `confirmation_required`, ничего не записано |
| `Retry` без последнего `API_ERROR` | `can_apply` | `noop` с причиной `retry_requires_api_error`, событие `RETRY` не пишется |
| `Pause → полный перезапуск → Resume` | не запрет, а сценарий сохранения | та же задача, стадия и шаг, `version` +1, без дублей артефактов и событий |

### Аудит отказа: почему он отдельный

Успешные переходы, конфликты правил и отказы автомата — три разные вещи, и смешивать их нельзя. `task_events` — это история **изменений** задачи и источник `latest_event_type`; писать туда отказы значило бы испортить и историю, и логику `Retry`. `invariant_events` — журнал срабатывания `hard`-правил, у него другая семантика и другая жизнь. Поэтому отказы FSM хранятся в собственном append-only журнале `task_transition_attempts`, который ничего не меняет в задаче и никогда не выдаётся за её новое состояние. Панель `Transition guard` явно подписывает это пользователю.

### Правила формирования execution-плана (исправленный дефект)

Планирование — это отдельная стадия `planning`, из которой задача после `Accept plan` **неизбежно** переходит в `execution`. Поэтому шаги плана не могут требовать, чтобы задача одновременно была в `planning` и `execution`.

Реальный дефект: для задачи «Day 15 — ручная приёмка переходов» provider по умолчанию сгенерировал plan rev 1 с шагами «Проверка планирования», «Формирование плана», «Принятие плана». После `Accept plan` эти шаги невыполнимы, и проверка объявляла их не подтверждёнными.

Второй, неполностью исправленный случай: новый живой план больше не требовал текущего `planning`, но всё ещё содержал «Выполнить и проверить validation», «Проверить завершение задачи» и «На тестовой копии состояния…». Валидация и `done` наступают **после** execution, поэтому такие шаги невыполнимы при запуске, а «тестовой копии» в UI не существует.

Третий случай: guard пропустил семантически невыполнимый план, где шаг предлагал вернуть задачу `execution → planning` (такого пользовательского действия в UI нет), а шаг и **acceptance criterion** требовали подтвердить уже состоявшиеся `VALIDATION_PASSED` и `done`. На момент выполнения execution-шагов validation/done ещё не произошли, а acceptance criteria оцениваются уже в validation — значит и шаг, и критерий дали бы ложное «не подтверждено».

Что исправлено:

- `TASK_PLANNING_SYSTEM_PROMPT` явно задаёт правила формирования `plan.steps`: текущая стадия `planning` — это этап формирования самого плана; шаги плана выполняются в `execution` и должны быть действиями/проверками самой задачи;
- запрещено включать в план шаги про workflow-переходы (planning, формирование/просмотр/принятие/утверждение/отклонение плана, запуск/завершение execution, validation) — это внешние переходы, а не шаги;
- если шаг проверяет предыдущую стадию, он делает это **как уже состоявшийся факт** по Event timeline или артефактам (например: «Проверить, что событие `PLAN_ACCEPTED` зафиксировано в журнале»), а не выполняет планирование/принятие заново;
- то же напоминание добавлено в action-сообщение `build_plan_messages`, которое вместе с инструкцией входит в planning-пакет;
- **runtime-проверка:** `parse_plan_response` после структурной валидации вызывает `plan_violations` и отклоняет execution-невыполнимый план ещё до `PLAN_CREATED` (`ExecutionIncompatiblePlanError`); проверяются **обе поверхности** — `steps` и `acceptance_criteria`;
- **корректирующий retry:** при отклонении стадия планирования повторяет вызов один раз с большим бюджетом и добавляет `plan_retry_feedback` — отдельные перечни недопустимых шагов и критериев с инструкцией: проверки прошлых стадий — только как ретроспективные факты по Event timeline/артефактам, `validation`/`done` не могут быть ни шагами, ни критериями, а возврат в `planning` — только как проверка запрета через `Transition guard`/аудит отказов. Если и второй ответ невыполним, planning завершается `API_ERROR(invalid_response)`: задача, версия и артефакты не меняются, доступен `Retry`.

Классы нарушений (обе поверхности — шаги и критерии): **будущие стадии** (`VALIDATION_PASSED`/`VALIDATION_FAILED`, «выполнить/запустить/провести/дождаться validation», «стадия validation/валидации», `finish_execution`, `done`/`completed`/«задача завершена») — всегда, ретроспективная рамка не спасает; **прошедшие стадии** (`PLAN_CREATED`/`PLAN_ACCEPTED`, plan/spec rev 1, «проверка planning/планирования») — только без ретроспективной рамки (`Event timeline`, `timeline`, `журнал`, `истори`, `артефакт`); **несуществующий переход** («вернуть/возврат/откат … planning», `execution → planning`) — всегда, кроме явной проверки через `Transition guard`/аудит отказов/диагностику; **несуществующая сущность** («тестовая копия», «копия состояния») — всегда. Глаголы-реализации (`реализовать`, `добавить`, `настроить`, `написать`, …) снимают срабатывание будущих/прошедших стадий и нужны, чтобы задача, которая сама реализует validation/planning, не блокировалась; HARD-фразы не снимаются.

Регрессия закреплена обезличенными fixture в `task_demo.py` (`REPORTED_PLAN_REV1` — старый дефект, `REPORTED_LIVE_PLAN` — validation/done/test-copy в шагах, `REPORTED_LOOPBACK_PLAN` — возврат в `planning` в шаге и `VALIDATION_PASSED`/`done` в шагах и критериях, `CORRECTED_PLAN_EXAMPLE` — ретроспективные проверки и guard-проверка запрета) и тестами `tests/test_task_demo.py` / `tests/test_tasks.py` / `tests/test_task_orchestrator.py`: `plan_violations` детектирует нарушения с локацией `step`/`criterion` и правилом (`nonexistent_transition`/`requires_other_stage`/`missing_entity`), исправленный и канонический планы чисты, нейтральная задача про реализацию validation не блокируется, а FakeClient подтверждает корректирующий retry и отказ `invalid_response` без изменения состояния. Подробно — `docs/specs/day-15-transition-control/DEMO_PLAN.md`.

### Граница фактов storage и текста модели (execution-результат)

Отдельный дефект достоверности: после шагов 1–2 текст результата шага 2 сгенерировал несуществующие «EVT-EXEC-001…004», заявил «`PLAN_ACCEPTED` (переход в execution ещё не выполнялся)» и описал фиктивную траекторию — это противоречило реальному журналу (`TASK_CREATED`, `PLAN_CREATED`, `PLAN_ACCEPTED`, два `STEP_COMPLETED`) и состоянию UI.

Правило: **журнал и состояние принадлежат коду, а не модели.** Реализовано так:

- в execution-пакет код добавляет блок `task_facts` (сразу после `task_snapshot`), собранный из storage: `stage`/`status`/`current_step`/`current_step_index`/`expected_action_type`/`version`, реальный Event timeline (`id`, `event_type`, `created_at`) и последние отказы из аудита. Это снимок только для чтения;
- `TASK_EXECUTION_SYSTEM_PROMPT` и action-сообщение шага требуют опираться только на этот снимок: не выдумывать и не называть event IDs/имена событий журнала, не заявлять чужую стадию/статус, не пересказывать timeline/аудит своими словами; результат — только содержимое шага;
- `validate_step_text(text, facts)` проверяет свободный текст по снимку и отклоняет: вымышленные ID (`EVT-…`), числовые ссылки на события, которых нет в журнале, противоречащие снимку `stage`/`status`/«задача выполнена», а также отрицание уже записанного события или достигнутого перехода. Кадры проверки запрета (`Transition guard`, «аудит отказов», «запрещ») не считаются заявлением о факте; доменные термины без заявления о факте не банятся;
- при нарушении стадия делает один корректирующий retry с `step_retry_feedback`, при повторе — `API_ERROR(invalid_response)`; отклонённый текст не сохраняется;
- UI прикрепляет к результату шага **реальную** строку журнала (code-rendered `Journal: #id · type · created_at · from→to`), а полный timeline остаётся в `Diagnostics / Task`. Модель эти данные не формирует.

Регрессия: `tests/test_task_prompts.py` (unit на реальном фиктивном тексте), `tests/test_task_orchestrator.py` (шаги 1–2 через FakeClient: грязный результат отклоняется, при retry сохраняется чистый текст без вымышленных ID и противоречащего состояния; грязный×2 даёт `invalid_response` без записи), `tests/test_task_context.py` (пакет несёт реальные event id), `tests/test_task_ui.py` (строка журнала у результата).

### Недоказанный отказ: запрет выдуманной попытки и тестовый probe

Ещё один дефект достоверности: на шаге «Проверить запрет недопустимого перехода» модель начала результат с «Инициирован недопустимый переход из стадии execution», хотя в storage-снимке `task_facts.refusals` не было ни одной записи, Event timeline содержал только `STEP_COMPLETED`, а реально был лишь read-only просмотр `Transition guard` (`Finish execution` = no / `progress_incomplete`).

Что исправлено:

- **валидатор** (`task_prompts.validate_step_text`) получил reason `unconfirmed_attempt`: утверждение, что попытка/переход **был выполнен или отклонён** («инициирован переход», «попытка предпринята», «переход отклонён», «отказ зафиксирован», «audit #N»), допускается только при подтверждении из снимка `task_facts.refusals` (существующий `action`/`reason` или непустой аудит); неизвестный `audit #N` — `fabricated_reference`. Условные формулировки («был бы отклонён», «будет отклонён», «показывает, что …») не считаются утверждением о факте;
- **промпт execution** и корректирующий feedback требуют: факт попытки/отказа — только из `task_facts` (refusals/audit id), иначе описание read-only Guard даётся условно («Transition guard показывает, что Finish execution сейчас был бы отклонён с причиной progress_incomplete»);
- **тестовый probe** в `Diagnostics / Task → Transition guard`: безопасная кнопка `Test Finish execution` появляется, только когда `Finish execution` сейчас не разрешён. Клик вызывает тот же production-guard (`_guarded`), который пишет одну append-only строку в `task_transition_attempts` и возвращает реальный `reason` + `audit #id`; `stage`/`status`/`version`/`current step` и `task_events` не меняются, провайдер не вызывается. Если переход сейчас допустим, кнопки нет — тест ничего не выполняет и аудит не пишет. При hard-инварианте audit id честно отсутствует (отказ идёт в `invariant_events`);
- **факт из кода**: результат шага не «сочиняет» попытку — снимок `refusals` приходит в пакет из storage, валидатор сверяет с ним текст, guard-панель рендерит те же строки аудита; `Journal: #…` под результатом шага по-прежнему формирует код.

Регрессия: `tests/test_task_prompts.py` (реальный текст шага 3 без отказа → `unconfirmed_attempt`; с записью/условной формой → принято), `tests/test_task_orchestrator.py` (`TransitionProbeTest`: отказ → аудит есть, состояние неизменно, провайдер не вызван; allowed → аудита нет), `tests/test_task_ui.py` (кнопка probe в Diagnostics, клик пишет один аудит и показывает `#id`, в Chat кнопки нет).

Когда `Finish execution` разрешён, кнопки нет и запись не создаётся.

6. Доведите задачу до `done` (`Finish execution` → `Run validation` при успехе) — в карточке остаются только `Open full result`/`New task`, а любой доменный отказ в `Transition guard` имеет причину `task_is_terminal`.

### Мини-материал по теме: контролируемые переходы состояний

**Конечный автомат (FSM).** Задача — это система с конечным набором состояний (`planning`, `execution`, `validation`, `done`) и статусом (`active`, `paused`, `blocked`, `completed`, `cancelled`). Не всякая пара «состояние → событие» допустима: например, из `planning` нельзя сразу попасть в `validation`. Правила переходов живут в домене (`tasks.py`) и не зависят от интерфейса.

**Почему UI — не защита.** Скрытая кнопка не запрещает действие: пользователь может открыть старую вкладку, отправить событие повторно или вызвать код напрямую. Поэтому каждый переход проверяется в трёх местах: UI показывает только допустимое, use case (`_guarded`) отказывает до побочных эффектов, а ядро (`apply_transition`) ещё раз проверяет preconditions перед записью. Даже если кнопка «просочилась», домен отклонит переход.

**Guard-переходы и red-path.** Хорошая проверка автомата — это не только «happy path», но и попытки сломать правила: начать execution без утверждённого плана, завершить execution с незавершёнными шагами, получить `done` без успешной validation, действовать после `done`/`cancelled`. Такие сценарии называются red-path (негативными). Для них важно проверить не только сам факт отказа, но и отсутствие побочных эффектов: провайдер не вызван, состояние и версия не изменились, успешный журнал не тронут.

**Наблюдаемость отказа.** Отказ должен быть объяснимым: что за действие, почему оно запрещено и что разрешено вместо него. Ещё полезнее — постоянный аудит попыток. Но аудит отказа нельзя писать в журнал успешных переходов: смешение превратило бы историю изменений в свалку и сломало бы логику, которая опирается на «последнее событие». Поэтому аудит вынесен в отдельную append-only таблицу и явно помечается как «не изменение состояния задачи».

**Идемпотентность и восстановление.** Поскольку состояние лежит в SQLite и защищено optimistic locking по `version`, повторная отправка формы не создаёт дублей, а пауза переживает полный перезапуск приложения: после старта читается та же активная задача, и `Resume` возвращает её на ту же стадию и шаг.

- Активный чат в сайдбаре подсвечен зелёным без `▶`; рекомендованная кнопка карточки тоже зелёная.
- `Pause` переживает полный перезапуск; `Resume` возвращает ту же задачу, стадию и шаг.

### Сценарий демонстрационного видео (3–5 минут)

Запись: захват экрана, идите по таблице сверху вниз. Цель видео — доказать, что запрещённый переход не выполняется и не меняет состояние, а не просто переключение кнопок.

## QA. Изолированный Local LLM + browser E2E (`qa/`)

Общий переиспользуемый runtime для реальных browser-E2E на локальной OpenAI-compatible модели. Он не привязан к `memory-state-agent`: ядро (`qa/lib/`) работает с HTTP, процессами, браузером и отчётами, а сценарий конкретного проекта лежит в `qa/integrations/<project>/`. Первая интеграция и первый E2E-сценарий — Day 15 этого проекта.

### Точка входа и режимы

Запуск — из корня репозитория:

```powershell
.\qa\run_local_e2e.bat MOCK           # без реальной модели: локальный mock-провайдер
.\qa\run_local_e2e.bat AUTO           # по умолчанию: локальная модель, иначе MOCK + SKIPPED
.\qa\run_local_e2e.bat LOCAL          # требовать локальную модель; без неё — exit 2 (без mock-подмены)
.\qa\run_local_e2e.bat NETWORK        # только явный opt-in; в текущем объёме отказывает
.\qa\run_local_e2e.bat TESTS          # unit-тесты самого runtime
.\qa\run_local_e2e.bat SESSION_START  # live-сессия: поднять Qwen один раз (если endpoint не готов)
.\qa\run_local_e2e.bat SESSION_STOP   # закрыть live-сессию и освободить только свой процесс
```

Коды выхода: `0` — PASS, `1` — FAIL сценария, `2` — не выполнены предпосылки (нет локальной конфигурации/модели, занят порт, нет зависимостей), `3` — отказ `NETWORK`. `AUTO` никогда молча не уходит во внешний платный API: при недоступном локальном runtime он выполняет `MOCK`-прогон и фиксирует `LIVE_LOCAL_LLM: SKIPPED (<причина>)`.

### Live-сессия: одна загрузка модели на несколько прогонов

Для live-приёмки не нужно поднимать модель на каждый сценарий. Последовательность `SESSION_START → LOCAL → AUTO → SESSION_STOP` держит одну модель на всю сессию:

- `SESSION_START` запускает Qwen через неотслеживаемую конфигурацию, если endpoint ещё не готов; если сервер уже поднят (чужим процессом) — сессия использует его, **не** присваивает владение и не останавливает; если runner уже поднимал модель — повторный старт присоединяется к ней без второй загрузки;
- `LOCAL`/`AUTO` внутри активной сессии присоединяются к тому же процессу, не перезагружают модель и не останавливают её по завершении прогона;
- `SESSION_STOP` освобождает **только** процесс/дерево, принадлежащее runner'у. Уже запущенный чужой сервер не трогается; при неподтверждённом владении процесс остаётся жить и помечается как `orphan-unproven`;
- `MOCK`, `TESTS` и read-only проверки сессию не активируют и не создают её состояние.

### Локальная конфигурация

Локальный endpoint, имя модели, ключ и команда запуска сервера берутся из **неотслеживаемой** конфигурации `qa/local.llm.local.json` (или переменных окружения `QA_LOCAL_LLM_*`). В репозитории лежит только обезличенный пример `qa/local.llm.example.json` с плейсхолдерами; реальный путь и команда запуска модели в Git не попадают. Без конфигурации режим `LOCAL` возвращает `2`, а `AUTO` честно сообщает `SKIPPED`.

Runner не сканирует диски: порядок источников — переменные окружения, затем существующий `qa/local.llm.local.json`, затем уже поднятый loopback-endpoint. Узкий поиск лаунчера возможен только при явно заданных `QA_LOCAL_LLM_LAUNCHER` или `QA_LOCAL_LLM_SEARCH_ROOTS`. Существующий машинный лаунчер не копируется в проект: runner запускает его **только как дочерний процесс** своего `AUTO`/`LOCAL`, ждёт readiness и останавливает только тот процесс, который запустил сам.

### Изоляция

Каждый прогон использует свой временный каталог `qa/.runs/<время>-<режим>/` со своей SQLite-БД (`db/app.db`), логами, скриншотами и отчётами, а приложение — свой порт (`8599`). Рабочая БД, чаты, задачи и `.env` владельца не читаются, не меняются и не удаляются: runtime сравнивает отпечатки рабочей БД и `stat` `.env` до и после прогона и выносит результат отдельной проверкой. Зависимости runtime живут в отдельном `qa/.venv`.

### Что проверяет сценарий Day 15

Реальный браузер (Playwright, системный Edge/Chrome), а не AppTest: создание временной задачи → `Run planning` → `Review plan`/`Accept plan` → `Run step` (ровно столько шагов, сколько в утверждённом плане; число берётся из сохранённого плана, а не зашито) → проверка панели `Transition guard` → `Test Finish execution` (ровно одна append-only строка аудита отказа, состояние/версия/шаг/журнал/артефакты не меняются) → `Finish execution` → `Pause` → полный перезапуск приложения на том же порту и БД → `Resume`. По ходу сохраняются скриншоты, а `PASS/FAIL` решает код по данным SQLite, а не модель.

Отдельно воспроизводятся известные дефекты Day 15 как регрессии: план с будущими стадиями, выдуманные идентификаторы событий/противоречащий timeline текст шага и заявление о попытке перехода без refusal audit. Каждый такой ответ отклоняется runtime-guard, повторяется один раз с корректирующим feedback и в итоге не попадает в артефакты.

### Отчёт и метрики

Оркестратор пишет `report.md` и `report.json`: режим, провайдер, проверки, `LIVE_LOCAL_LLM`, скриншоты и блок фактического использования локальной модели — провайдер и модель, число локальных LLM-вызовов, `input`/`output`/`total` токены, TTFT, полное время и токены/с (только если сервер вернул `usage`/`timings`), а также число сетевых API-вызовов (`Network API calls: 0` при прогоне без сетевых LLM/API-вызовов; доступ в интернет для первой установки зависимостей — это не сетевой вызов модели и не обращение к внешнему API). Метрики берутся из реальных ответов сервера и суммируются по вызовам; если поля нет — в отчёте стоит `нет данных`, а не оценка по символам. Для `MOCK` метрики помечены как синтетические.

При работе через live-сессию в отчёт добавляется блок `Session`: `session started`/`stopped`, число реальных загрузок модели, число live-прогонов, использовавших её, и признак владения процессом (`runner`/`external`/`unproven`). Секретов, локальных путей и команды запуска в отчёте нет: они остаются только в неотслеживаемой конфигурации.

### Статус

Live-local подтверждён фактически в единой сессии `SESSION_START → LOCAL → AUTO → SESSION_STOP` на реальном llama-server/Qwen: `LIVE_LOCAL_LLM: OK`, реальные `usage`/`timings` (input/output/total, TTFT, tokens/s), `Network API calls: 0`, `model_loads: 1`, `live_runs: 1 → 2`, сценарии с фактическим числом шагов плана (5 и 4) дошли до `Resume`; `SESSION_STOP` освободил только свой процесс и удалил состояние. Unit: `qa`-набор 239 тестов OK, `week-03` — 1006 OK; отдельно проверены MOCK-E2E, `smoke_test.bat`, изоляция рабочей БД/`.env` и отсутствие утечек ключа и локального пути. Полностью непроверенными на живом уровне остаются ветка с недоказуемым владельцем (`orphan-unproven`) и негатив `LOCAL` при уже остановленном endpoint — они покрыты offline-тестами.
