## Что унаследовано от финальной Week 2

Приложение по-прежнему ведёт несколько независимых чатов, хранит полную переписку в SQLite и переживает перезапуск.

- Несколько чатов: создание, выбор, переименование, удаление с подтверждением, восстановление последнего выбранного чата.
- По одному набору настроек на чат: system prompt, модель, `temperature`, `max_tokens`, потоковый вывод, демо-лимит контекста, инварианты и стратегия контекста с её окнами.
- Пять стратегий контекста (`Full history`, `Summary (compression)`, `Sliding window`, `Sticky Facts (fact memory)`, `Branching`): стратегия влияет только на payload очередного запроса, полная переписка всегда хранится и отображается.
- Накопительная сводка (День 9): якорь покрытия, пакетные обновления, повторная попытка при обрыве, раздельный учёт успешных и оборванных вызовов.
- Sticky Facts (День 10): отдельный непотоковый вызов после пользовательского хода извлекает факты строго в JSON, факты со статусами `active`/`replaced`/`cancelled`.
- Ветвление (День 10): ветки от завершённого хода, дерево линий, переключение, изоляция соседних веток, удаление ветки без каскада, привязка сводки к линии.
- Статистика: точные токены и `finish_reason` из API, кэш hit/miss, оценочная стоимость, накопительные счётчики, сравнение диалогов, безопасный демо-лимит контекста.
- Миграции схемы SQLite: идемпотентное добавление колонок и таблиц без потери данных.

Полное описание Дней 6–10 приведено в `week-02/first-agent/README.md`; новый проект сохраняет эти функции и тесты (все проверки адаптированы под английские подписи).

## День 11. Модель памяти агента

### Задача

Реализовать три раздельных слоя памяти:

- Short-Term Memory — история текущего диалога;
- Working Memory — состояние текущей задачи, чата и линии;
- Long-Term Memory — явно сохранённые знания, доступные между чатами.

Пользователь должен контролировать, какие данные сохраняются и передаются модели.

### Что реализовано

- три слоя памяти;
- добавление, редактирование и удаление записей;
- Include для включения записи в контекст;
- Promote для переноса Working Memory в Long-Term Memory;
- изоляцию Working Memory между чатами и ветками;
- общую Long-Term Memory;
- сохранение после перезапуска;
- System Prompt и Invariants, которые не являются памятью;
- сжатие длинной истории.

### Как это работает

| Механизм | Назначение |
|---|---|
| Short-Term Memory | История текущего диалога |
| Working Memory | Состояние текущей задачи |
| Long-Term Memory | Общие знания между чатами |
| Include | Передача выбранной записи модели |
| Promote | Перенос рабочего знания в долгосрочное |
| System Prompt | Роль и стиль поведения агента |
| Invariants | Постоянные правила и ограничения |

Перед каждым запросом приложение формирует контекст из System Prompt, Invariants, включённых записей Working Memory и Long-Term Memory, истории текущего диалога и нового сообщения пользователя.

### Трудности

- после переноса основы предыдущего учебного проекта обнаружились конфликты унаследованных permissions;
- общие и ролевые permissions были разделены;
- для тестовых точек входа добавлены точные разрешения;
- после исправлений проведена полноценная приёмка памяти.

### Итог

## День 11 — explicit Memory Layers

### Три слоя и их области

| Слой | Что хранит | Область действия | Где хранится |
|---|---|---|---|
| **Short-term** | историю активного чата и активной ветки | активная линия | `messages` (`branch_id`) |
| **Working** | структурированные данные текущей задачи | чат + конкретная ветка (`NULL` = основная линия) | таблица `working_memory` |
| **Long-term** | профиль, устойчивые предпочтения, решения и знания | глобально, между всеми чатами | таблица `long_term_memory` |

Слои хранятся раздельно: элементы Working и Long-term не смешиваются с перепиской и не влияют на неё. Слои пишутся в SQLite и переживают перезапуск.

**Invariants и System Prompt не являются памятью.** Это отдельные настройки чата, они не становятся элементами слоёв и учитываются в статистике токенов отдельно.

### Явные операции

- **Add** — добавить элемент в Working или Long-term.
- **Edit** — изменить ключ и значение элемента.
- **Promote** — перенести элемент из Working в Long-term (операция «move»: исходный элемент удаляется, а не дублируется).
- **Forget** — окончательно удалить элемент из слоя.
- **Include in prompt** — чекбокс: включён ли элемент в блок, который уходит модели. Исключённые элементы видны в интерфейсе, но не попадают в запрос.

Операции выполняются **вручную**. Автоматических записей в слои памяти нет: ни одна стратегия контекста не создаёт и не меняет элементы памяти, автоподсказок и автоматического сохранения нет. RAG не используется.

Ветка не наследует Working основной линии: у новой ветки свой пустой Working-слой, который заполняется вручную. Long-term при этом остаётся общим.

### Как слои попадают в запрос

Блоки вставляются в payload **любой** стратегии сразу после system prompt в порядке:

1. инварианты (если заданы);
2. Working-память активной линии;
3. Long-term-память.

Каждый блок — отдельное `system`-сообщение. Если память пуста и инварианты не заданы, payload полностью совпадает с payload Дней 9–10 — поведение прежних стратегий не меняется. Демо-лимит контекста считается по финальному payload, поэтому включённые элементы памяти и инварианты участвуют в предпроверке переполнения.

### Ветвление

Short-term и Working расходятся по ветке, Long-term остаётся общим:

- история у каждой ветки своя (как и раньше);
- Working-элементы принадлежат конкретной линии: `NULL` — основная линия, иначе id ветки; sibling-ветки не видят элементы друг друга;
- Long-term виден из любого чата и любой ветки и переживает удаление чата или ветки.

Удаление ветки удаляет только её Working-элементы; удаление чата каскадно удаляет его Working; Long-term не затрагивается.

### Интерфейс слоёв

В основной области под историей чата есть секция **Memory layers** с четырьмя раскрывающимися панелями:

- **Short-term memory · current line** — активная линия, число сообщений и приблизительный размер её истории в токенах, компактная таблица сообщений.
- **Working memory · this chat & line** — область (чат и линия), приблизительный вклад слоя в prompt tokens, число включённых из общего числа элементов, чекбоксы `Include`, кнопки `Promote`/`Edit`/`Forget` и форма `Add`.
- **Long-term memory · shared across chats** — то же без `Promote`; пометка, что слой общий для всех чатов.
- **System prompt & invariants (not memory)** — отдельные оценки токенов и текст system prompt и инвариантов; здесь ничего не хранится как память.

Приблизительный вклад слоя в prompt tokens считается той же локальной эвристикой (`tokens.estimate_tokens`) и тем же форматированием блока, что и реальный payload; значение помечается `≈`. Оценка токенов — не токенизатор.

## System prompt и Invariants

System prompt задаётся в `Chat settings`. Рядом добавлено поле **Invariants** — правила, которые модель должна соблюдать всегда; они отправляются отдельным system-блоком и показаны отдельно от памяти. Инварианты хранятся в колонке `chats.invariants` и переживают перезапуск. Пустые инварианты не влияют на payload.

Изменение инвариантов (как и прочих настроек) сохраняется в SQLite и не вызывает платных вызовов модели.

## Хранение

Хранение по-прежнему отделено от интерфейса (`storage.py`, в `app.py` нет SQL). Схема Week 2 дополнена:

- `chats.invariants` — текст инвариантов (миграция добавляет колонку идемпотентно, у старых строк значение пустое);
- `working_memory` — `chat_id`, `branch_id` (`NULL` = основная линия), `item_key`, `value`, `included`, время; уникальность ключа в пределах линии обеспечивается двумя частичными уникальными индексами (отдельно для основной линии и для веток);
- `long_term_memory` — `item_key`, `value`, `included`, время; уникальный индекс по ключу, глобальная область.

Миграция совместима с базой финальной Week 2: старые таблицы и строки не изменяются, новые таблицы создаются при первом открытии, повторное открытие идемпотентно. Для чатов, перенесённых из Week 2, авто-заголовок по первой реплике работает и со старым значением `"Новый чат"`, и с новым `"New chat"`; пользовательский заголовок не перезаписывается.

## Иконки чатов в сайдбаре

В строке каждого чата — кнопки-иконки: карандаш (`Rename chat`) и корзинка (`Delete chat`). Иконка имеет по 4 пикселя внутренних отступа слева и справа до края кнопки, а ширина кнопки задаётся её содержимым (`width="content"`), поэтому при сворачивании и разворачивании боковой панели ширина кнопки не меняется. Удаление по-прежнему требует подтверждения.

## Структура проекта

- `memory.py` — чистый модуль памяти: слои, `MemoryItem`, валидация ключа/значения, форматирование блоков и вставка system-блоков в payload. Без I/O и без Streamlit.
- `tokens.py` — детерминированная локальная оценка токенов.
- `strategies.py` — константы и английские подписи стратегий контекста.
- `facts.py` — модель Sticky Facts, разбор JSON и сборка промпта (День 10, без изменений).
- `context.py` — сборка payload стратегий и сжатие истории (День 9, без изменений).
- `stats.py` — нейтральные контейнеры `TurnStats`, `AskResult`, `SummaryOutcome` и агрегаторы.
- `pricing.py` — тарифы и расчёт оценочной стоимости.
- `models.py` — реестр моделей и отображаемые названия.
- `agent.py` — агент: вызов API, стратегии, сводка, факты, ветки, загрузка слоёв памяти и вставка блоков в payload; не зависит от Streamlit.
- `storage.py` — `ChatStore`: схема и миграции, чаты, сообщения и линии, статистика, сводки, факты, ветки и операции памяти.
- `app_logic.py` — чистые помощники интерфейса: сравнение настроек, индикатор ожидания, оценка токенов сообщений.
- `app.py` — Streamlit-интерфейс: чаты, настройки, история, панели стратегий, статистика и секция Memory layers.
- `tests/` — `unittest`-набор: unit-тесты чистой логики, интеграционные тесты с реальной временной SQLite, FakeClient-сценарии агента и UI-проверки через Streamlit `AppTest` (без сети и без настоящего `.env`).
- `requirements.txt` — зависимости: `openai`, `python-dotenv`, `streamlit`; новых зависимостей нет.
- `run_app.bat` — запуск приложения двойным щелчком.
- `.env.example` — образец `.env` без настоящего ключа.

## Первый запуск

Приложение рассчитано на запуск в Windows 11 и не зависит от окружения, базы данных или путей предыдущих недель. Первый запуск можно выполнить сразу двойным щелчком по `run_app.bat`: скрипт сам создаст локальное окружение `.venv` и установит зависимости из локального `requirements.txt`. Если Python не найден, окно не закроется молча — будет показана понятная инструкция.

Ключ DeepSeek хранится только в `.env` (в Git не попадает):

```powershell
Copy-Item .env.example .env
notepad .env
```

Замените `your_api_key_here` своим ключом DeepSeek и сохраните файл. Если `.env` нет, приложение всё равно запускается и объясняет, что нужно добавить `DEEPSEEK_API_KEY`, — окно не закрывается молча. База `data/chat_history.db` создастся автоматически при первом запуске.

## Сценарий ручной проверки Дня 11

1. Создайте чат, отправьте пару сообщений и раскройте **Memory layers**.
2. В **Working memory · this chat & line** добавьте элемент: `project` → `Orbita`, `deadline` → `Friday`.
3. Снимите галочку `Include` у одного элемента и убедитесь, что приблизительный вклад слоя в prompt tokens уменьшился; включите обратно.
4. Измените значение через `Edit`, затем удалите ненужный элемент через `Forget` с подтверждением.
5. Перенесите элемент в общий слой через `Promote`: он исчезнет из Working и появится в **Long-term memory · shared across chats**.
6. Создайте второй чат: Long-term-элементы видны и там, а Working у нового чата пуст.
7. В панели **System prompt & invariants (not memory)** убедитесь, что system prompt и инварианты показаны отдельно от слоёв памяти.
8. Переключитесь на стратегию `Branching`, создайте ветку от завершённого хода и убедитесь, что Working ветки независим от основной линии, а Long-term — общий.
9. Перезапустите приложение: слои памяти, инварианты и активная ветка восстанавливаются из SQLite.
10. Сверните и разверните боковую панель: ширина иконок-кнопок переименования и удаления не меняется, у иконок сохранены боковые отступы 4px.

## Ограничения и оговорки

- **Автоматических записей памяти и автоподсказок нет**, RAG отсутствует — всё, что попадает в слои, добавляет пользователь вручную.
- `Promote` — это перенос, а не копирование: после него элемент существует только в Long-term.
- Ветка не наследует Working родительской линии; общий только Long-term.
- Ключ элемента уникален в пределах слоя и линии; ключи сравниваются точно (с учётом регистра).
- Приблизительный вклад слоя в prompt tokens — локальная оценка (`≈`), а не точный подсчёт провайдера.
- Русскими остаются служебные блоки, которые уходят модели (память, инварианты, сводка, факты); это сделано для сохранения поведения Дней 9–10. Значение по умолчанию для system prompt переведено на английский и касается только новых чатов.
- Перенос старой базы из Week 2 возможен вручную (копирование `data/chat_history.db`), но автоматически данные Week 2 в Week 3 не переносятся.
- Точная ширина иконок-кнопок и фактические 4px отступы проверяются визуально в браузере; автотесты подтверждают только CSS-правило и способ задания ширины.
- Реальный вызов API при проверке не выполнялся: сетевые сценарии покрыты фиктивным клиентом, таймаутом и пустым ответом.

> Файл `.env` содержит секретный API-ключ и не попадает в Git благодаря `.gitignore`. База `data/chat_history.db` и её `-wal`/`-shm` также исключены из Git.
